# CLAUDE.md — манифест проекта TradeDesk

Правила для AI‑ассистентов в этом репозитории.

**Разделение документов:** `DEVELOPER_MANUAL.md` описывает **как мы работаем** (процесс, роли, ревью, релизы) и не привязан к проекту. Этот файл описывает **проект**: стек, границы, конвенции, DoD. `docs/WORKFLOW.md` — проектная настройка процесса (трекер, ветки, worktree).

Продукт: журнал сделок с автосинком из MetaTrader 5, дашборд, аналитика. Рабочее название — TradeDesk.

## 2. Стек и границы

- **Backend:** Python 3.12, FastAPI, async SQLAlchemy 2, Alembic, arq. `arq` стоит и работает: сервис `worker`, точка входа `apps/api/app/worker.py` (`X-25`). `boto3` и `pandas` разрешены `SPEC.md` §2.3, но в зависимостях их ещё нет — придут со своими задачами.
- **Frontend:** Vite + React 19 + TypeScript, TanStack Query/Table, Tailwind, shadcn/ui.
- **Коллектор:** Python + `MetaTrader5`, только Windows, вне Docker, синхронный код.
- Список разрешённых зависимостей — `SPEC.md` §2.3. Новая зависимость — только с обоснованием в PR.
- Все счета в USD (v1). Всё время в БД — UTC `timestamptz`. Деньги — `numeric(18,2)`, цены и объёмы — `numeric(18,8)`.
- Пользователь имеет много счетов; любой пользовательский список принимает `account_ids`. Никогда не привязывай сделки/позиции/рефлексии к `user_id` напрямую.
- `deals` — append‑only факты брокера. `positions` пересобираются из deals. Пользовательский слой (`journal_entries`, `reflections`, `attachments`) никогда не затирается пересборкой.

## 4. Команды

Полный список с пояснениями — `make help`, и он же источник правды: разошёлся с этим разделом — прав `make help`. Заглушек среди целей больше нет, все перечисленные работают.

**Гейт перед PR:**

```
make ci        # ВЕСЬ гейт: ci-api + ci-web. Ровно тот же состав гоняет GitHub Actions
make ci-api    # lint-api + lint-collector + lint-hooks + test-api + test-collector + test-release + test-scripts
make ci-web    # lint-web + test-web + build-web
make ci-target # ruff + mypy + unit-тесты на ЦЕЛЕВОМ Python 3.12 в контейнере
```

**Окружение разработки:**

```
make install   # .venv + зависимости обоих python-пакетов + npm ci. Предусловие для всего остального
make hooks     # pre-commit install (после make install)
```

**Локальное окружение в Docker:**

```
make init      # .env из .env.example с генерацией секретов. Существующий .env НЕ перезаписывает
make up        # docker compose --profile local up -d --build, ждёт готовности, печатает URL
make down      # остановка; данные в volume остаются
```

**Данные установки (`T-02`, единственные команды, работающие на данных человека):**

```
make backup                       # проверенный дамп в backups/td-<дата>.sql.gz, хранит 14
make restore file=backups/….gz    # показывает, что перезапишет, и требует слова restore
make update [ARGS=--check]        # сверка MASTER_KEY → backup → архив релиза поверх → build → up
```

**Проверки по отдельности:**

```
make lint      # = lint-api + lint-collector + lint-web
make lint-api / lint-collector    # ruff check + ruff format --check + mypy
make lint-web                     # eslint + prettier --check + tsc --noEmit
make lint-hooks                   # pre-commit run --all-files
make test      # = test-api + test-collector (pytest) + test-web (vitest)
make build-web # vite build
make smoke     # playwright-смоук входа против поднятого make up. В make ci НЕ входит
make format    # автоформат
```

**Релиз (`docs/RELEASE.md`):**

```
make release VERSION=vX.Y.Z   # zip в dist/ + sha256. Ту же цель по тегу зовёт CI
```

**Схема и типы:**

```
make migrate           # alembic upgrade head в .venv (в контейнере это делает старт api)
make revision m="…"    # новая alembic-миграция (autogenerate)
make downgrade [to=…]  # откат на шаг назад
make types             # openapi запущенного api → apps/web/src/api/schema.d.ts. Требует make up
```

Установка и первый запуск для человека, который репозитория не знает, — `SETUP.md`.

Коллектор MT5 собран целиком: процесс одного счёта (`S1-08`) — подключение к терминалу, окно выборки, батч, heartbeat, — менеджер процессов над ним (`S1-09`, `python -m collector.main`) и установка (`S1-10`): `run-collector.bat` (нужен Python **3.12**, ставит `.venv` и зависимости, собирает `collector.env`, запускает менеджер), `install-service.bat` / `install-service.ps1` (автозапуск через Планировщик заданий), `stop-collector.bat` (остановка без сирот: сначала просьба менеджеру выйти самому, потом сила) и `status-collector.bat` (состояние задачи, процессы и хвост лога). Всё гоняется `make test-collector`. Запустить его можно только на Windows: библиотеки `MetaTrader5` под macOS и Linux не существует, поэтому на машине разработки проверяются лишь чистые функции, цикл на подделках, `spawn` дочернего процесса и байты файлов установки. **Ни одна строка коллектора на Windows не выполнялась**; сценарии ручного прогона — `docs/collector-windows-checklist.md` (вход в `T-06`).

⚠️ `make ci` включает `pre-commit run --all-files`, а часть хуков умеет править файлы (`ruff --fix`, форматтеры). Прогон гейта может изменить рабочее дерево — это не поломка, а поведение хуков.

⚠️ `make ci-target` **дополняет** `make ci`, а не заменяет её: он гоняет ruff, mypy и unit-тесты на целевом Python 3.12 в контейнере, но без pre-commit и без интеграционных тестов (testcontainers не достаёт опубликованный порт из sibling-контейнера). Нужен, потому что на машине разработки стоит 3.14: локальный зелёный прогон на ней не доказывает зелёный CI. Авторитетная проверка остаётся за GitHub Actions.

## 5. Правила кода

- **Python:** `ruff` (line‑length 100), типы везде, `mypy --strict` для `domains/ingest` и `domains/analytics`. Async в API; в коллекторе — синхронный код.
- **TypeScript:** strict, `any` запрещён; импорты через `@/`; строки UI только в `src/i18n/ru.ts`.
- **API:** префикс `/api/v1`, snake_case, ошибки в формате `SPEC.md` §5.1 (`{"error": {"code", "message", "details"}}`), курсорная пагинация, время ISO 8601 с `Z`.
- **Валидация — на границе API один раз**, pydantic v2. Внутри системы повторно не валидировать.
- **Миграции** только вперёд‑совместимые (`SPEC.md` §11.4): новые колонки nullable или с default; переименование — добавление + backfill + удаление в следующем релизе.
- **Комментарии — «почему», не «что».** Комментарии‑отчёты о проделанной работе запрещены. Длинные объяснения — в `docs/`.
- **Секреты, пароли, токены** — никогда в логах, фикстурах, тестах, коде. Фикстуры deals — обезличенные. Пароль счёта читается только эндпоинтом `GET /internal/collector/assignments` и никогда не возвращается в пользовательский API.
- Не трогай `packages/shared-schemas/ingest-deals.schema.json` без синхронного обновления pydantic‑моделей, коллектора и теста соответствия.

## 6. Тесты

Обязательны для: `normalizer.py`, `position_builder.py` (фикстуры `tests/fixtures/deals`), идемпотентности `/ingest/deals`, auth‑потока, формул `analytics/metrics.py`.

- Интеграционные тесты — через testcontainers. Сейчас поднимаются Postgres и Redis; minio добавится с вложениями в `S2-04`. Не мокай базу там, где тестируется SQL.
- Тестовая БД защищена guard'ом: имя обязано содержать `_test`; guard кидает исключение до первого запроса.
- Порог покрытия `ingest` и `analytics` — 90 %. **Пока не измеряется:** `pytest-cov` нет в зависимостях. Домен `domains/analytics` появился с `S2-05` и под `mypy --strict` уже ходит; порог включится вместе с `pytest-cov`.
- Новый код‑путь = тест. Нет теста — явное «почему нет» в итоге.
- Перед PR: **`make ci` зелёный**. Это единственная точка правды — CI вызывает те же цели, поэтому локальный гейт и удалённый совпадают. `make lint && make test` — подмножество: мимо них проходят `lint-hooks` (в том числе `detect-private-key`) и `build-web`.

## 7. Definition of Done

Адаптация `DEVELOPER_MANUAL.md` §6.4 под этот стек. Неприменимый пункт помечается явно, не пропускается молча.

- [ ] Код написан, типы строгие; нет `any` (TS), нет необоснованного `Any` (Python).
- [ ] Валидация pydantic на границе для новых/изменённых эндпоинтов.
- [ ] `make lint` и `make test` зелёные (или явно — что именно гонялось вместо них и почему).
- [ ] Для нового кода есть тесты или явно сказано, почему нет.
- [ ] При изменении схемы — миграция создана, `upgrade head` и `downgrade` проверены; при изменении API — `make types` перегенерирован.
- [ ] UI‑изменения проверены в браузере (или явное «в браузере не проверял»).
- [ ] Секреты не попали в код, логи, фикстуры, вывод команд.
- [ ] Никаких комментариев «что сделано» в коде.
- [ ] Дифф содержит только файлы задачи. **Исключение — документ, который стал неверным из-за этой задачи:** его правка законна и обязательна, см. следующий пункт. Ревьюер не считает её выходом за скоуп.
- [ ] Если задача изменила состояние проекта — появилась команда, заработал компонент, изменилось то, что документы называют «пока не готово», — соответствующий документ поправлен **в том же PR**: `SPEC.md`, этот файл, `README.md`, `docs/metrics.md`, `docs/fixtures.md` и прочие, где записаны **решения и контракты**.
- [ ] **Исключение — шапка `SPEC.md` с номером версии и changelog'ом: её в ветке задачи НЕ трогают.** Раздел спеки (§5, §8, §9…) правится в ветке — это контракт, и ревьюер обязан видеть его в диффе. А номер версии и запись в changelog ставит оркестратор на `main`, **тем же коммитом, которым двигает доску в Done**. Причина механическая: changelog — одна физическая строка, к которой дописывает каждая задача, поэтому две параллельные ветки конфликтуют в ней **всегда**, а разводится это только вручную и только с переномерацией версии. Что писать в changelog — скажи в итоге задачи.
- [ ] **Исключение — `docs/PROJECT_CONTEXT.md`: в ветке задачи его НЕ трогают.** Он описывает **состояние** проекта, а состояние меняется в момент мержа, а не в момент написания кода. Его правит оркестратор на `main` сразу после мержа, **тем же коммитом, которым двигает доску в Done**. Это привязка к действию, которое и так происходит каждый раз, — иначе правка потеряется, ради чего весь этот пункт и заведён. Что писать — скажи в итоге задачи, оркестратор перенесёт.

⚠️ Пункт про документы добавлен по итогам `S0-09`, исключение для `PROJECT_CONTEXT.md` — по итогам четырёх подряд конфликтов слияния в нём (`S2-05`+`S2-07`, `S2-06`, `S1-04`+`T-02`): файл один, а правит его каждая задача, и параллельные ветки дерутся за соседние строки. Разводится это тривиально, но каждый раз, и содержательного смысла в правке из ветки нет — она описывает будущее, которое наступит только после мержа.

⚠️ Сам пункт добавлен по итогам `S0-09`. Документы писались авансом, под будущее состояние, и никто не возвращался их править: `CLAUDE.md` называл заглушками шесть работающих целей и ссылался на несуществующий `run-collector.bat`, `README.md` утверждал «кода ещё нет» при семи влитых задачах, `PROJECT_CONTEXT.md` — «приложения пустые». Ревью диффа такое не ловит: файл не в диффе, значит его не смотрят. Ловит только этот пункт.

## 8. Ask first — остановиться и спросить

Проектное дополнение к `DEVELOPER_MANUAL.md` §3.2:

- Изменение зафиксированного в `SPEC.md` решения — сначала предложение текстом или `docs/adr/NNNN-<slug>.md`, потом код. Молча не менять.
- Новая зависимость вне `SPEC.md` §2.3.
- Изменение схемы ответа существующего эндпоинта — фронт генерирует типы из OpenAPI.
- Изменение `ingest-deals.schema.json`, инвариантов `deals`/`positions`, auth‑флоу.
- Смена схемы шифрования credentials или ротация `MASTER_KEY` на данных.
- Деструктивные операции против не‑тестовой БД — сначала показать SQL.
- Рефакторинги >2 файлов, не связанные с текущей задачей.
