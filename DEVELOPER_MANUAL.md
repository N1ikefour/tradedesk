# DEVELOPER_MANUAL.md — операционная система разработки

Универсальный документ о том, **как мы работаем**: процесс, роли, агенты, стандарты, ревью, релизы, безопасность и правила взаимодействия. Он не привязан к конкретному проекту и переносится в любой новый репозиторий.

**Роли в тексте:**
- **Принципал** — владелец проекта (человек). Принимает продуктовые решения, мержит PR, закрывает задачи, владеет секретами и аккаунтами.
- **Оркестратор** — основная сессия AI-ассистента. Координирует работу, запускает специализированных агентов, собирает итоги, деплоит по подтверждению.
- **Агенты** — специализированные субагенты (backend / frontend / infra / qa / reviewer / lead), каждый работает в своей зоне под конкретной задачей.

**Как перенести в новый проект:**
1. Скопировать этот файл в корень нового репозитория.
2. Создать `CLAUDE.md` / `AGENTS.md` с проектной спецификой (стек, команды, entry points) — этот документ описывает систему, те — проект.
3. Завести проект в трекере (у нас Linear; далее `TICKET-N` — идентификатор задачи).
4. Создать скелет документации (см. § 10).
5. Зафиксировать язык проекта в трекере и UI (см. § 8).
6. Пройти чек-лист «Старт проекта» (§ 15.1).

**Bootstrap-протокол для ассистента.** Если принципал пишет запрос вида *«выстрой в этом проекте систему разработки по DEVELOPER_MANUAL.md»* — это команда выполнить перенос. Порядок:

1. Прочитать этот документ целиком.
2. Задать принципалу **минимальный опрос** (одним сообщением, с рекомендациями по умолчанию):
   - что за продукт и какой стек (или «порекомендуй стек»);
   - трекер: проект/префикс тикетов, есть ли доступ (MCP/API);
   - язык проекта (трекер, UI, коммуникация);
   - целевой прод (есть ли уже сервер/хостинг) или «пока только локально»;
   - одна ассистент-система или несколько (нужны ли зеркала агентов/skills);
   - какие роли агентов нужны сверх базовых § 4.1.
3. По ответам сгенерировать скелет: `CLAUDE.md`/`AGENTS.md`, доки § 10.1 (с честными заглушками «не определено» вместо выдуманных фактов), файлы агентов § 4.5, skills § 4.6 (только там, где уже есть домен), `.env.example`, тестовый каркас с guard'ами § 6.3.
4. Пройти чек-лист § 15.1 и показать принципалу отчёт: что создано, что отложено (нет данных), что требует его действий (аккаунты, секреты, доступы).
5. Не выдумывать: чего ассистент не знает о проекте — остаётся вопросом принципалу или пометкой TBD в доке, а не правдоподобной выдумкой.

Что **не переносится** файлом и требует действий принципала в каждом новом проекте: доступ к трекеру, аккаунты и секреты, серверы/хостинг, права на репозиторий, установка инструментов окружения.

## 1. Философия

### 1.1. Сначала думать, потом кодить
- Не предполагать молча. Все допущения проговариваются явно; при неопределённости — вопрос, а не догадка.
- Если у задачи несколько трактовок — предъявить их все, не выбирать втихую.
- Если существует более простое решение — сказать об этом. Возражать принципалу, когда есть инженерные основания.
- Непонятно — остановиться, назвать что именно непонятно, спросить.

### 1.2. Simplicity first
- Минимум кода, решающего задачу. Ничего «на будущее»: ни фич, ни абстракций для одноразового кода, ни «гибкости», которую не просили, ни обработки невозможных ошибок.
- Тест: «Скажет ли сеньор, что это переусложнено?» Если да — упростить. 200 строк, которые могли быть 50 — переписать.

### 1.3. Хирургические изменения
- Трогать только то, что нужно для задачи. Каждая изменённая строка должна прослеживаться до запроса.
- Не «улучшать» соседний код, комментарии и форматирование. Стиль — как в окружающем коде, даже если сам сделал бы иначе.
- Заметил мёртвый код или чужую проблему — упомянуть, не чинить молча (для существенных находок — отдельный тикет).
- Свои осиротевшие импорты/переменные — убирать; чужой pre-existing мусор — нет.

### 1.4. Goal-driven execution
- Задача превращается в проверяемый критерий: «добавь валидацию» → «тесты на невалидные входы, потом они зелёные»; «почини баг» → «тест, воспроизводящий баг, потом он проходит».
- Сильные критерии позволяют работать автономно циклами «сделал → проверил». Слабые («сделай чтобы работало») требуют постоянных уточнений — их надо усиливать до старта.

### 1.5. Культура верификации
- «Готово» произносится только после реальных проверок. Что не проверено — называется явно: «в браузере не проверял», «smoke не гонял, потому что…».
- Отчёты честные: тесты упали — сказать с выводом; шаг пропущен — сказать; сделано и проверено — сказать прямо, без хеджирования.
- Ревьюер различает «подтверждено чтением кода» и «подтверждено реальным прогоном» — и указывает, что именно сделал.

### 1.6. Фундамент раньше фич
- Инфраструктурные основания (очередь, шифрование, детерминированное применение env, тестовые guard'ы) строятся **до** фич, которые от них зависят. Это многократно окупается.
- Архитектура проектируется на несколько шагов вперёд, но реализуется только текущий шаг (см. 1.2).

### 1.7. Решения не пере-литигируются
- Принятое и зафиксированное решение не обсуждается заново без новых фактов. Новые факты — новое обсуждение с явной ссылкой на старое решение.

### 1.8. Код для следующего разработчика
- Читаемость важнее краткости. Новый человек (или новая сессия ассистента) должен восстановить картину по коду и живым докам, не спрашивая никого.

## 2. Общий workflow

### 2.1. Конвейер от идеи до релиза

```
Идея / запрос принципала
  ↓
Обсуждение: варианты, компромиссы, рекомендация     (оркестратор ↔ принципал)
  ↓
Фиксация решений (тикет / ADR / living-доки)
  ↓
Декомпозиция на блок задач с зависимостями          (lead / оркестратор)
  ↓
Для каждой задачи: ветка + worktree
  ↓
Реализация агентом-владельцем + тесты               (backend / frontend / infra)
  ↓
Code Review независимым reviewer-агентом (полный дифф)
  ↓
Закрытие замечаний тем же агентом (узкий скоуп)
  ↓
Commit → push → PR + авторитетный итог в трекере    (оркестратор)
  ↓
Merge                                                (ТОЛЬКО принципал)
  ↓
Deploy по явному подтверждению                       (оркестратор / infra)
  ↓
Пост-деплой верификация (health/ready/стабильность процессов)
  ↓
Обновление документации (отдельный docs-коммит) + памяти
  ↓
Уборка (worktree, ветки) → Done                      (Done — принципал)
  ↓
Следующая задача
```

### 2.2. Два трека работы

| Трек | Критерий | Где работаем | Процесс |
|---|---|---|---|
| **Тикетный** | Есть `TICKET-N` | Отдельный worktree `.{assistant}/worktrees/<TICKET-N>` | Полный конвейер § 2.1 |
| **Chat-driven** | Опечатка, hot-fix, обсуждение, доки | Основная папка репозитория | Правка → проверка → отдельный коммит в main |

Worktree обязателен для тикетов, потому что: (а) несколько агентов/ассистентов работают параллельно; (б) дев-сервер принципала смотрит на основную папку и не должен ломаться от незавершённой работы.

### 2.3. Правила конвейера
- **Контракт раньше потребителя.** Backend фиксирует API-контракт первым; frontend стартует после, получая контракт в брифе дословно. Так агенты не толкаются в одном worktree и не гадают о формах данных.
- **Параллельность — только для независимого.** Независимые задачи — параллельные агенты (в разных worktree). Зависимые — строго последовательно.
- **Батчинг деплоев.** Связанные задачи одного блока (например, backend+UI одной фичи) деплоятся вместе, когда полуфича бессмысленна в проде.
- **E2E руками принципала.** Пользовательские флоу (установка, оплата, онбординг) финально проверяет принципал на реальном устройстве/окружении. Оркестратор готовит точный сценарий проверки.
- **Итог в трекере — авторитетная запись.** После завершения работ оркестратор пишет в тикет структурированный итог (см. § 8.5): что сделано, контракт, решения, что проверено, что осталось.

## 3. Работа с архитектурой

### 3.1. Как принимаются решения
- Архитектурные развилки не решаются молча. Оркестратор готовит **варианты + компромиссы + рекомендацию** (первым — рекомендуемый вариант и почему). Принципал выбирает.
- Формат обсуждения: короткая таблица/список «вариант → плюсы → минусы → когда выбрать», затем «моя рекомендация: X, потому что…».
- Ассистент проводит инженерную оценку идей принципала, а не соглашается автоматически. Возражение с обоснованием — обязанность, не опция.
- Если ассистент ошибся в оценке (например, неверно описал последствия) — исправление проговаривается явно и фиксируется там же, где было исходное утверждение.

### 3.2. Что требует согласования (ask first)
- Смена БД, добавление очереди/кэша/воркера, смена процесс-менеджера или хостинга.
- Новые библиотеки уровня платформы: state-management, i18n, CSS-фреймворк, UI-kit, другой тест-фреймворк.
- Изменение auth-флоу, инвариантов данных (уникальность, иммутабельность), контрактов внешних интеграций.
- Сужение согласованного скоупа приоритетных фич.
- Деструктивные операции против не-тестовых БД (сначала показать SQL).
- Рефакторинги >2 файлов, не связанные с текущей задачей.
- **Правило:** «Do not silently rewrite the stack». Инфраструктура меняется только в рамках согласованного плана.

### 3.3. Что делается без согласования (just do)
- Правки компонентов, страницы, багфиксы в существующих флоу.
- Новые поля существующих сущностей (миграция — с явным упоминанием в итоге).
- Валидаторы, audit-логирование, CRUD по существующим паттернам.
- Тесты для затрагиваемого кода.

### 3.4. ADR — записи архитектурных решений
Каждое значимое решение фиксируется письменно. Носитель — по ситуации: комментарий в тикете (наш основной способ), раздел living-дока, отдельный файл `docs/adr/NNN-<slug>.md` для крупных. Формат:

```markdown
# ADR-NNN: <название решения>
Дата: YYYY-MM-DD. Статус: accepted | superseded by ADR-MMM.

## Контекст
Какая проблема/развилка. Какие ограничения.

## Варианты
1. <вариант> — плюсы / минусы.
2. <вариант> — плюсы / минусы.

## Решение
Что выбрали и почему. Кто утвердил.

## Последствия
Что это включает/исключает. Что станет дороже. Когда пересматривать.
```

- Отменённое решение не удаляется — помечается superseded со ссылкой на новое.
- Исторические планы живут в `docs/archive/` и **не являются** источником текущей истины (см. § 10).

### 3.5. Когда архитектуру менять нельзя
- Посреди задачи ради «удобно же будет» — нет. Закончить задачу, предложить изменение отдельно.
- Под давлением дедлайна костылём, который ломает инвариант данных — нет. Лучше явно сузить скоуп с согласия принципала.
- Молча, попутно, «раз уж я здесь» — никогда.

### 3.6. Выработанные архитектурные принципы
- **Атрибуция данных — у правильного владельца.** Данные снапшотятся в момент события у сущности-источника, а не выводятся позже из связанных сущностей (урок: пиксель принадлежит клику, не потоку).
- **Атомарные захваты ресурсов.** Конкурентный claim — атомарный `UPDATE ... WHERE status='available'`, а не read-then-write.
- **«Мёртвое, но живое».** Ресурс, на который завязаны существующие пользователи (домен, URL, ключ), при выводе из оборота продолжает обслуживаться — он лишь исключается из выдачи новым.
- **Кэши — с явной инвалидацией.** Eventual-consistency кэш допустим, если каждая мутация источника дёргает инвалидацию, а TTL страхует пропущенные.
- **Совместимость по умолчанию.** Старые алиасы параметров, legacy-маршруты и fallback'и живут, пока живы их потребители.
- **Мягкое предупреждение vs жёсткая блокировка** опасных операций — это продуктовое решение принципала, не техническое. Предлагать оба, реализовывать выбранное так, чтобы усиление не ломало контракт.

## 4. Работа с агентами: роли

### 4.1. Основной состав

| Роль | Владеет | Делает | НЕ делает |
|---|---|---|---|
| **Оркестратор** | Процессом целиком | Декомпозиция, брифы, запуск агентов, сборка итогов, commit/push/PR, итог в трекере, деплой по подтверждению, доки, память | Не мержит PR, не переводит в Done, не принимает продуктовые решения |
| **Lead** | Координацией блока задач | Декомпозиция фичи на тикеты, зависимости, порядок запуска, аудит пробелов («что ещё надо поправить») | Не пишет продуктовый код |
| **Backend** | Серверным кодом | API, модели/миграции, бизнес-логика, валидация, audit, backend-тесты | Не трогает frontend; не деплоит |
| **Frontend** | Клиентским кодом | UI/страницы, состояния, клиентские тесты, вёрстка по существующей системе | Не меняет API-контракт (несоответствие — эскалация, не самодеятельность) |
| **Designer** | Визуальным направлением и дизайн-системой | Конкурентный анализ по реальным источникам, UI-концепции, дизайн-система (токены, компоненты, состояния), спецификации для frontend (состояния, отступы, адаптив). Носитель дизайна выбирается под стек (§ 4.5) | Не пишет продуктовый код; не меняет вёрстку сам — передаёт frontend спецификации, а не «картинки» |
| **Infra** | Прод-инфраструктурой | Провижининг, reverse-proxy, DNS/TLS, процесс-менеджер, деплой-скрипты, бэкапы, мониторинг | Не меняет прикладной код |
| **QA** | Верификацией | Планы проверок, smoke, E2E-сценарии, release readiness | Не чинит найденное сам — репортит |
| **Reviewer** | Качеством диффа | Ревью полного диффа по чек-листу, реальный прогон тестов, вердикт с severity | Ничего не правит и не расширяет скоуп |

### 4.2. Расширенные роли (при необходимости — маппинг)
Если проект требует ролей из «большого» списка, они отображаются так:
- **System Architect / Tech Lead** → принципал (решения) + оркестратор (проработка) + lead (декомпозиция).
- **Database Engineer** → backend (схема, миграции, запросы).
- **DevOps** → infra.
- **Security** → reviewer (обязательные security-пункты чек-листа) + infra (hardening) + отдельный security-агент для аудитов.
- **Mobile Developer** → отдельная роль по образцу frontend, свой worktree.
- **Documentation Engineer** → оркестратор (living-доки — его обязанность после каждого деплоя).
- **Product Analyst** → принципал; ассистент готовит данные и варианты.

### 4.3. Право решения
- **Продукт, скоуп, приоритеты, merge, Done, деньги, аккаунты, секреты** — только принципал.
- **Архитектурные развилки** — принципал по рекомендации оркестратора (§ 3.1).
- **Тактические инженерные решения внутри согласованного дизайна** — агент-владелец; нетривиальные фиксирует в итоге.
- **Спорное/неоднозначное** — всегда эскалация вверх, никогда «сам решил и поехал».

### 4.4. Механика: файл агента vs skill

Роли реализуются **двумя разными артефактами** в репозитории. Их путают, поэтому различие — явно:

| | **Файл агента** | **Skill** |
|---|---|---|
| Отвечает на вопрос | **Кто** работает | **Что знает** работающий |
| Что это технически | Системный промпт субагента: идентичность, зона, обязанности, запреты | Пакет доменных знаний, подгружаемый к задаче по триггеру |
| Где лежит | `.claude/agents/<role>.md` (зеркало для другой ассистент-системы: `.codex/agents/<role>.toml`) | `.claude/skills/<name>/SKILL.md` (зеркало: `.agents/skills/<name>/SKILL.md`) |
| Кто им пользуется | Оркестратор спавнит агента этого типа под задачу | **Любой** исполнитель, чья задача совпала с триггером: оркестратор, профильный агент, даже reviewer |
| Когда нужен | На каждую роль из § 4.1 | Только когда у роли есть **переиспользуемое доменное знание** |

Связь между ними: файл агента в своём Load First **ссылается на профильный skill** — так роль получает и обязанности (свой файл), и домен (skill). Дублирование доменных правил в обоих — осознанное: skill доступен всем, файл агента добавляет ролевые запреты и workflow.

**Не каждой роли нужен skill.** Роль, определяемая процессом, а не доменом (reviewer), обходится файлом агента: её «знание» — чек-лист § 9 и project-доки. Заводить skill ради галочки — запрещено (§ 1.2).

При мульти-ассистентной работе (две системы параллельно) роли и skills зеркалятся в оба неймсписа; содержимое идентично, различается только формат носителя.

### 4.5. Файл агента: формат и что писать

```markdown
---
name: <role>                  # id для запуска агента этого типа
description: <зона одной строкой — по ней оркестратор выбирает тип>
model: <опционально: модель для роли>

# <Role> Agent
```

### 4.6. SKILL.md: формат и что писать

```markdown
---
name: <skill-name>
description: Use when <перечисление тем, файлов, типов задач, при которых
  skill должен подхватиться — это ТРИГГЕР, а не аннотация>.
---

# <Skill Name>

## Load First     # какие project-доки прочитать до работы (+ «для флоу X перечитай риски в Y»)
## Own            # какие пути/артефакты покрывает этот домен
## Domain Rules   # инварианты домена — самая ценная часть
## Workflow       # доменные шаги: паттерны модулей, миграции, порядок тестов
## Ask First      # доменные эскалации
```

Правила:
- **`description` — это триггер срабатывания.** Пишется как условие «Use when …» с конкретными темами/технологиями/типами задач. Расплывчатый description = skill не подхватится, когда нужен.
- **Тело — конденсат, не учебник.** 1–2 экрана. Всё, что длиннее — ссылка на профильный док. Skill повторяет из доков только то, что исполнитель должен держать в голове постоянно (инварианты), остальное — «прочитай X».
- **Обновление вместе с доменом.** Изменился инвариант → в одном PR правятся ARCHITECTURE.md и затронутый skill (+ зеркало другой ассистент-системы).
- **Новая роль** = файл агента всегда; skill — только если у роли появился собственный домен.

### 4.7. Выбор состава ролей под проект

Когда этот мануал подключается к проекту (новому или существующему), состав ролей **не берётся целиком** — его подбирает оркестратор под конкретный продукт и задачи принципала:

1. **Инвентаризация.** Прочитать проект: стек, структура, состояние кода, наличие дизайн-системы, инфраструктуры, тестов. Спросить принципала о задачах и приоритетах, если они не даны явно.
2. **Предложение состава.** Из § 4.1–4.2 выбрать минимальный набор ролей, закрывающий задачи, с обоснованием по каждой («зачем эта роль здесь»). Роли «про запас» не создаются (§ 1.2). Обязательный минимум всегда: оркестратор + reviewer. Designer включается при наличии дизайн-задач; носитель дизайна (живой прототип в коде или внешний инструмент) выбирается под стек, а выбранный инструмент проверяется пробным вызовом на права и лимиты **до** планирования работ (§ 4.5).
3. **Утверждение принципалом** — состав ролей это решение уровня скоупа (§ 4.3).
4. **Создание артефактов.** Файлы агентов по § 4.5 только для утверждённых ролей; skills — только где есть собственный домен (§ 4.4).
5. **Пересмотр.** При изменении скоупа состав пересматривается тем же циклом; неиспользуемые роли удаляются.

## 5. Правила взаимодействия агентов

### 5.1. Брифы (оркестратор → агент)
Каждый агент получает самодостаточный бриф:
1. **Задача и тикет** (`TICKET-N`), рабочая директория (точный путь worktree, «НЕ основная папка»).
2. **Read first** — какие доки/файлы прочитать до старта (project-доки + конкретные модули-образцы).
3. **Контекст** — что уже сделано, зафиксированный контракт, принятые решения.
4. **Скоуп** — что сделать и что явно НЕ делать («не трогай `apps/api`», «не реализуй X — это другой агент»).
5. **Паттерны** — «повтори паттерн существующего модуля Y», а не «придумай».
6. **Проверки** — какие команды прогнать и что должно быть зелёным; правила про порты/чужие процессы/тестовую БД.
7. **Запреты** — не коммитить/не пушить (коммитит оркестратор после ревью), не двигать статусы за пределами разрешённого.
8. **Формат ответа** — «машинный вывод»: точный контракт, список файлов, результаты прогонов числами, принятые решения по edge-кейсам.

### 5.2. Передача работы
- **Backend → Frontend:** передаётся зафиксированный контракт (метод, путь, тело, форма ответа, коды ошибок с условиями) — дословно в бриф. Frontend не выводит контракт из кода заново.
- **Код → Reviewer:** полный дифф против базовой ветки + список файлов + фокус-лист «на что смотреть в первую очередь» + перечень кейсов, которые должны быть покрыты тестами.
- **Reviewer → фикс:** находки возвращаются **тому же агенту-автору** узким продолжением: «добавь ровно X, ничего другого не меняй». После нетривиальных фиксов — повторное ревью; после тривиальных (тест добавлен, прогон зелёный) — достаточно результатов прогона.

### 5.3. Правила совместной работы
- **Один тикет = один worktree.** Несколько агентов в одном тикете работают в нём **последовательно** (backend закончил → frontend в том же worktree). Параллельно — только разные тикеты/worktree.
- **Ревьюер независим** — не тот агент, что писал код.
- **Никто из агентов не мержит PR и не переводит задачи в Done.** Это принципал. Оркестратор двигает In Progress / In Review.
- **Агенты не ходят в прод на запись.** Read-only диагностика — можно (логи, health). Любая мутация прода — только оркестратор после явного подтверждения принципала (§ 12).
- **Ресурсные коллизии.** Перед запуском dev-серверов/инфры проверить занятые порты; не убивать чужие процессы; занято — использовать свободный порт или зафиксировать blocker. После проверки погасить то, что сам поднял, и отметить в итоге, что реально запускалось.
- **Сбои агентов.** Транзиентная ошибка (упал вызов, не распарсился ответ) → перезапуск с тем же брифом. Систематическая → разбираться, не долбить повторами.
- **Комментарии в трекере от агентов** (старт/итог) — на языке проекта, по шаблонам § 8.

### 5.4. Когда работу продолжать нельзя
- Обнаружено несоответствие контракту/дизайну → стоп, эскалация.
- Задача требует ask-first решения (§ 3.2) → стоп, вопрос.
- Требуется секрет/доступ, которого нет → стоп, запрос принципалу (секреты вводит он сам, § 11).
- Правка вылезает за скоуп тикета → стоп, предложить отдельный тикет.

## 6. Стандарты разработки

### 6.1. Код
- **Строгая типизация везде.** TypeScript strict (или аналог в другом стеке); `any` запрещён.
- **Валидация на границе API — один раз.** Схемной библиотекой (у нас Zod). Внутри системы повторно не валидировать.
- **Аудит мутаций.** Каждая admin-видимая мутация пишет audit-запись (`entityType, entityId, action, beforeData, afterData`). `before` снимается ДО мутации, в той же транзакции.
- **Плоская модульность без преждевременных фреймворков.** Роутеры/модули — простые единицы, монтируемые в одном месте. Не вводить прослойки-абстракции, пока нет ≥3 реальных потребителей.
- **Состояние — локальное, пока не доказана необходимость глобального.** Глобальный store не появляется «на всякий случай».
- **Строки UI — inline до появления реальной мультиязычности.** i18n-библиотека — ask-first.
- **Комментарии — «почему», не «что».** Комментарии-отчёты о проделанной работе в коде запрещены. Неочевидное решение — короткое «почему» рядом.
- **Ошибки** обрабатываются там, где возможны. Кодов ошибок — стабильный словарь (`SNAKE_CASE`), маппинг на HTTP-статусы централизован. 4xx осмысленные: 400 — невалидный вход/неприменимая операция, 403 — права, 404 — нет сущности, 409 — конфликт состояния.
- **Бинарники и медиа — вне репозитория** (отдельный media-корень, раздача статикой).

### 6.2. Принципы — как мы их читаем
- **KISS + YAGNI** — главные, усилены § 1.2.
- **DRY** — про знание, не про строки: не плодить источники истины; но не абстрагировать два случайно похожих куска.
- **SOLID** — прагматично: границы модулей и зависимостей чистые, но без церемоний ради церемоний.
- **Clean Architecture** — как направление зависимостей (домен не знает про транспорт), не как обязательные слои.
- **Отказоустойчивость** — деградировать мягко: необязательный сервис упал → фича деградирует, страница не падает (`.catch` с fallback-состоянием); фоновые операции — вне request path.

### 6.3. Тесты
- Живут рядом с кодом (`*.test.ts(x)` в той же директории).
- Backend — интеграционные против собранного приложения (Supertest против `buildApp()`), с отдельной тестовой БД.
- Frontend — jsdom/компонентные; мок API-обёртки с роутингом по пути (не порядко-зависимые моки).
- **Тестовая БД защищена guard'ами:** имя обязано содержать `_test`-маркер; guard кидает исключение до первого запроса, если URL смотрит не туда; тесты запускаются только через npm-скрипты проекта (не сырым раннером из корня).
- Новый код-путь = тест. Нет теста — явное «почему нет» в итоге.
- **Флэйки-протокол:** известный флэйки-тест не гоняется до победного в чужом тикете — перезапуск, пометка в итоге, починка в профильном тикете.

### 6.4. Definition of Done (универсальный)
- [ ] Код написан, типы строгие, нет `any`.
- [ ] Валидация на API-границах (для новых/изменённых endpoint'ов).
- [ ] Audit-лог на каждой admin-мутации.
- [ ] Тесты проекта зелёные (backend + frontend).
- [ ] Для нового кода есть тесты или явно сказано, почему нет.
- [ ] При изменении схемы — миграция создана, клиент перегенерирован.
- [ ] UI-изменения проверены в браузере (или явное «в браузере не проверял»).
- [ ] Smoke зелёный для изменений API (или явно почему не гонялся).
- [ ] Никаких комментариев «что сделано» в коде.
- [ ] Неприменимый пункт помечен явно, не пропущен молча.

## 7. Git workflow

### 7.1. Модель
- **Trunk-based:** `main` всегда деплоябелен. Прод обновляется из `main`.
- Ветка на задачу: `<TICKET-N>-<короткий-slug>` (например `TICKET-94-admin-domain-mgmt`).
- Worktree на ветку: `.{assistant}/worktrees/<TICKET-N>` (несколько ассистент-систем — разные неймспейсы: `.claude/…`, `.codex/…`).
- Chat-driven правки без тикета — прямо в `main` отдельными коммитами.

### 7.2. Коммиты
Формат:
```
<type>: <императивное описание ≤72 символов>

<Тело: ЗАЧЕМ и что на уровне решения, буллетами.
Контракты/edge-кейсы, если важны для истории.>

<TICKET-N.>

Co-Authored-By: <ассистент> <noreply@...>
```
- `type`: `feat` / `fix` / `docs` / `test` / `refactor` / `chore`.
- Коммит — цельная единица работы, а не «WIP». Оркестратор коммитит после ревью, одним осмысленным коммитом (или логичной серией).
- Doc-обновления — **всегда отдельным `docs:`-коммитом**, не смешиваются с кодом.
- Запрещено: `--no-verify`, обход подписи, force-push в общие ветки, amend опубликованного, секреты в истории (см. § 11).

### 7.3. Pull Request
Тело PR — по шаблону:
```markdown
## <TICKET-N> — <название>
<1-2 предложения: что даёт изменение.>

### Backend / Frontend / Infra
<Контракты эндпоинтов, ключевые решения, «миграция есть/нет».>

### Дизайн-решение
<Развилки и что выбрано, с кем согласовано.>

### Тесты
<Числа прогонов, вердикт ревьюера.>

### Не в этом PR
<Осознанно отложенное — кандидаты в отдельные тикеты.>

Тикет: <ссылка>
```
- PR открывает оркестратор. **Мержит только принципал.**
- После merge: `git pull --ff-only` в основной папке → `worktree remove` (+ добить остатки node_modules) → `branch -d` → уборка подтверждена списком worktree.

### 7.4. Версионирование и релизы
- По умолчанию — **continuous deploy из main**: версия приложения — из env/манифеста (`APP_VERSION`), «релиз» = задеплоенный коммит, зафиксированный в server-state доке.
- Если продукт требует версионных релизов: semver, git-теги `vX.Y.Z`, релиз собирается из main, changelog по коммитам с момента прошлого тега.
- CHANGELOG.md заводится, когда появляются внешние потребители изменений; до того историю несут PR + итоги в трекере.

## 8. Работа с трекером (Linear)

### 8.1. Язык
Язык проекта в трекере фиксируется на старте (у нас — русский): названия, описания, планы, AC, тест-планы, комментарии, итоги. На английском остаются: статусы, labels, имена сущностей/файлов из кода, команды, env vars, названия внешних сервисов.

### 8.2. Структура работы
- **Блок (epic)** — фича из нескольких тикетов. Заводится, когда работа не помещается в один PR или имеет внутренние зависимости. У блока есть порядок запуска и явные зависимости между тикетами.
- **Тикет** — единица владения: один тикет = один владелец = одна ветка = один worktree = один PR.
- **Фикс-тикеты** — находки аудита/ревью после мержа фичи оформляются отдельными тикетами и батчатся в один деплой.
- **Полировка** (не блокирующая UX/качество) — в бэклог отдельными тикетами, не раздувает скоуп текущего.

### 8.3. Анатомия тикета
```markdown
## Контекст
<Откуда задача, что уже есть, ссылки на связанные тикеты.>

## Что сделать
<Список конкретных работ. Для fullstack — разбить на backend / frontend.>

## ⚠️ Семантика / развилки
<Опасные последствия, продуктовые развилки, что продумать в дизайне.>

## Acceptance criteria
<Проверяемые пункты, включая «тесты зелёные», права доступа, audit.>

## Зависимости
<TICKET-X (что именно оттуда нужно). «Не блокирует <веху>» — если так.>
```

### 8.4. Статусы и переходы

| Статус | Кто ставит | Условие |
|---|---|---|
| Backlog / Todo | принципал / lead | Задача описана |
| In Progress | оркестратор | Работа началась (worktree создан) |
| In Review | оркестратор | Реализация + верификация + PR готовы. Не раньше |
| Done | **только принципал** | Смержено в main (и задеплоено, если деплой был частью задачи) |
| Canceled / Superseded | принципал | С комментарием-причиной и ссылкой на замену |

### 8.5. Комментарии-итоги
Авторитетная запись о завершении — комментарий оркестратора в тикете:
```markdown
## Итог (оркестратор) — готово к ревью/мержу
Реализовано X, отревьюено (вердикт). PR: <ссылка>.

### Что сделано
<Контракты, ключевые решения, «миграции нет/есть».>

### Дизайн-развилка
<Что выбрали и с кем согласовали.>

### Тесты / проверки
<Числа, вердикт ревьюера, что подтверждено.>

### Не проверялось / follow-up
<Явный список непроверенного и отложенного.>

Мерж — за тобой; после мержа задеплою по подтверждению.
```
Задача считается завершённой, когда: смержена, задеплоена (если требовалось), итог написан, доки обновлены, принципал перевёл в Done.

## 9. Code Review

### 9.1. Процесс
1. Ревью проводит **независимый reviewer-агент** после того, как весь код задачи готов (backend + frontend вместе).
2. Вход: полный дифф против базовой ветки, список файлов, фокус-лист «проверь в первую очередь пункты 1–N», перечень кейсов для оценки покрытия.
3. Ревьюер **реально запускает** проверки: таргетированные тест-сьюты изменённых модулей, typecheck обоих пакетов, скан диффа на `any`/`console`/`debugger`, проверку что в диффе только заявленные файлы. Что запускал — перечисляет; что подтверждено только чтением — помечает отдельно.
4. Выход — машинный вердикт (§ 9.4). Оркестратор триажит: блокеры/пробелы → узкие фиксы тому же автору → перепрогон → PR.

### 9.2. Чек-лист ревьюера (минимум)
**Безопасность — первой:**
- Авторизация навешана на **каждый** новый маршрут (правильный guard, правильная роль). Нет пути вызвать мутацию мимо прав.
- Скоупинг данных по владельцу в каждом запросе (нет утечки чужих сущностей).
- Вход валидирован на границе; никакие пользовательские данные не попадают в логи/ответы сырыми секретами.

**Корректность:**
- Семантика state-machine переходов (кто из какого статуса куда может).
- Гонки и атомарность: конкурентные захваты, transaction-границы, before/after снапшоты.
- Edge-предикаты (классика: self-exclusion в проверках уникальности — «кроме текущей записи»).
- Инвалидация кэшей на каждой мутации источника; порядок «после коммита транзакции».
- Коды ошибок и их маппинг на статусы; сообщения осмысленные.

**Тесты — полнота, не только зелёность:**
- Перечислить, какие кейсы покрыты, и **явно назвать непокрытые** (не-happy-path ветки, права для каждой роли, каждый новый код ошибки).

**Frontend:**
- Состояния: loading/disabled во время запроса, серверные ошибки показываются, предупреждения видны ДО подтверждающего действия, «Отмена» не имеет side effects.

**Гигиена:**
- В диффе только относящиеся к задаче файлы. Стиль соответствует окружению. Pre-existing проблемы упоминаются как nit «не этого тикета» — НЕ чинятся.

### 9.3. Severity

| Уровень | Что это | Действие |
|---|---|---|
| **blocker** | Дыра в правах/безопасности, потеря/порча данных, сломан основной флоу, гонка с реальными последствиями | PR не идёт дальше до фикса |
| **major** | Логическая ошибка с обходным путём; нарушение процесса (нет PR/статуса); отсутствие теста на критичный путь | Чинится до мержа |
| **minor** | Слабое место UX, спорный компромисс, требующий подтверждения принципала | Фикс или явное «принято осознанно» |
| **nit** | Косметика, pre-existing, вкусовщина | На усмотрение; чаще — отдельный тикет/игнор |

### 9.4. Вердикт
- **approve** — блокеров и незакрытых major нет; можно с оговорками (перечисленными).
- **needs-changes** — есть блокеры/major; список с `file:line`, «в чём проблема и как чинить».
- Обязательный раздел **«Остаточные риски / что НЕ проверялось»** — даже при approve.
- PR отклоняется (не мержится) при: незакрытом blocker; отсутствии тестов на новый критичный путь без объяснения; выходе за скоуп тикета; несоответствии зафиксированному контракту.

### 9.5. Чего ревьюер не делает
Не правит код. Не расширяет скоуп. Не требует рефакторинга не относящегося к задаче кода. Не гоняет заведомо флэйки-тесты до победного — отмечает и идёт дальше.

### 10.1. Набор документов

| Документ | Что содержит | Когда обновляется |
|---|---|---|
| `README.md` | Что это, как запустить за 5 минут | При смене запуска |
| `CLAUDE.md` / `AGENTS.md` | Правила для ассистентов: read-order, стек, конвенции, DoD, ask-first списки | При смене правил |

| `docs/ARCHITECTURE.md` | As-built: repo map, модель данных, auth, ключевые флоу, «что молча ломает флоу X» | При изменении архитектуры |
| `docs/DEVELOPMENT.md` | Локальный запуск, тесты, env, troubleshooting, entry points «с чего начать задачу типа Y» | При смене dev-процесса |
| `docs/WORKFLOW.md` | Проектная специфика процесса (трекер, worktree, ревью) | При смене процесса |

| `docs/SERVER_STATE.md` | **Фактическое** состояние прода: deployed commit, сервисы, инциденты и уроки | **Только после реальной проверки на сервере** |
| `docs/handover/` | Инструкции для операторов/пользователей продукта | При смене пользовательских флоу |
| `docs/adr/`, `docs/archive/` | Решения; исторические планы | Append-only |

### 10.2. Правила
- **Living vs archive.** Текущая истина — только в живых доках; `docs/archive/` хранит историю решений и не управляет реализацией. Устаревший план → в архив с датой в имени.
- **Не дублировать — ссылаться.** Каждый факт живёт в одном документе, остальные ссылаются.
- **Штамп актуальности.** Живые доки несут `Updated: YYYY-MM-DD` в шапке.
- **Verified-only для server-state.** В док о состоянии сервера пишется только то, что проверено реальными командами; непроверенное — в разделе «не проверялось».
- **Пост-деплойный ритуал:** после каждого деплоя оркестратор поднимает deployed commit и изменения в PROJECT_CONTEXT + SERVER_STATE (+ профильные доки), коммитит отдельным `docs:`-коммитом в main и пушит — без напоминаний.
- **Инциденты** записываются в SERVER_STATE как «⚠️ инцидент + урок» рядом с деплоем, который их вызвал.
- **Память ассистента** (межсессионная) дополняет, но не подменяет доки: в память идёт то, чего нет в репозитории (предпочтения принципала, договорённости о процессе, состояние внешних систем); всё, что описывает код и репозиторий — в доки.

## 11. Безопасность

### 11.1. Секреты — железные правила
- Секреты (ключи, токены, пароли, connection strings, приватные IP) **никогда** не попадают в: репозиторий, трекер, PR, логи, вывод команд, скриншоты, историю shell.
- **Ассистент не вводит секреты.** Значения вводит принципал сам (в env-файл на сервере, в поле формы, в password manager). Ассистент готовит место, инструкцию и проверку присутствия.
- Проверка env — только **presence-check**: `present`/`MISSING` для секретов, значения — только для non-secret флагов (паттерн `env:check` / `printEnvStatus`).
- Ключ шифрования данных at-rest после backfill **не меняется и не теряется** — иначе данные нечитаемы. Это проговаривается при каждом касании.
- Токены — least privilege и **раздельные по потребителям** (токен приложения ≠ токен reverse-proxy, разные скоупы, разные места хранения).
- Утёкший секрет → немедленная ротация; сам факт и время — в SERVER_STATE (без значения).

### 11.2. Приложение
- **Env-guards в проде:** приложение отказывается стартовать со значениями по умолчанию для секретов, с wildcard CORS, без обязательных ключей при включённых интеграциях.
- **Auth:** короткоживущий access-токен + ротация refresh; деактивация пользователя убивает refresh сразу (access дотлевает TTL).
- **RBAC:** роли с минимальными правами; скоупинг «своё» на уровне запросов; admin-only маршруты — только через общий guard.
- **Rate limiting** на auth и публичных endpoint'ах.
- **Валидация** всех входов на границе (включая query/headers), санитизация неподставленных плейсхолдеров/макросов — симметрично для всех параметров (урок: очищали одни макросы и не очищали другие).
- **Audit-лог** каждой чувствительной мутации.
- **CORS** — явный allowlist; динамические origin'ы — через кэш активных хостов с инвалидацией; same-origin fast-path только по неподделываемому заголовку (перезаписываемому reverse-proxy).
- **Выпуск TLS-сертификатов** для динамических хостов — только через ask-endpoint, авторизующий хост (защита от эмиссии сертификатов на чужие домены).
- Логи не содержат значений секретов и PII сверх необходимого; при передаче наружу — редактирование.

### 11.3. Процессные
- Прод по умолчанию **read-only** для ассистента и агентов; любые мутации — § 12.2.
- `npm audit fix --force` вслепую — запрещено; аудит зависимостей — отдельной задачей с разбором.
- Отказ от неправомерных схем (чужие платёжные средства, обход проверок) — с предложением легитимной альтернативы.

## 12. DevOps

### 12.1. Окружения

| Окружение | БД | Правило |
|---|---|---|
| **local/dev** | Локальная (docker) | Свободно; внешние интеграции — mock-провайдеры по умолчанию |
| **test** | Отдельная, имя с `_test` | Guard: тесты падают до первого запроса, если БД не тестовая |
| **prod** | Продовая | Read-only по умолчанию; мутации — по явному подтверждению |

- Провайдеры внешних API (DNS, переводы, аналитика) — за seam'ом с mock-реализацией: dev/test не требуют токенов и не дёргают реальные сервисы.

### 12.2. Мутации прода — только с подтверждением
Каждое из действий требует **отдельного** явного «да» принципала (одобрение одного не распространяется на следующее): деплой; рестарт процессов; миграции; правка env/секретов; правка конфига reverse-proxy; любые деструктивные операции. Read-only диагностика (логи, health, SELECT-запросы) — свободно.

### 12.3. Деплой
Скриптованный, идемпотентный, один вход (`deploy.sh`):
```
backup → git pull --ff-only → install (с dev-deps для сборки) →
codegen (ORM) → build (web → публикация статики → api) →
migrate deploy → prune dev-deps → restart процессов с обновлением env → save
```
Правила:
- **Env применяется детерминированно двумя каналами:** приложение само грузит env-файл на старте (no-override) + деплой рестартует процессы с обновлением окружения (`restart --update-env`, не `reload`). Это закрывает оба класса инцидентов: «новая переменная не доехала» и «изменённое значение не обновилось».
- Скрипт деплоя, обновляющий сам себя через pull, применяет собственные правки со **второго** прогона — помнить при изменении deploy.sh.
- На разделяемом сервере деплой **не перетирает** общие конфиги (Caddyfile/nginx с чужими vhost, чужие процессы в менеджере) — только ручной merge с backup'ом и `validate` перед reload.
- Каденция: fast-forward only; локальный `main` = origin/main = прод после деплоя.

### 12.4. Пост-деплой верификация (обязательная)
- `/health` → ok, окружение production, uptime растёт.
- `/ready` → ok, зависимости (БД) ok.
- Процесс-менеджер: все процессы online, **счётчик рестартов не растёт** (нет рестарт-цикла).
- Для затронутых фич — таргетная проверка (endpoint отвечает, страница отдаётся).
- Итог верификации — принципалу и в SERVER_STATE.

### 12.5. Миграции
- Создаются в dev (`migrate dev`), применяются в проде только `migrate deploy` внутри деплоя.
- Прод-миграция = часть подтверждённого деплоя; отдельные ручные прогоны — отдельное подтверждение + предварительный просмотр SQL для деструктивных.
- Обратно-несовместимые изменения — в два шага (expand → migrate data → contract).

### 12.6. Rollback и backup
- Перед каждым деплоем — автоматический backup (дамп БД + манифест).
- Предпочтительный откат — **forward-fix** (revert-коммит → обычный деплой); откат БД — восстановление из дампа только при порче данных.
- Restore **тестируется**: периодическая проверка восстановления в одноразовую БД с контрольными подсчётами; непроверенный бэкап считается несуществующим.
- Офсайт-копия бэкапов — обязательный пункт пре-прод чек-листа.

### 12.7. Наблюдаемость
- Структурные JSON-логи с requestId, method, path, statusCode, duration, origin, ip; ротация логов включена.
- `/health`, `/ready`, `/metrics` — публичные для мониторинга; внешний uptime-мониторинг на них.
- При разборе инцидентов: сначала проверить **формат** логов (префиксы перед JSON и т.п.), потом парсить.

## 13. Правила общения с принципалом

Как ассистент обязан себя вести:

1. **Думать как tech lead, а не исполнитель.** Оценивать идеи инженерно; несогласие с обоснованием — обязанность.
2. **Не писать код без понимания задачи.** Неоднозначно → уточнить до старта, предъявив варианты трактовки.
3. **Предлагать лучшее.** Видишь архитектуру/путь лучше — предложи, даже если не спрашивали. Проще/быстрее/надёжнее — покажи альтернативу.
4. **Предупреждать заранее.** Потенциальная проблема, технический долг, опасное последствие («установленная база сломается») — сказать ДО того, как решение принято.
5. **Объяснять компромиссы.** Каждая рекомендация — с ценой. Формат: варианты → трейдоффы → «рекомендую X, потому что».
6. **Не пересказывать всё меню.** Когда информации достаточно — действовать; выбор — рекомендация, а не обзор всех опций.
7. **Признавать ошибки явно.** Ошибся в диагнозе/оценке — сказать прямо, исправить след в тикете/доке, где ошибка была зафиксирована.
8. **Отчитываться честно.** Упало — показать вывод. Пропустил — сказать. Готово и проверено — сказать без хеджирования. Непроверенное — всегда помечено.
9. **Данные раньше теорий.** При отладке — сначала ground truth (логи, БД, реальные статусы), потом гипотезы. Если факт противоречит красивой теории — теория умирает, не факт.
10. **Уважать принятые решения.** Зафиксированное не пере-обсуждается без новых фактов (§ 1.7).
11. **Матрица подтверждений.** Никогда: merge, Done, ввод секретов, финансовые операции — это принципал. По явному per-action «да»: деплой, рестарт, миграции, env, конфиги прода, деструктивное. Свободно: локальная разработка, тесты, read-only диагностика, доки (пост-деплойные doc-коммиты в main — по установленному порядку, без переспрашивания).
12. **Язык — принципала** (у нас русский), технические термины — как принято в индустрии.
13. **Отказывать в неправомерном** прямо, с объяснением и легитимной альтернативой.
14. **Заканчивать статусом.** Каждый значимый этап завершается: что сделано → что проверено → что дальше → что нужно от принципала.

## 14. Best practices (выработанные)

### Процесс
- **Machine-readable выводы агентов.** Финальное сообщение агента — данные (контракт, файлы, числа прогонов, решения), а не эссе. Оркестратор собирает из них итог.
- **Контракт-first handoff** между backend и frontend (§ 5.2) — убирает целый класс интеграционных багов.
- **Узкие продолжения** вместо новых агентов для точечных фиксов: «добавь ровно X, ничего другого не меняй» тому же агенту с контекстом.
- **Аудит пробелов lead-агентом** после серии фич («что ещё надо поправить с учётом последних правок») → батч фикс-тикетов до тестирования.
- **Один авторитетный итог** в тикете вместо размазанных комментариев.

### Инженерия
- **Атомарный claim** конкурентных ресурсов через условный UPDATE (§ 3.6).
- **Снапшот атрибуции в момент события** у сущности-владельца (§ 3.6).
- **Dead-but-resolving:** выводимый из оборота ресурс продолжает обслуживать существующих пользователей (§ 3.6).
- **Идемпотентный upsert** во внешних системах: искать по естественному ключу → патчить при расхождении → создавать при отсутствии; не маскировать конфликт «уже существует» как успех.
- **Дедупликация событий** по бизнес-ключу с окном по времени для бес-ключевых случаев.
- **Инвалидация + TTL** для всех кэшей поверх мутируемых данных.
- **Фича-гейты через env с mock-дефолтом:** прод включает реальный провайдер, dev/test не требуют секретов, guard не даёт включить реальный провайдер без ключа.

### Отладка
- **Ground truth первым:** статусы ответов в логах и строки в БД раньше любых теорий. Полный тайм-лайн запросов вокруг инцидента читается целиком, не выборочно.
- **Исключать переменные:** повторить в чистом окружении (инкогнито/новое устройство), прежде чем валить на кэш.
- **Тихие деградации** (`202 skipped`, `catch {}` best-effort) — первый подозреваемый, когда «запрос был, а записи нет».
- **Проверять формат перед парсингом** (структура логов, схема таблиц — `\d`/пробный SELECT перед большим запросом).

### Операционка
- **Сложные удалённые команды** кодировать (base64 → decode | bash) вместо борьбы с многоуровневым квотингом; для SQL — файл + `psql -f`.
- **Таймауты на всё удалённое** (`ConnectTimeout`).
- **Чужие сервисы на общем сервере** — неприкосновенны; их список — в server-state доке.
- **Worktree-гигиена:** после мержа — remove + prune + удаление локальной ветки; директория добивается вручную, если мешают артефакты установки.
- **Временные файлы** — только в scratchpad-директорию сессии, не в репозиторий.

## 15. Чек-листы

### 15.1. Старт проекта
- [ ] DEVELOPER_MANUAL.md скопирован; CLAUDE.md/AGENTS.md написаны под проект.
- [ ] Репозиторий: main защищён соглашением «мержит принципал», ветки `<TICKET>-slug`.
- [ ] Трекер: проект создан, язык зафиксирован, статусы соответствуют § 8.4.
- [ ] Скелет доков (§ 10.1) с «Updated:»-штампами.
- [ ] `.env.example` с рабочими dev-дефолтами; env-guards для прода.
- [ ] Тестовая инфраструктура: тестовая БД с `_test`-guard, npm-скрипты запуска.
- [ ] Файлы агентов заведены на на нужные роли в данный проект § 4.1 (формат § 4.5); доменные skills — где есть домен (§ 4.6); при мульти-ассистентности — зеркала в оба неймспейса.
- [ ] Секреты: определено, где живут (password manager + сервер), кто вводит (принципал).

### 15.2. Перед новой фичей
- [ ] Развилки дизайна проговорены, решения зафиксированы (тикет/ADR).
- [ ] Декомпозиция: тикеты, владельцы, зависимости, порядок.
- [ ] Понятно, что фундаментного нужно построить сначала.
- [ ] Критерии приёмки проверяемы.

### 15.3. Перед Pull Request
- [ ] DoD (§ 6.4) пройден по пунктам.
- [ ] Ревью независимым reviewer-агентом: approve, блокеров нет.
- [ ] Пробелы покрытия из ревью закрыты (или явно приняты).
- [ ] Дифф содержит только файлы задачи.
- [ ] Тело PR по шаблону, тикет слинкован, статус In Review.

### 15.4. Перед merge (принципал)
- [ ] Итог в тикете прочитан; «не проверялось» осознано.
- [ ] Дизайн-развилки совпадают с договорённостями.
- [ ] CI зелёный.

### 15.5. Перед deploy
- [ ] PR смержен; локальный main == origin/main.
- [ ] Явное подтверждение принципала на этот деплой.
- [ ] Известно: есть ли миграции, меняется ли env, трогается ли конфиг proxy.
- [ ] Если env/конфиг — значения на месте (presence-check), план ручного merge конфига.
- [ ] Бэкап будет снят (входит в скрипт) / снят.

### 15.6. После deploy
- [ ] health/ready ok; процессы online; счётчики рестартов не растут.
- [ ] Таргетная проверка задеплоенной фичи.
- [ ] SERVER_STATE + PROJECT_CONTEXT: deployed commit поднят; уроки/инциденты записаны.
- [ ] `docs:`-коммит запушен в main.
- [ ] Worktree и ветка убраны; память ассистента обновлена.
- [ ] Принципалу — итог: что в проде, что проверено, что осталось.

### 15.7. Перед первым production-запуском (hardening)
- [ ] Секреты не в репо; env-guards работают; presence-check чистый.
- [ ] Auth: TTL, ротация refresh, rate limits.
- [ ] CORS/TLS-выпуск ограничены allowlist'ами/ask-гейтом.
- [ ] Audit-лог пишется; логи без секретов; ротация логов.
- [ ] Бэкапы + проверенный restore + офсайт-копия.
- [ ] Внешний мониторинг health/ready.
- [ ] Runbook деплоя и rollback актуальны; аудит зависимостей проведён.

### 15.8. После завершения задачи
- [ ] Итог в тикете; Done поставлен принципалом.
- [ ] Follow-up'ы оформлены тикетами, не потеряны в чате.
- [ ] Уроки (если были) — в соответствующий док.

### 15.9. После релиза
- [ ] E2E ключевых флоу руками принципала пройден.
- [ ] Обратная связь превращена в тикеты.
- [ ] Living-доки отражают новое состояние продукта.
- [ ] Ретроспектива инцидентов деплоя → правки runbook'а.
