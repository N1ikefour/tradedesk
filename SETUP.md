# SETUP — установка и запуск TradeDesk

Инструкция доводит до рабочего приложения в браузере и до первого входа. Читать другие
файлы проекта для этого не нужно.

> **Это черновик для разработчика.** Он прогнан целиком на macOS (Docker 29.6.1,
> Compose v5.3.0). Windows-путь описан, но на Windows **не проверялся** — такие места
> помечены плашкой «⚠️ На Windows не проверено». Дальше по этому тексту две разные
> задачи: `T-06` — прогон инструкции на чистой Windows-машине, `T-01` — финальная
> версия для не-разработчика со скриншотами, которую пишут уже по итогам прогона.

Шагов семь. Сколько уйдёт времени — зависит почти целиком от того, как быстро
скачаются образы Docker на первом запуске; на чистой машине мы этого не мерили.
Восьмой раздел — обновление и резервные копии; он понадобится не сегодня, но читать
его нужно до первого обновления, а не после.

---

## Что вы получите

Приложение в браузере на `http://localhost:5173` и вход в него по коду. Всё крутится
у вас на машине: наружу ничего не смотрит, регистрироваться нигде не нужно.

Чего вы **не** получите на этом шаге: сделок из MetaTrader 5. Программа-сборщик, которая
их забирает, ставится отдельно и только на Windows — это не входит в эту инструкцию.

## 1. Что нужно на машине

Ставить Python, Node и базу данных **не нужно** — они запускаются внутри Docker.

| Что | Зачем | Как проверить |
|---|---|---|
| **Docker Desktop** | в нём работает всё приложение | `docker --version` и `docker compose version` |
| **Git for Windows** — только на Windows | не для скачивания: он приносит `bash` и `openssl`, без которых не отработают шаги 3 и 4 | `bash --version` в Git Bash |

Проект скачивается **архивом**, поэтому Git как таковой не нужен: на macOS и Linux не
нужен вовсе, на Windows нужен ровно как источник `bash` и `openssl` для скриптов запуска.
Поставить его придётся, но открывать Git Bash — нет: все шаги установки на Windows
запускаются двойным щелчком по файлам `.bat`, которые сами зовут этот `bash`.

Проверено на Docker 29.6.1 с Docker Compose v5.3.0. Нужен Docker Compose **версии 2 или
новее** (команда пишется `docker compose`, через пробел, а не `docker-compose`). Более
старые версии мы не проверяли.

**Место на диске.** Замерено после установки: образы — около 1 ГБ, данные и зависимости —
около 320 МБ. С кэшем сборки закладывайте **3 ГБ свободного места**.

**Память.** Пять контейнеров в покое занимают около 310 МБ, из них планировщик фоновых
задач — около 60 МБ. На машине с 16 ГБ этого не заметно; Docker Desktop сверх того
резервирует несколько гигабайт под свою виртуальную машину.

Места на диске планировщик не добавляет: он работает на том же образе, что и сервер
приложения, — второй образ состоит из тех же слоёв и занимает не диск, а только имя.

### Чем запускать команды

Команды ниже показаны в двух видах: короткие `make …` и длинные `sh infra/scripts/…`.
Делают они **одно и то же** — `make` просто вызывает те же скрипты.

- **macOS:** `make` приходит с Command Line Tools. Если `make --version` ругается —
  выполните `xcode-select --install`.
- **Linux:** `make` обычно уже стоит; если нет — поставьте пакет `make`.
- **Windows:** `make` в системе нет. Смотрите блок ниже.

### ⚠️ На Windows не проверено

> Всё в этом блоке написано по устройству проекта и по документации Docker, но
> **на Windows-машине не прогонялось** — разработка идёт на macOS. Считайте это
> обоснованным предположением, а не проверенным фактом. Проверка на чистой
> Windows-машине — задача `T-06`.

1. **Docker Desktop for Windows** требует включённого **WSL2**. Установщик Docker
   предлагает его включить сам; после этого нужна перезагрузка.
2. **Git for Windows** (<https://git-scm.com/download/win>). Скачивать проект им не нужно —
   нужен «Git Bash» с `bash`, `sh` и `openssl`: на них написаны скрипты запуска, и без
   них шаг 3 работать не будет.
3. `make` на Windows нет, и он не нужен. Все команды из этой инструкции есть файлами
   в папке `infra\scripts`, которые запускаются **двойным щелчком**:

   | Шаг | Файл |
   |---|---|
   | 3. Создать файл настроек | `init.bat` |
   | 4. Запустить | `start.bat` |
   | 7. Остановить | `stop.bat` |
   | 8. Обновить, копия, восстановление | `update.bat`, `backup.bat`, `restore.bat` |

   Своей логики внутри у них нет: каждый вызывает свой `.sh` через bash из Git for
   Windows, поэтому поведение на Windows и на macOS одно и то же. Всё, кроме
   `start.bat` и `stop.bat`, в конце ждёт нажатия клавиши — иначе окно закрылось бы
   вместе с тем, ради чего их и запускали: предупреждением про `MASTER_KEY`, путём
   к свежей копии, таблицей «что будет перезаписано».

   Git Bash при этом нужен — из него берётся `bash`, а для шага 3 ещё и `openssl`.
   Но **заходить** в него, чтобы пройти установку, не обязательно. Если всё же захотите
   (или понадобится команда, которой нет отдельным файлом): правая кнопка в папке
   проекта → «Open Git Bash here», дальше вариант `sh infra/scripts/…`.

## 2. Скачать проект

Проект приезжает одним архивом со страницы релизов — клонировать репозиторий не нужно.

### ⚠️ Куда распаковывать — решите до распаковки

**В пути к папке не должно быть русских букв.** Ни в одной части пути — включая имя
папки вашей учётной записи.

- Windows: `C:\tradedesk`
- macOS: `/Users/Shared/tradedesk`
- Linux: `~/tradedesk`

Домашняя папка (`~`, она же `C:\Users\<имя>`) годится не всегда: если ваше имя
пользователя написано по-русски, оно тоже часть пути. На macOS это тот самый случай,
поэтому там предлагается `/Users/Shared` — общая папка, которая есть в системе изначально.

Куда **нельзя**: `C:\Users\Никита\Downloads\tradedesk-0.1.0` — то есть ровно туда, куда
браузер складывает скачанное по умолчанию, если ваше имя пользователя написано
по-русски. Шаг 4 такой путь не примет.

Причина не в нашей программе. TradeDesk собирает несколько образов за один запуск
(сервер, фоновый обработчик, а в варианте с доменом ещё и приложение), и на такую
сборку Docker открывает одну общую сессию: её имя он берёт из пути к папке и передаёт
в служебном заголовке, куда русские буквы не проходят. Сборка обрывается **раньше, чем
начинается**, а ошибка выглядит так и про папку не говорит ни слова:

```
failed to dial gRPC … header key "x-docker-expose-session-sharedkey"
contains value with non-printable ASCII characters
```

Пробелы в пути допустимы — это проверено отдельно. Мешают **не-латинские** символы:
русские буквы, иероглифы, эмодзи.

> **Что именно проверено, а что нет.** На macOS (Docker 29.6.1, Compose v5.3.0) сборка
> падает, когда русские буквы стоят в имени самой папки установки. Один образ из такой
> папки при этом собирается, а несколько — нет; нам это не помогает, их всегда несколько.
> Русские буквы только в папках **выше** по пути там сборку не ломали. Обратного вывода
> из этого мы не делаем: на Windows путь устроен иначе, и до прогона на живой Windows
> граница «имя папки против родительских» — предположение. Поэтому шаг 4 смотрит на путь
> целиком и отказывается работать раньше, чем что-то соберёт. Лишний отказ вы прочитаете
> словами и перенесёте папку; пропущенный случай отдаёт вам ошибку про gRPC.

Шаг 4 проверяет путь сам и, если он непригоден, скажет словами, что делать, и покажет
обход на случай, если перенести папку нельзя. Но переносить папку после установки
хлопотнее, чем сразу распаковать в правильное место.

### Порядок

1. Откройте <https://github.com/N1ikefour/tradedesk/releases>.
2. В самом верхнем релизе, в разделе **Assets**, скачайте `tradedesk-<версия>.zip`.
3. Распакуйте архив в папку по адресу без русских букв: `C:\tradedesk` на Windows,
   `/Users/Shared/tradedesk` на macOS, `~/tradedesk` на Linux.

> Аккаунт GitHub для этого не нужен: репозиторий открытый, страница и архив
> скачиваются как обычный файл.

Внутри архива **один каталог** `tradedesk-<версия>` — в нём и лежит проект. Все
дальнейшие команды выполняются из него:

```bash
cd tradedesk-0.1.0        # подставьте свою версию
```

Windows-распаковщик по умолчанию создаёт папку с именем архива, и получается
`tradedesk-0.1.0\tradedesk-0.1.0` — это нормально, работать нужно во **вложенной**:
в ней лежат `docker-compose.yml` и `SETUP.md`.

### Проверить, что файл скачался целиком (необязательно)

Рядом с архивом на странице релиза лежит `tradedesk-<версия>.zip.sha256` — контрольная
сумма. Оборванная загрузка иначе проявится непонятной ошибкой на сборке.

```bash
shasum -a 256 -c tradedesk-0.1.0.zip.sha256   # macOS и Linux, ожидается «OK»
certutil -hashfile tradedesk-0.1.0.zip SHA256 # Windows: сверить строку глазами
```

### ⚠️ На Windows не проверено

> Windows помечает всё скачанное из интернета, и эта пометка переходит на файлы,
> распакованные встроенным распаковщиком. Из-за неё запуск `init.bat` на шаге 3 или
> `start.bat` на шаге 4 может упереться в предупреждение SmartScreen. **Мы этого не
> наблюдали** — Windows-машины у нас нет, и утверждать, что шаг нужен, мы не станем.
>
> Если предупреждение появится: правой кнопкой по **скачанному zip** → «Свойства» →
> галочка «Разблокировать» → «Применить», и только потом распаковывать. Проверка этого
> места — часть прогона `T-06`, и в финальную инструкцию (`T-01`) оно попадёт со
> скриншотом или не попадёт вовсе.

## 3. Создать файл настроек

```bash
make init
```

На Windows то же самое делает двойной щелчок по `infra\scripts\init.bat`
(⚠️ на Windows не проверено). Окно дождётся нажатия клавиши, чтобы вы успели прочитать
предупреждение про `MASTER_KEY`.

Машина без `make` или Git Bash вместо щелчка:

```bash
sh infra/scripts/init-env.sh
```

Команда создаёт файл `.env` в корне проекта: берёт шаблон `.env.example` и подставляет
в него сгенерированные пароли и ключи. В репозиторий `.env` не попадает — он в
`.gitignore`, и это правильно.

Вывод должен быть таким:

```
Создан /path/to/tradedesk/.env (права 600). Секреты сгенерированы, плейсхолдеры заменены.

⚠️  MASTER_KEY шифрует пароли брокерских счетов. Потеря ключа необратима —
    сохраните .env вместе с резервными копиями базы, иначе дамп бесполезен.

Дальше: make up
```

> «Права 600» — это ограничение доступа в том виде, в каком его понимают macOS и Linux:
> файл читает только ваша учётная запись. На Windows команда выполняется та же, но
> действуют там права NTFS, а не эти; насколько одно переходит в другое, мы **не
> проверяли** — Windows-машины у нас нет. От чего защита работает одинаково: `.env`
> не уезжает ни в репозиторий, ни в релизный архив, ни в резервную копию.

### ⚠️ Файл `.env` терять нельзя

Внутри `.env` лежит `MASTER_KEY` — ключ, которым шифруются пароли ваших брокерских
счетов в базе. Он существует в единственном экземпляре и нигде больше не хранится.

- Потеряли `.env` — пароли счетов из базы **не восстановить ничем**. Резервная копия
  базы без этого ключа бесполезна: в ней лежат зашифрованные строки, а ключа нет.
- Поэтому храните копию `.env` там же, где будете хранить резервные копии базы.
- Повторный `make init` **ничего не перезаписывает**: если `.env` уже есть, команда
  откажется работать и объяснит почему. Это защита, а не ошибка.

Менять `MASTER_KEY` руками не нужно. Остальные значения в `.env` тоже трогать не надо —
кроме портов, если понадобится (см. «Если запуск упал»).

## 4. Запустить

Убедитесь, что Docker Desktop запущен (значок кита в трее/меню-баре), и выполните:

```bash
make up
```

Windows (Git Bash) или машина без `make`:

```bash
sh infra/scripts/start.sh
```

На Windows то же самое делает двойной щелчок по `infra\scripts\start.bat`
(⚠️ на Windows не проверено).

**Что происходит.** Поднимаются пять контейнеров: база данных PostgreSQL, Redis,
сервер приложения, планировщик фоновых задач и веб-интерфейс. Сервер при старте сам
приводит структуру базы в актуальный вид — отдельной команды для этого нет.

Планировщик — это то, что следит за временем без вас. Раз в минуту он проверяет, давно ли
выходил на связь коллектор каждого счёта, и если тот молчит дольше пяти минут, переводит
счёт в «требует внимания». Наружу планировщик ничего не отдаёт, своей страницы у него нет,
и в обычной работе вы о нём не вспоминаете.

**Сколько ждать.** Первый запуск дольше остальных: скачиваются образы (около 1 ГБ),
собирается образ сервера, ставятся зависимости веб-части.

На нашей машине запуск «с нуля» — пустая база, пустые зависимости — занял 40 секунд,
но образы там уже были скачаны, а сборка бралась из кэша. **На по-настоящему чистой
машине будет заметно дольше**: добавьте скачивание около 1 ГБ и первую сборку образа
сервера. Сколько именно это займёт, мы не мерили и придумывать не будем. Повторные
запуски — 15–35 секунд.

Команда ждёт, пока все пять контейнеров действительно станут рабочими, и только потом
печатает адреса. Если что-то не поднялось — она покажет последние строки лога и
завершится с ошибкой, а не соврёт про успех.

Какая версия у вас установлена, показывает <http://localhost:8000/api/v1/version> — это
тот же номер, что стоит в имени скачанного архива и в файле `VERSION` рядом с
`docker-compose.yml`. Он пригодится, если что-то придётся чинить вместе.

Успешный вывод:

```
TradeDesk поднят (профиль local).

  Приложение   http://localhost:5173
  API          http://localhost:8000/api/v1/health
  Документация http://localhost:8000/api/v1/docs

Код для входа писем не шлёт: он лежит на странице
  http://localhost:8000/api/v1/dev/outbox
Искать его в логах не нужно — в логи код не попадает никогда.

Остановить: make down
```

## 5. Войти

### Письма никуда не отправляются — не ждите их

Почта к приложению не подключена. Код для входа **не придёт ни на какой адрес**. Он
кладётся на локальную страницу «Письма (dev)», которая живёт только у вас на машине.

Адрес почты при входе можно указать любой, даже несуществующий: аккаунт заводится по
первому входу. Например, `me@example.com`.

### Порядок

1. Откройте <http://localhost:5173>. Появится экран «Вход».
2. Введите адрес почты и нажмите «Получить код». Форма перейдёт к полю «Код из письма».
3. Нажмите ссылку **«Открыть письма (dev)»** под формой — это и есть страница
   «Письма (dev)». Прямой адрес: <http://localhost:5173/dev/outbox>.
4. Самое верхнее письмо — ваше. В нём строка вида «Код для входа в TradeDesk: 123456».
   Письма ещё нет — нажмите «Обновить».
5. Вернитесь кнопкой **«К форме входа»**. Поле кода останется на месте: запрашивать код
   заново не нужно.
6. Введите код. Форма отправляется сама, как только набраны шесть цифр, — кнопку
   «Войти» нажимать не обязательно.

Код действует 10 минут и годится на один вход. Запросили несколько раз — берите
**самый верхний** код в списке. Если код успел истечь, страница входа скажет об этом
и предложит запросить новый.

Вы попадёте на экран «Дашборд». Слева вверху появится меню, справа — ваш адрес почты
и кнопка «Выйти». Это и есть успешная установка. Страница «Письма (dev)» после входа
есть и в самом меню.

Если вам удобнее без браузера, тот же список писем отдаёт
<http://localhost:8000/api/v1/dev/outbox> — там же, но в виде JSON. Именно этот адрес
печатает `make up`.

## 6. Что уже работает, а чего ещё нет

Проект на раннем этапе. Меню полное, но за большинством пунктов пока заглушки.

**Работает:**

- вход по коду и выход;
- **Настройки** — экран открывается и даёт задать имя, часовой пояс и час начала
  торгового дня (сохранение мы в этом прогоне не проверяли);
- переключение тёмной и светлой темы;
- страница «Письма (dev)».

**Ещё не работает — открывается страница с надписью «Экран появится в одной из
следующих задач»:**

- Дашборд;
- Журнал и карточка позиции;
- Календарь;
- Счета (и переключатель счетов в шапке — там пока подпись-заглушка).

**Синхронизации с MetaTrader 5 нет.** Программа-сборщик, которая забирает сделки из
терминала, в этот запуск не входит: она работает только на Windows и ставится отдельно.
Поэтому сделок в приложении сейчас взяться неоткуда — это не поломка установки.

## 7. Остановить и запустить снова

```bash
make down
```

Windows (Git Bash) или машина без `make`:

```bash
sh infra/scripts/stop.sh
```

На Windows то же самое делает `infra\scripts\stop.bat` (⚠️ на Windows не проверено).

Команда гасит только контейнеры TradeDesk; чужие контейнеры на машине она не трогает.

**Данные остаются.** База живёт в отдельном хранилище Docker, которое остановка не
удаляет. Проверено: после `make down` и повторного `make up` пользователь и его сессия
остались на месте — браузер даже не попросил войти заново.

Чтобы запустить снова — тот же `make up`. Повторный запуск ничего не ломает: команду
можно выполнять сколько угодно раз.

## 8. Обновиться, сделать копию, восстановить

Три команды, которые работают с **вашими** данными. Всё остальное в проекте можно
запустить заново с нуля; эти — нет, поэтому каждая сначала показывает, что собирается
сделать, и останавливается, если что-то не сходится.

| Команда | Скрипт | Что делает |
|---|---|---|
| `make update` | `infra\scripts\update.bat` | обновляет установку до свежего релиза |
| `make backup` | `infra\scripts\backup.bat` | сохраняет копию базы в `backups/` |
| `make restore file=…` | `infra\scripts\restore.bat` | возвращает базу из копии |

### Обновление

```bash
make update            # или: sh infra/scripts/update.sh
make update ARGS=--check   # только посмотреть, что доступно, ничего не менять
```

`update` сам скачивает архив со страницы релизов, сверяет контрольную сумму,
раскладывает файлы поверх установки и пересобирает приложение. Перед этим он
**делает резервную копию базы** — на случай, если новая версия чем-то не подойдёт.

Два места, где он откажется работать, и это правильно:

- **Обновляться нужно в той же папке, где приложение уже работало.** Если распаковать
  новую версию рядом и запустить обновление там, `update` остановится и скажет об этом.
  Причина в `MASTER_KEY` (см. раздел 3): в новой папке нет `.env`, ключ создастся
  заново, и пароли ваших счетов станут нечитаемы. Журнал при этом останется на месте,
  и заметить подмену было бы почти невозможно.
- **Файл `.env` должен быть на месте.** Без него обновление не начнётся.

`.env` и папка `backups/` обновление переживают: их нет в архиве, и трогать их незачем.

Если интернета нет — скачайте архив вручную и укажите файл:

```bash
sh infra/scripts/update.sh --file ~/Downloads/tradedesk-0.2.0.zip
```

В конце обновление **спрашивает у приложения его версию** и сверяет её с той, что
приехала в архиве. Не сошлось — это не «мелкая неточность в отчёте», а ровно тот случай,
когда файлы новые, а работает старый код: «обновился, и не помогло». Тогда `update`
останавливается, показывает обе цифры и говорит, что делать (пересобрать образ без кэша
и запустить `update` ещё раз).

**Если обновление оборвалось** (пропало питание, кончилось место, закрыли окно), запустите
`update` ещё раз. Он покажет, на чём именно остановился, и продолжит с того же места:

- оборвалось на переносе файлов — доперенесёт оставшиеся;
- оборвалось на сборке или запуске — дособерёт и поднимет.

Пока обновление не доведено до конца, `update` **не скажет** «уже последняя версия»,
даже если номер в файле версии уже новый: приложение при этом может лежать. Если у вас
на руках другой архив (например, вышла следующая версия), укажите его через `--file` —
обновление начнётся заново, поверх этих файлов. Если продолжить не получится вовсе —
`update` назовёт файл резервной копии, из которой можно вернуть базу.

### Резервная копия

```bash
make backup
```

Копия ложится в `backups/td-<дата>.sql.gz`. Скрипт **читает файл обратно** и проверяет,
что дамп дописан до конца и в нём есть все таблицы базы: оборвавшаяся копия по размеру
и имени выглядит как настоящая, и обнаружить подмену в день восстановления поздно.

Хранятся последние 14 копий, лишние удаляются по времени создания. В эти 14 **считаются
только файлы, которые открываются**: если в `backups/` попал посторонний файл с похожим
именем, он не вытеснит настоящую копию — про такие файлы скрипт скажет отдельно, но сам
их не удалит.

> ⚠️ **Копия базы без `.env` бесполезна.** Пароли счетов лежат в ней зашифрованными,
> а ключ — только в `.env`. Храните копию `.env` рядом с копиями базы.

### Восстановление

```bash
make restore file=backups/td-20260907-220321.sql.gz
```

Это единственная команда, которая **стирает** текущее содержимое базы. Поэтому она:

1. проверяет файл до того, как что-то трогает: повреждённую копию не примет, и копию
   чужой базы — тоже;
2. показывает таблицу «сейчас в базе / станет из копии», чтобы было видно, что
   теряется. Таблица, которой в копии нет вовсе, помечена «останется как есть» — её
   строки восстановление не тронет, и это не то же самое, что «станет 0»;
3. говорит, тем ли `MASTER_KEY` зашифрованы пароли счетов в этой копии. Не тем — журнал,
   сделки и рефлексии вернутся полностью, а пароли счетов придётся ввести заново;
4. просит ввести слово `restore` — не «y», а слово целиком;
5. снимает ещё одну копию текущего состояния, прежде чем перезаписать;
6. заливает всё одной транзакцией: либо применится целиком, либо база останется прежней.

Сверх этого `restore` и `update` проверяют путь к папке установки (см. «Если запуск
упал») — до того, как что-то сделают. Обе команды заканчиваются запуском приложения,
а после переноса папки путь мог стать непригодным: наткнуться на такой отказ уже после
перезаписи базы было бы худшим из моментов.

## Если запуск упал

Запуск не молчит: он либо доводит все пять контейнеров до рабочего состояния и печатает
адреса, либо говорит, что не вышло. Два случая ниже — те, с которыми мы столкнулись
лично; третий разбор — про всё остальное.

### В пути к папке есть русские буквы

```
В пути к папке установки есть символы, которые Docker не понимает:

    C:\Users\Никита\Downloads\tradedesk-0.1.0
```

Дальше сообщение объясняет причину и что делать. Коротко: перенесите **всю папку**
установки туда, где в пути только латиница — `C:\tradedesk`, `/Users/Shared/tradedesk`,
`~/tradedesk` — и запустите снова. Переносите вместе со скрытым файлом `.env`: в нём
`MASTER_KEY`.

Это не наша придирка и не то, что лечится повтором: Docker обрывает сборку нескольких
образов из такой папки ещё до начала (подробности и границы проверенного — в разделе 2).
Проверка стоит до сборки, чтобы вместо невнятной ошибки про gRPC вы увидели название
причины.

**Если перенести папку нельзя.** Обход есть, и он из двух переменных сразу — из
терминала (на Windows — Git Bash), находясь в папке установки:

```bash
TD_ALLOW_NON_ASCII_PATH=1 DOCKER_BUILDKIT=0 sh infra/scripts/start.sh
```

`TD_ALLOW_NON_ASCII_PATH=1` снимает нашу проверку, `DOCKER_BUILDKIT=0` включает старый
сборщик Docker — тот заголовка с путём не шлёт. Порознь ни одна не поможет: с первой
падает Docker, со второй до Docker не дойдёт дело. Плата — первая сборка заметно
дольше: старый сборщик не видит кэш нового. Проверено на macOS; штатный путь — всё-таки
перенести папку.

### Порт занят

TradeDesk занимает четыре порта на `127.0.0.1`: **5173** (приложение), **8000** (сервер),
**5432** (база), **6379** (Redis). Если какой-то из них уже держит другая программа,
запуск остановится:

```
Error response from daemon: ... Bind for 0.0.0.0:5432 failed: port is already allocated

Порт занят другой программой. TradeDesk слушает 5173 (web), 8000 (api),
5432 (postgres), 6379 (redis) — всё на 127.0.0.1.
Освободи порт или задай другой в .env: WEB_PORT, API_PORT, POSTGRES_PORT, REDIS_PORT.
```

У нас на 5432 сидел PostgreSQL от соседнего проекта — это самый частый случай. Так же
легко занимается 6379: Redis есть почти в каждом проекте.

**Как починить.** Откройте `.env` и найдите закомментированный блок под строкой
`# Порты на хосте` — ближе к концу файла, сразу после `DOMAIN=`:

```
#WEB_PORT=5173
#API_PORT=8000
#POSTGRES_PORT=5432
#REDIS_PORT=6379
```

Уберите `#` у нужной строки и поставьте другой номер — например `POSTGRES_PORT=5433`.
Сохраните файл и повторите `make up`.

Если меняете `WEB_PORT`, поправьте в том же `.env` и строку `APP_URL=http://localhost:5173`
на новый номер: это единственное место, где адрес приложения записан явно, и держать там
неверный незачем. На работу приложения расхождение сейчас не влияет — по коду `APP_URL`
читает одна проверка, источника запросов, и она вдобавок разрешает тот адрес, по которому
открыта страница. Отдельно этот случай мы не прогоняли, вывод сделан по коду.

### Что-то ещё

Если ни один из двух случаев выше не подошёл, последняя строка выглядит так:

```
docker compose up завершился с кодом 1 — окружение не поднято.
Причина — в строках Docker выше. Что делать: SETUP.md, раздел «Если запуск упал».
```

Число в этой строке — код возврата Docker. Пустого места на его месте не бывает: если код
неизвестен (Docker прервали на полпути), так и будет написано словами. Причину ищите
в строках Docker над сообщением; их же присылайте нам вместе с кодом, если разбираться
придётся вместе.

Другие неполадки здесь не перечислены намеренно: их мы не наблюдали и выдумывать
не стали. Раздел пополнится в `T-01` — по тому, что вылезет на прогоне `T-06`
на чистой Windows-машине.

## Что здесь проверено, а что нет

Честно, чтобы вы знали, где инструкция опирается на предположение.

**Проверено реальным прогоном (macOS, Docker 29.6.1, Compose v5.3.0):** создание `.env`,
отказ повторного `make init` перезаписывать файл, запуск с занятым портом и его
исправление через `.env`, полный запуск всех пяти контейнеров, вход по коду со
страницы писем, открытие экрана настроек, остановка и повторный запуск с сохранением
данных, запуск скриптами `sh infra/scripts/…` напрямую, без `make`.

**Проверено для раздела «Если запуск упал» (`X-53`, `X-54`), на macOS:** запуск с
заведомо испорченным `docker-compose.yml` — Docker вернул код 1, и это число стоит
в сообщении (до правки на его месте был пробел); запуск из папки с кириллицей —
шаг 4 отказывается работать и называет причину, ни одной команды Docker при этом
не выполняется. Обход проверен по частям: `DOCKER_BUILDKIT=0 docker compose --profile
local build` из той же папки доходит до конца, а `TD_ALLOW_NON_ASCII_PATH=1` пропускает
шаг 4 дальше проверки (это под тестом, `make test-scripts`); целиком, одной командой
и до работающего приложения, обход не прогонялся. Сама сборка из кириллического пути
падает у Docker, а не у нас; что именно проверено и где граница — ниже.

**Проверено на релизном архиве (`X-19`):** архив распакован в пустую папку, и с шага 3
по шаг 5 инструкция пройдена именно в ней — `.env`, запуск, вход по коду. Версия,
которую показывает `/api/v1/version`, совпала с именем архива. Проверка шла на macOS;
номера портов при этом были другими, потому что на машине уже работала другая копия.

**Проверено для раздела 8 (`T-02`), на macOS,** на установке, развёрнутой из релизного
архива в папку с пробелом в пути, с данными: счёт с паролем (то есть с зашифрованным
блобом в базе), пользователь, теги. Проверялись версии 0.9.0 → 0.9.1 → 0.9.2, собранные
`make release` из этой ветки:

- `make backup` — копия снимается, проверяется чтением, ротация считает по времени
  создания, а не по имени. Отдельно проверено на замусоренном каталоге: 21 посторонний
  файл с именем `td-*.sql.gz` (нулевые, не-gzip, один с датой 2100 года) не вытеснил
  ни одной из пяти настоящих копий, и все 21 названы в выводе. С `TD_BACKUP_KEEP=3`
  ротация действительно удаляет лишние — среди целых копий, мусор не трогая;
- повреждённая копия (оборванный gzip и оборванный дамп) — `restore` отказывается
  восстанавливать, база не тронута;
- `make restore` — данные вернулись целиком; страховочная копия, которую `restore`
  снимает перед заливкой, тоже восстанавливается и возвращает состояние «до»;
- `restore` из копии, в которой одной таблицы нет вовсе, — предпросмотр пишет
  «останется как есть», а не «станет 0». Сама заливка при этом откатилась: внешний ключ
  уцелевшей таблицы держит индекс той, которую дамп сносит, — psql отказался, транзакция
  откатилась, база осталась прежней;
- `restore` из копии с чужим `MASTER_KEY` — предпросмотр называет отпечаток и говорит,
  что пароли счетов придётся ввести заново;
- `make update` — обновление из файла прошло до конца: приложение поднялось и назвало
  ту же версию, что в архиве; теги, счёт с паролем, `.env` и `backups/` целы;
- `update`, оборванный ровно между переносом файлов и сборкой (процесс убит, контейнеры
  погашены) — повторный запуск **не** сказал «уже последняя версия», а показал этап
  и дособрал приложение;
- `update` на архиве, где версия приложения отстала от файла `VERSION`, — отказ с обеими
  цифрами и кодом возврата 1; из этого состояния установка вылечилась указанием
  правильного архива через `--file`;
- `update` с подменённым `MASTER_KEY` — отказ (код 4), ничего не изменено;
- `update` без `.env` и `update` в клоне репозитория — отказ;
- `restore` с путём в форме Windows (`backups\td-….sql.gz`) — файл найден.

**Не проверено:**

- **Всё, что относится к Windows** — установка Docker Desktop с WSL2, работа Git Bash,
  файлы `init.bat`, `start.bat`, `stop.bat`, `update.bat`, `backup.bat`, `restore.bat`.
  Ни один `.bat` не запускался: Windows-машины у нас нет. Разойтись с `.sh` им почти
  негде — каждый только вызывает свой `.sh` через bash; своего у них ровно два:
  сообщение про отсутствующий bash и ожидание клавиши в конце (`init`, `update`,
  `backup`, `restore`). И это утверждение проверено чтением, а не прогоном.
  Эти места помечены плашкой.
- **Права на `.env` под Windows.** `init-env.sh` вызывает `chmod 600`; на NTFS доступ
  определяют не эти биты, а права учётной записи, и как одно ложится на другое,
  мы не проверяли.
- **Путь к файлу с обратными слэшами на самой Windows.** `restore.bat backups\td-….sql.gz`
  отдаёт путь в форме cmd, а Git Bash разделителем `\` не считает — `restore.sh` такой
  путь распознаёт и приводит к своему виду. Проверено это на macOS подстановкой такого
  же аргумента, а не в Git Bash.
- **Скачивание архива со страницы релизов.** Релизов сейчас **не опубликовано ни
  одного**, поэтому шаг 2 и `make update` без аргументов упрутся в пустую страницу.
  Проверено другое: репозиторий действительно открыт и читается без аккаунта GitHub,
  а `update` умеет ставить версию из файла, скачанного вручную (`--file`).
- **Распаковка zip на Windows.** `update` пробует по очереди `unzip`, `bsdtar`, `tar`
  и `Expand-Archive` из PowerShell; на macOS сработал первый, остальные три не
  проверялись.
- **Путь установки с кириллицей — на Windows.** На macOS проверено прогоном и разложено
  по случаям (копия проекта, `docker compose --profile local build`): папка
  `tradedesk-тест` — обрыв до начала сборки с `failed to dial gRPC … header key
  "x-docker-expose-session-sharedkey" contains value with non-printable ASCII
  characters`; та же папка на латинице — собирается; кириллица только в родительских
  папках — собирается; один образ вместо двух из папки с кириллицей — собирается;
  `COMPOSE_BAKE=false` не спасает, `DOCKER_BUILDKIT=0` спасает. Это ограничение Docker,
  а не наших скриптов. **На Windows путь устроен иначе, и там это предположение** —
  проверит `T-06`; заодно там выяснится, ломает ли на Windows кириллица в родительских
  папках. Отказ шага 4 при таком пути сработает в любом случае: он смотрит на сам путь
  целиком, а не на поведение Docker, и потому строже измеренного — так задумано.
  Проверка раздела 8 шла в папке с пробелом, но без кириллицы, и пробел проблемой
  не оказался.
- **Позиции, сделки и рефлексии в проверке раздела 8.** Их в базе не было: сборщик
  позиций (`S1-03`) сделки в позиции ещё не превращает, а сеялки нет. Пользовательский
  слой представлен тегами и счётом с паролем — то, что пишется через API сегодня.
  Утверждение «`update` не теряет позиции и рефлексии» на реальных позициях
  **не проверено**.
- **Пометка «скачано из интернета» и SmartScreen** на шаге 2. Windows-машины у нас нет;
  нужен ли шаг «Разблокировать», выяснит `T-06`.
- **Время первого запуска на чистой машине.** У нас образы уже были скачаны, а сборка
  бралась из кэша. На Windows вдобавок медленнее ставятся зависимости веб-части — из-за
  того, как Docker пробрасывает файлы проекта внутрь контейнера.
- **Сохранение настроек** на экране «Настройки»: экран открывали, значения не меняли.
