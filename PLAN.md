# План поэтапной разработки платформы трейдер‑аналитики

Версия 1.3 — 3 сентября 2026 (v1.1: веха «Первый тест»; v1.2: несколько счетов на пользователя; v1.3: все счета в USD, ссылка на SPEC.md)

Ориентир — функционал HybridTrader (dash.hybridtrader.ai): дашборд, журнал сделок с автосинком из MetaTrader 5, психология трейдера, отчёты, Macro Desk. Сначала делаем для себя, затем выводим на рынок СНГ.

---

## 1. Цели и принципы

**Цель этапа «для себя».** Открыл браузер — увидел все свои сделки из MT5, свежие, без единого ручного действия, с базовой статистикой и возможностью записать рефлексию по каждой сделке.

**Цель этапа «рынок СНГ».** Тот же продукт, выдерживающий десятки‑сотни пользователей, с оплатой подписки, поддержкой нескольких путей импорта и модулями психологии, отчётов и макро‑контекста.

**Принципы, которые не нарушаем.**

1. Сбор сделок — серверный. Пользователь один раз вводит данные счёта (investor‑пароль, только чтение), дальше всё происходит само.
2. Один нормализованный формат сделок для всех источников (терминал, советник, CSV). Источник — деталь реализации за интерфейсом `TradeSource`.
3. Данные брокера («факты») и пользовательский слой (заметки, теги, рефлексии, правки) хранятся раздельно и не затирают друг друга.
4. Всё время — в UTC. Смещение сервера брокера хранится отдельно. Отображение — в таймзоне пользователя.
5. Рефлексия — структурированная (поля с фиксированными значениями), не свободный текст. На ней строится модуль психологии.
6. Каждый этап заканчивается работающим продуктом, которым можно пользоваться. Не начинаем следующий, пока текущий не в ежедневном использовании.
7. Проект с первого дня запускается локально одной командой по инструкции, без сервера. Первый внешний тест — self‑hosted у друга сразу после журнала и автосинка (см. веху «Первый тест» после этапа 2).

## 2. Стек и архитектура

| Слой | Технология | Почему |
|---|---|---|
| API | Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, Pydantic v2 | Официальная библиотека MT5 только на Python; pandas/polars для аналитики; LLM‑слой позже на том же языке |
| База | PostgreSQL 16 (JSONB под сырые данные, materialized views под агрегаты) | Одна база на всё; TimescaleDB подключим только под котировки в Macro Desk |
| Кеш / очереди | Redis 7 + arq (воркер фоновых задач) | Импорт CSV, пересчёт агрегатов, письма, rate‑limit OTP |
| Коллектор MT5 | Python‑сервис на Windows‑VPS + пакет `MetaTrader5`, терминалы в portable‑режиме | Единственный «официальный» путь без брокерской лицензии; один терминал = один счёт |
| Советник | MQL5 Expert Advisor (`WebRequest` → API) | Запасной путь для тех, кто не отдаёт investor‑пароль |
| Фронтенд | Vite + React 19 + TypeScript, React Router, TanStack Query/Table, Tailwind, shadcn/ui, Lightweight Charts, Recharts | SPA за логином, SEO не нужен, серверная логика уже в FastAPI |
| Контракт | OpenAPI из FastAPI → `openapi-typescript` для фронта | Типы не расходятся |
| Auth | Email + одноразовый код (OTP), сессия в httpOnly‑cookie | Как у оригинала; без паролей |
| Письма | Абстракция `EmailProvider`: Resend/Postmark сейчас, Unisender/SendPulse для СНГ | Доставляемость — известная боль, провайдер меняется одной строкой |
| Файлы | S3‑совместимое хранилище (Cloudflare R2 → Yandex Object Storage / Selectel) | Скриншоты сделок, подписанные ссылки |
| Инфра | Docker Compose на Linux‑VPS (api, worker, postgres, redis, caddy) + Windows‑VPS для коллектора | Kubernetes не нужен до сотен пользователей |
| Наблюдаемость | Sentry, structlog, heartbeat коллектора, uptime‑чек | «Needs attention» в UI строится на heartbeat |
| Биллинг (этап 7) | ЮKassa / CloudPayments для СНГ, Paddle для международного | Stripe напрямую недоступен |

### Схема потоков

```
[MT5 терминал брокера]                     [Пользователь: браузер]
        │  history_deals_get                          │
        ▼                                             ▼
[Коллектор, Windows‑VPS]  ──HTTP, сервисный токен──▶ [FastAPI]  ◀── [React SPA]
   • один процесс на счёт                               │
   • опрос каждые 60 с                                  ├──▶ [PostgreSQL]
   • heartbeat                                          ├──▶ [Redis / arq worker]
                                                        └──▶ [S3: скриншоты]
[MQL5 советник у пользователя] ──WebRequest──▶ тот же /ingest
[CSV‑файл] ──загрузка──▶ worker → тот же нормализатор
```

```

  docs/

```

## 3. Модель данных (ядро)

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | Пользователь | email, timezone, created_at |
| `sessions`, `otp_codes` | Auth | user_id, code_hash, expires_at, attempts |
| `trading_accounts` | Счёт у брокера. **У пользователя их может быть несколько** (демо + реальный, разные брокеры, проп‑счета) | user_id, label («Демо FTMO», «Реал Alpari»), is_demo, color, platform (`mt5`/`tradelocker`/`csv`), broker, server, login, currency, account_type (`hedging`/`netting`), server_utc_offset, status, last_sync_at, credentials_ref, sort_order, is_archived |
| `credentials` | Зашифрованные данные доступа | account_id, ciphertext (envelope‑шифрование, ключ на пользователя) |
| `deals` | Факты от брокера, неизменяемые | account_id, deal_ticket, order_ticket, position_id, symbol_raw, type, entry (in/out/inout), volume, price, profit, commission, swap, fee, time_utc, raw JSONB. **Уникальный ключ `(account_id, deal_ticket)`** |
| `positions` | Собранные из deals позиции — единица журнала | account_id, position_id, symbol_norm, direction, open_time, close_time, avg_entry, avg_exit, volume, net_pnl, gross_pnl, commission, swap, status (`open`/`closed`), duration |
| `symbols` | Нормализация символов | raw → norm (`EURUSD.m` → `EURUSD`), asset_class, contract_size, pip_size, quote_currency |
| `journal_entries` | Пользовательский слой над позицией | position_id, notes, tags[], planned_entry/sl/tp (для R‑multiple), manual_overrides JSONB |
| `reflections` | Структурированная рефлексия | position_id, setup_grade (A/B/C/D), execution_grade, followed_plan (bool), emotion_before/during/after (enum), mistakes[] (enum), confidence (1–5), free_text |
| `attachments` | Скриншоты | position_id, s3_key, width, height |
| `sync_runs` | Журнал синхронизаций | account_id, source, started_at, finished_at, deals_received, deals_new, error |
| `daily_stats` (mat. view) | Агрегаты по дням | account_id, date, pnl, trades, wins, losses, volume |
| `subscriptions` (этап 7) | Доступ | user_id, plan, status, provider, period_end |

Замечание по нескольким счетам: все сделки, позиции, рефлексии и агрегаты привязаны к `account_id`, а не к пользователю напрямую. Любой запрос журнала и аналитики принимает набор `account_ids` — один счёт, несколько или все. **Решение: на этапах 0–4 все счета в USD**, конвертации валют нет; поле `currency` хранится и проверяется при подключении (счёт не в USD пока не принимаем с понятным сообщением), таблица `fx_rates` и пересчёт — отложены до выхода на рынок. По умолчанию демо‑счета не смешиваются с реальными в сводной аналитике — пользователь включает это явно.

Замечание по `positions`: у хеджинговых счетов `position_id` в deals однозначно собирает позицию; у неттинговых позиция по символу одна, и «сделка» в журнале определяется по обнулению объёма. Сборщик позиций — отдельный, хорошо протестированный модуль; на него пишем тесты первым делом.

## 4. Этапы

Оценки даны для одного разработчика, работающего полный день с AI‑ассистентом. Двое — примерно ×0,6 по срокам.

### Этап 0 — Фундамент (1,5–2 недели)

Цель: пустой, но полностью собранный продукт — вход по OTP, пустой дашборд, деплой на VPS одной командой.

Задачи:

1. Монорепо, линтеры (ruff, mypy, eslint, prettier), pre‑commit, CI (GitHub Actions: тесты + сборка образов).
2. FastAPI‑скелет: конфиг, подключение к БД, Alembic, health‑эндпоинт, structlog, Sentry.
3. Миграции ядра: `users`, `sessions`, `otp_codes`, `trading_accounts`, `credentials`, `deals`, `positions`, `symbols`, `sync_runs`.
4. Auth: запрос кода → письмо → проверка → cookie‑сессия. Rate‑limit 3 кода / 10 мин на email, 5 попыток на код, код живёт 10 минут. `EmailProvider` с реализацией Resend и `ConsoleEmailProvider` для разработки.
5. Шифрование `credentials`: envelope‑схема (мастер‑ключ в переменной окружения, на пользователя — data key). Тесты на шифрование/расшифровку/ротацию.
6. React‑скелет: роутинг, страницы Login / Dashboard / Journal / Accounts / Settings (заглушки), тёмная тема, layout с боковой навигацией, генерация типов из OpenAPI.
7. Docker Compose в двух профилях: `local` (api, worker, postgres, redis, фронт на localhost, письма выводятся в консоль/логи — код входа виден без почтового сервиса) и `prod` (то же + caddy, автосертификаты, реальный `EmailProvider`, бэкап Postgres по cron).
8. Черновик `SETUP.md` — инструкция локального запуска (дорабатывается на этапах 1–2, финальная версия — на вехе «Первый тест»).

Готово, когда: `docker compose --profile local up` поднимает всё на чистой машине и можно войти по коду из логов; CI зелёный; продовый профиль проверен хотя бы на локальной машине.

Риски: настройка почты (SPF/DKIM/DMARC) — заложить день; выбор Windows‑VPS для следующего этапа сделать уже сейчас, чтобы не ждать.

### Этап 1 — Коллектор MT5 и ингест (2–3 недели)

Цель: сделки с реального счёта появляются в базе автоматически, свежие в пределах минуты, без дублей.

Задачи:

1. Контракт `/ingest`: JSON‑схема батча deals (`packages/shared-schemas`), сервисный токен коллектора, идемпотентность по `(account_id, deal_ticket)`, ответ «принято / дубликаты / ошибки».
2. Нормализатор deals → `deals`: маппинг типов MT5 (`DEAL_TYPE_*`, `DEAL_ENTRY_*`, `DEAL_REASON_*`), перевод времени сервера брокера в UTC по смещению счёта, сохранение `raw`.
3. Сборщик позиций deals → `positions` для хеджинговых и неттинговых счетов: частичные закрытия, доливки, свопы и комиссии по всем deals позиции, открытые позиции. Набор тестовых фикстур с реальными выгрузками (свои счета + демо‑счета 2–3 брокеров).
4. Таблица `symbols` и нормализация: базовый словарь + эвристика (обрезка суффиксов), ручное сопоставление неизвестных через UI позже.
5. Коллектор (`apps/collector-mt5`): менеджер процессов, по одному терминалу в portable‑режиме на счёт; `initialize(path, login, password, server)`; первичная загрузка всей истории, затем инкрементально с `last_sync_at − 24 ч` (перекрытие гасится идемпотентностью); `positions_get` для открытых; heartbeat в API каждые 60 с; ретраи и переподключение; логи.
6. Скрипт установки коллектора на Windows (Python, терминал MT5, служба через NSSM или Task Scheduler, автозапуск после перезагрузки). Коллектор — обычный Windows‑процесс вне Docker: библиотека `MetaTrader5` не видит терминал из контейнера. Ходит в API по `http://localhost:8000` при локальном запуске и по домену — при серверном; адрес и токен задаются в `collector.env`.
7. UI «Accounts»: список счетов пользователя (несколько на аккаунт — демо и реальные), добавить счёт (название, метка «демо», цвет, платформа, брокер, сервер, логин, investor‑пароль), статусы `pending / connected / needs_attention / paused`, «последний синк», кнопка «синхронизировать сейчас», пауза, архивирование и удаление (удаление — с удалением credentials, сделки остаются). Коллектор поднимает по терминалу на каждый активный счёт; лимит счетов на машину задаётся в конфиге.
9. Глобальный переключатель счетов в шапке приложения: один счёт / несколько (мультивыбор) / все реальные / все. Выбор запоминается и применяется ко всем экранам — журнал, календарь, дашборд, позже психология и отчёты. Счёт помечается своим цветом в таблицах и на графиках.
8. Экран статуса синка: последние `sync_runs`, ошибки человеческим языком («неверный пароль», «сервер не найден», «терминал недоступен»).

Готово, когда: добавил свой счёт в UI → через минуту вся история в базе; закрыл сделку в терминале → через минуту она в базе; перезагрузка Windows‑VPS не требует ручных действий; повторный прогон истории не создаёт дублей.

Риски и как гасим:

- Официальная библиотека MT5 работает только с Windows‑терминалом и держит один логин на процесс — поэтому по процессу на счёт и planning памяти ~300–400 МБ на терминал.
- Брокер может блокировать вход с IP дата‑центра или требовать 2FA (у некоторых проп‑фирм) — проверить на своих брокерах до начала этапа; для таких счетов — советник (этап 4).
- Investor‑пароль не даёт торговать, но всё равно чужой секрет: логировать доступ, никогда не писать пароль в логи, показывать пользователю, что хранится и зачем.
- Смещение сервера брокера с переходом на летнее время: хранить историю смещений или брать смещение из `TIME_TRADE_SERVER` каждой синхронизации и записывать в `sync_runs`.

### Этап 2 — Журнал (2–3 недели)

Цель: полноценный журнал сделок, которым удобно пользоваться каждый день с ноутбука и телефона.

Задачи:

1. API журнала: список позиций с фильтрами (набор счетов из глобального переключателя, период, символ, направление, результат, тег), сортировка, пагинация курсором; карточка позиции с deals, заметками, рефлексией, вложениями. В сводном режиме — колонка «счёт» с цветной меткой; ручная сделка создаётся с явным выбором счёта.
2. Таблица сделок (TanStack Table): виртуализация, сохранение фильтров в URL, колонки настраиваемые, мобильный режим — карточки вместо таблицы.
3. Карточка сделки: факты от брокера (нередактируемые), deals внутри позиции, поле заметок, теги (автокомплит по существующим), ручные поля `planned_sl / planned_tp / planned_entry` для расчёта R.
4. Рефлексия: форма по схеме `reflections` (оценки сетапа и исполнения, следование плану, эмоции до/во время/после, ошибки из словаря, уверенность, свободный текст). Схема словарей вынесена в конфиг — будем менять.
5. Скриншоты: загрузка drag‑and‑drop и вставка из буфера, сжатие на клиенте до 2000 px, presigned‑upload в S3, превью, удаление.
6. Календарь: месяц с P&L и числом сделок по дням, клик — список сделок дня. Дни по таймзоне пользователя. В режиме нескольких счетов — суммарный P&L дня и разбивка по счетам при наведении.
7. Ручное добавление сделки (для счетов без интеграции) и правка ручных сделок; импортированные — только пользовательский слой.
8. Настройки: таймзона, валюта отображения, часы торговой сессии (для группировки «день»).

Готово, когда: неделю ведём журнал только здесь; на телефоне удобно; ни одного «сделка не в тот день».

Риски: свободные теги быстро превращаются в помойку — ограничить словарём с возможностью добавлять; рефлексия должна заполняться за 30 секунд, иначе её не будут заполнять — измерять время заполнения и упрощать.

### Веха «Первый тест» — self‑hosted у друга (1 неделя подготовки, затем 1–2 месяца использования)

Цель: посторонний человек клонирует репозиторий, по инструкции запускает платформу у себя на компьютере и ведёт в ней журнал 1–2 месяца, пока мы делаем этапы 3–4 и переезжаем на сервер. Это первый реальный тест журнала и автосинка на чужом счёте, чужом брокере и чужой машине.

Подготовка (после этапа 2, до начала этапа 3):

1. `SETUP.md` — пошаговая инструкция для человека, который не разработчик: установить Git и Docker Desktop (WSL2), клонировать репозиторий, скопировать `.env.example` → `.env`, выполнить `docker compose --profile local up`, открыть `http://localhost:5173`, взять код входа из логов (или из окна «Письма» в dev‑режиме, чтобы не лазить в логи). Отдельный раздел — установка коллектора: Python, терминал MT5 брокера, `collector.env`, запуск скриптом `run-collector.bat`, автозапуск через Task Scheduler. Скриншоты каждого шага.
2. Скрипты «одной кнопки»: `start.bat` / `start.sh` (поднять всё), `stop.bat`, `update.bat` (git pull + пересборка + миграции без потери данных), `backup.bat` (дамп Postgres в файл).
3. Обновления без потери данных: миграции Alembic обратно совместимы, данные Postgres — в именованном volume, `update.bat` делает бэкап перед миграцией.
4. Экспорт/импорт всей базы пользователя (дамп → загрузка), чтобы через 1–2 месяца перенести его журнал с локальной машины на сервер без ручного ввода. Проверить перенос на своих данных до передачи другу.
5. Запасной путь на случай, если коллектор у него не заведётся (брокер блокирует, не Windows, 2FA): CSV‑импорт минимальной версии (формат отчёта MT5) — переносится из этапа 4 сюда, если понадобится.
6. Канал обратной связи: Telegram‑чат + кнопка «Сообщить о проблеме» в приложении, которая копирует в буфер версию, ОС, последние ошибки коллектора. Лёгкая анонимная телеметрия ошибок в Sentry (по согласию).
7. Чек‑лист приёмки для друга на первую неделю: подключить демо и реальный счёт, дождаться синка обоих, проверить, что сделки и P&L каждого совпадают с терминалом, переключиться между счетами и в сводный режим, заполнить 10 рефлексий, загрузить скриншот, проверить календарь.

Что мы делаем параллельно: этап 3 (дашборд), этап 4 (советник, CSV, стабилизация), переезд на VPS. Раз в 1–2 недели друг обновляется через `update.bat`, получает новые экраны и продолжает тест. По окончании — переносим его данные на сервер, он переходит на серверную версию, локальная остаётся как вариант self‑hosted (может пригодиться для рынка как отдельное предложение).

Готово, когда: друг запустил платформу и подключил счёт по инструкции без нашего вмешательства (или мы записали каждое место, где понадобилась помощь, и поправили инструкцию); в течение первых двух недель нет расхождений сделок с терминалом.

Риски: ~~у друга Mac или Linux~~ и ~~слабый ноутбук~~ — **сняты 2026‑09‑03: Windows, 16 ГБ**; обновления ломают базу — миграции тестируются на копии его дампа перед выкаткой.

### Этап 3 — Дашборд и аналитика (2 недели)

Цель: стартовый экран отвечает на вопросы «как я торгую» и «что требует внимания».

Задачи:

1. Документ `docs/metrics.md` с формулами: net/gross P&L, winrate, profit factor, expectancy, средний win/loss, R‑multiple (по `planned_sl`, иначе «н/д»), максимальная просадка по эквити закрытых сделок, серии побед/поражений, P&L по символам, по дням недели, по часам, по длительности удержания. Тесты на формулы против ручного расчёта.
2. Мат. view `daily_stats` и сервис агрегатов с инвалидацией после каждого ингеста (arq‑задача).
3. Дашборд: KPI‑плитки за выбранный период, кривая эквити (Lightweight Charts), календарь‑мини, топ/антитоп символов, распределение по времени суток, открытые позиции, блок «требует внимания» (счёт needs_attention, сделки без рефлексии, дни без записей). Подчиняется глобальному переключателю счетов: для одного счёта — его метрики; для нескольких — сводные плюс сравнение счетов рядом (таблица «счёт → P&L, winrate, PF, сделок») и кривые эквити по счетам на одном графике разными цветами. Демо и реал в сводке разделяются, если пользователь не включил смешивание.
6. `daily_stats` считается по счёту; сводка по нескольким счетам — сумма по дням, чтобы не пересчитывать сделки на лету.
4. Пустое состояние: онбординг «подключи счёт → дождись синка → заполни первую рефлексию» с прогрессом.
5. Экспорт: CSV выгрузка журнала, PDF/PNG кривой эквити.

Готово, когда: цифры сходятся с отчётом терминала MT5 по тому же периоду (проверка вручную по 3 счетам); дашборд открывается < 1 с при 5 000 сделок.

Риски: расхождение с отчётами брокера из‑за свопов/комиссий и порядка округления — фиксируем в `metrics.md`, что и как считаем, и показываем «gross / net» отдельно.

### Этап 4 — Запасные пути импорта и стабилизация (2 недели)

Цель: пользоваться могут те, кто не отдаёт пароль, и те, у кого не MT5; система переживает сбои сама.

Задачи:

1. MQL5‑советник: чтение истории, отправка батчами на `/ingest` с персональным ключом журнала, инкрементальная отправка, обработка ошибки 4014 с подсказкой «добавьте URL в разрешённые», инструкция для Windows и Mac (Wine‑сборка), упаковка для MQL5 Market.
2. CSV‑импорт: загрузка → определение формата (MT5 report XLSX/HTML, generic CSV) → маппинг колонок с превью → нормализация → тот же ингест. Пресеты для 3–4 популярных форматов. Обработка дат и разделителей.
3. Ручное сопоставление неизвестных символов через UI.
4. Надёжность коллектора: наблюдатель процессов, автоперезапуск терминала при зависании, алерт в Telegram при отсутствии heartbeat > 5 мин, ежедневная полная сверка истории (reconciliation) с отчётом о расхождениях.
5. Нагрузочный тест: 50 счетов × 5 000 сделок, генератор синтетической истории.
6. Экспорт и удаление данных пользователя по запросу (понадобится для рынка).

Готово, когда: 3 внешних тестировщика (знакомые трейдеры) подключились каждым из трёх способов без нашей помощи.

### Этап 5 — Психология и отчёты (3–4 недели)

Цель: аналог разделов Psychology, Composure и Reports.

Задачи:

1. Аналитика по рефлексиям: P&L и winrate в разрезе эмоций, оценок сетапа, «следовал плану / нет», типов ошибок; «стоимость привычки» — суммарный P&L сделок с данной ошибкой против остальных; повторяющиеся паттерны (например, третья сделка после двух убыточных).
2. Composure: индекс дисциплины на скользящем окне ~30 дней с экспоненциальным весом, состояния `calm / stable / elevated / fragile / tilted`, правила перехода задокументированы.
3. Отчёты: недельный и месячный текстовые разборы. Сначала шаблонные (генерация из цифр), затем LLM‑слой: промпт получает агрегаты и выборку рефлексий, возвращает разбор по фиксированной структуре. Абстракция `LLMProvider`, лимит токенов, кеширование, ручной «пересобрать».
4. AI‑оценка сделки: по запросу — разбор конкретной сделки с учётом рефлексии и контекста дня.
5. Уведомления: email/Telegram — «не заполнено N рефлексий», еженедельный отчёт готов.

Готово, когда: недельный отчёт читается как полезный, а не как пересказ таблицы (проверяем на себе и тестировщиках).

Риски: при малом числе рефлексий выводы шумные — показывать доверительные пометки «мало данных», не делать выводов с n < 10; стоимость LLM — считать на отчёт и ограничивать частоту.

### Этап 6 — Macro Desk (4–6 недель, отдельное решение о старте)

Цель: рыночный контекст к каждому дню и сделке. Самый дорогой модуль по внешним данным; стартуем только после того, как этапы 0–5 в ежедневном использовании.

Задачи:

1. Источники: экономический календарь (лицензируемый провайдер или бесплатный с ограничениями), новости (агрегаторы вроде Benzinga/NewsAPI‑класса, RSS), котировки (провайдер данных или собственный терминал MT5 как источник цен по нужным символам), сентимент (опционально). Абстракции `NewsProvider`, `CalendarProvider`, `PriceProvider`.
2. Хранение временных рядов: TimescaleDB, retention‑политики.
3. Сигналы Flow / Bearing / Pulse / Edge Factor: первая версия — прозрачные правила на технических индикаторах и календаре, документированные; статусы `stale / closed / degraded` при проблемах с данными.
4. Ежедневный премаркет‑брифинг и недельный обзор (шаблон + LLM).
5. Привязка контекста к сделкам: «что происходило на рынке в момент входа» в карточке сделки.
6. Экран Macro Desk: инструменты, сигналы, календарь с фильтром по важности, лента новостей.

Риски: стоимость данных может превысить экономику подписки — до старта посчитать бюджет на источники; юридические ограничения на перепубликацию новостей — показывать заголовки и ссылки, не тексты.

### Этап 7 — Биллинг и выход на рынок СНГ (3–4 недели)

Задачи:

1. Сущность `subscriptions`, gating доступа по статусу, grace‑период, льготный доступ для ранних пользователей.
2. Платёжный провайдер: ЮKassa или CloudPayments (рекуррентные платежи, вебхуки, чеки по 54‑ФЗ через провайдера), абстракция `PaymentProvider` под Paddle на будущее.
3. Юридическое: оферта, политика конфиденциальности, согласие на обработку данных, хранение данных в РФ при необходимости (перенос S3 и БД к российскому провайдеру).
4. Почтовый провайдер для СНГ, домены, DKIM.
5. Лендинг (отдельный проект, можно Next.js), страница брокеров, гайды по подключению, FAQ.
6. Поддержка: тикеты (email → Linear/Telegram), база знаний, шаблоны ответов по типовым проблемам («код не пришёл», «сделки не появились»).
7. Масштабирование коллектора: менеджер пула Windows‑машин, распределение счетов, мониторинг занятости памяти, лимит счетов на машину.
8. Онбординг новых пользователей, аналитика продукта (события), бета с ограниченным набором пользователей.

Готово, когда: посторонний человек оплатил, подключил счёт и ведёт журнал без обращения в поддержку.

## 7. Решения, принятые сейчас (ADR‑кратко)

1. Backend — Python/FastAPI, frontend — Vite + React + TS. Next.js не используем для приложения; лендинг — отдельный проект.
2. Основной способ сбора — серверный коллектор с официальной библиотекой `MetaTrader5` на Windows‑VPS. MetaApi — не используем на старте, держим как запасной провайдер за интерфейсом `TradeSource`.
3. Единица журнала — позиция, собранная из deals. Deals неизменяемы, хранятся с `raw`.
3a. Пользователь ↔ счета — один ко многим с первого дня; все данные привязаны к счёту, все экраны работают через глобальный переключатель счетов (один / несколько / все).
3b. Все счета в USD до выхода на рынок; мультивалютность — этап 7.
6. Детальная спецификация этапов 0–2 и вехи «Первый тест» для разработки с AI‑агентами — в `SPEC.md`; правила работы агентов в репозитории — в `CLAUDE.md`.
4. Рефлексия — структурированная схема с enum‑словарями в конфиге.
5. Биллинг и Macro Desk — после ежедневного использования базовых модулей.
