## Что не так

Для Windows есть `infra/scripts/start.bat` и `stop.bat` — их можно запустить двойным щелчком. Файла `init.bat` **нет**.

Значит шаг создания `.env` — самый первый после клонирования — на Windows выполним только из Git Bash. Инструкция это честно говорит, но получается разрыв: два шага из трёх запускаются щелчком, а первый требует другого инструмента.

## Почему это важно

Целевой пользователь — не разработчик на Windows (`T-01`). Для него «откройте Git Bash» это отдельный барьер, причём на самом первом шаге, до того как он увидел хоть какой-то результат. Именно там люди бросают.

Плюс `init-env.sh` генерирует секреты через `openssl`, который приходит с Git for Windows. То есть Git Bash всё равно нужен как зависимость — вопрос лишь в том, обязан ли человек в него **заходить**, или `.bat` вызовет его сам, как это уже делают `start.bat` и `stop.bat`.

## Что сделать

`infra/scripts/init.bat` по образцу существующих `.bat`: вызывает `init-env.sh` через bash из Git for Windows.

Проверить, что переносится на Windows корректно:
- права `600` на `.env` — на NTFS это работает иначе, чем в POSIX. Если гарантии нет, лучше сказать честно, чем притвориться;
- отказ перезаписывать существующий `.env` — защита от потери `MASTER_KEY`, она обязана работать одинаково;
- вывод с предупреждением про `MASTER_KEY` не должен потеряться при запуске двойным щелчком: окно не должно закрыться раньше, чем человек прочитает.

## Оговорка про проверку

**На Windows это не проверить с текущей машины** — разработка идёт на macOS. Возможны два пути: написать по образцу и пометить непроверенным (как уже сделано в `SETUP.md`), либо отложить до `T-01`, где прогон на чистой Windows-VM входит в DoD.

Второй путь честнее: `.bat`, написанный вслепую и никем не запущенный, создаёт видимость поддержки Windows там, где её нет.

## Границы

- Только `infra/**`.
- Логику `init-env.sh` не менять — `.bat` обязан быть тонкой обёрткой, иначе два пути разойдутся.
