## Контекст

**Первая задача фронтенда.** До сих пор `apps/web` — заглушка из `S0-01`: vite, одна страница, ничего больше. Весь проект делали backend и infra.

DoD прямой: **вход через UI по коду из `/dev/outbox`.** Не «страница верстается», а «человек открыл браузер и вошёл».

Что готово со стороны API (`S0-04`, `S0-06`, `X-03`):

```
POST /api/v1/auth/request-code  {email}       → 202 {"status":"accepted"} ВСЕГДА
POST /api/v1/auth/verify        {email, code} → 200 {id,email,display_name,timezone,day_boundary_hour} + Set-Cookie
POST /api/v1/auth/logout                      → 204
GET  /api/v1/auth/me                          → 200 те же поля | 401
GET  /api/v1/dev/outbox?limit=50              → 200 {items:[…]}  только APP_ENV=local
```

Ошибки — `{"error": {"code", "message", "details"}}`, и **схема OpenAPI теперь их описывает** (`X-03`, ADR-0004): у каждого маршрута свой набор кодов сужен enum'ом. Коды, которые встретятся здесь: `validation_error` (400, `details.fields`), `invalid_code` и `too_many_attempts` (422), `rate_limited` (429, `details.retry_after`), `unauthorized` (401), `forbidden_origin` (403).

Стек поднимается `make up`, вход проверен через vite-прокси в `S0-06`.

## ⚠️ Семантика / развилки

**1. Маршруты §9.1 — заглушки, кроме двух.**
Настоящие: `/login` и `/dev/outbox`. Остальные (`/`, `/journal`, `/journal/:id`, `/calendar`, `/accounts`, `/accounts/:id`, `/settings`) — пустые страницы с заголовком, чтобы роутер и layout были проверяемы. **Не строй Dashboard, журнал, календарь и счета** — это `S2-10`, `S2-06`, `S2-09`, `S1-11`. `/settings` — `S0-08`.

**2. ⚠️ `make types` перестаёт быть заглушкой.** Это первая настоящая генерация типов из OpenAPI, и ради неё делался `X-03`. Клиент API обязан использовать сгенерированные типы, а не рукописные интерфейсы — иначе весь `X-03` был напрасен.

**3. Все строки UI — только `src/i18n/ru.ts`.** `CLAUDE.md` §5. Хардкод строки в компоненте — ошибка, а не мелочь: структура готовится под английский в этапе 7.

**4. Тёмная тема по умолчанию, светлая переключением** (`SPEC.md` §12, §14). Выбор пользователя переживает перезагрузку.

**5. `401` → редирект на `/login`.** Обрабатывается в клиенте один раз, а не в каждом компоненте.

**6. Место под переключатель счетов в шапке — только место.** Сам переключатель это `S1-11`, там же появятся счета. Не выдумывай его поведение.

**7. `/dev/outbox` — страница только при `APP_ENV=local`.** API уже отдаёт 404 в проде; фронт не должен показывать ссылку на неё там, где её нет.

**8. Развилка по smoke-тестам — реши и обоснуй.**
`SPEC.md` §13 требует Playwright-смоук на вход и запуск в CI против `docker compose --profile local`. Полный набор оттуда (ручная сделка, рефлексия, календарь) сейчас недостижим — этих фич нет.

Рекомендую: написать смоук **только на вход**, гонять локально, а в CI **не включать** в `make ci` — установка браузеров растянет каждый прогон. Отдельная цель, которую зовут осознанно. Если видишь лучше — аргументируй.

**9. Проверка входа в настоящем браузере — за оркестратором.** Ты проверяешь тестами и сборкой; живой браузер открою я. Это разделение, а не недоверие: DoD требует человеческого прохода, и подменять его словами нельзя.

## Acceptance criteria

Сверх DoD:

- `make types` генерирует `src/api/schema.d.ts` из живой схемы; файл под контролем версий или явно нет — реши и обоснуй.
- Клиент использует сгенерированные типы; рукописных копий контракта нет.
- Ошибка `429` показывается человеку с понятным текстом и учитывает `retry_after`.
- Ошибка `invalid_code` и `too_many_attempts` различимы для пользователя: «неверный код» и «попытки исчерпаны, запросите новый» — разные состояния.
- `401` на любом запросе уводит на `/login` без «моргания» защищённой страницы.
- Тёмная тема применяется до первого кадра, без вспышки светлой.
- Ни одной строки UI вне `i18n/ru.ts`.
- `make ci` зелёный, `npm run build` зелёный.
