## Контекст

**Первая задача, где продукт запускается целиком.** До сих пор всё жило в тестах и контейнерах testcontainers. DoD прямой и проверяемый: на чистой машине `make init && make up` → вход работает, код виден в `/dev/outbox`.

Это же черновик того, что будет делать друг-тестировщик по `SETUP.md` (`S0-09`, `T-01`). У него Windows, 16 ГБ, Docker Desktop, профиль `local`.

Смержено и доступно: API с `/health`, `/version`, полным auth-флоу и `/dev/outbox`; 13 таблиц + `dev_outbox`; шифрование credentials; веб — заглушка из `S0-01` (настоящий фронт в `S0-07`).

## ⚠️ Семантика / развилки

**1. ⚠️ `X-06` закрывается здесь — иначе вход сломается у тестировщика.**

Лимит «10 запросов кода в час на IP» сейчас читает адрес TCP-соединения. Как только между браузером и API появляется прокси, все пользователи приходят с одного адреса и **лимит становится общим на всю установку**. Ревью `S0-04` прогнало: 12 пользователей с одного адреса → `[202 ×10, 429, 429]`, блокируется одиннадцатый **пользователь**.

**В профиле `local` это тоже ломается:** vite проксирует `/api` в api-контейнер, значит API видит адрес vite, а не браузера.

Обе части:
- **инфра:** `uvicorn --forwarded-allow-ips` с **конкретным** адресом прокси, не `*`. Прокси обязан ставить `X-Forwarded-For` и не давать клиенту его подделать;
- **приложение:** читать `X-Forwarded-For` только от доверенного источника; список — из окружения, в `.env.example`. Исправить порядок: проверять IP-лимит **до** инкремента счётчика по email, иначе отбитые общим лимитом запросы жгут личную квоту.

Детали и acceptance — в `docs/tickets/X-06.md`. Закрываем его этим PR.

**2. ⚠️ Сервис `worker` НЕ добавляем**, хотя `SPEC.md` §11.1 его перечисляет. arq в проекте нет — решение `S0-04`, там же обоснование. Сервис, который сразу падает, хуже отсутствующего: тестировщик увидит красный контейнер и решит, что установка сломана. Появится вместе с воркером.

**3. ⚠️ `minio` НЕ добавляем в этой задаче**, хотя §11.1 относит его к профилю `local`. Им никто не пользуется до `S2-04` (вложения), а интеграционные тесты поднимают свой через testcontainers. Лишний сервис — лишние 200+ МБ памяти и лишняя точка отказа в установке у друга. Добавим в `S2-04` вместе с потребителем.

Оба отступления от §11.1 — осознанные, цель спеки остаётся. Записать в итог.

**4. Профиль `prod` пишем, но проверить не можем.** Сервера нет, домена нет, `docs/SERVER_STATE.md` пуст. Caddy с автосертификатом без реального домена не проверяется никак. Пиши по §11.1, но **честно помечай в итоге как непроверенное** — не выдавай написанный YAML за работающий прод.

**5. `make init` не перезаписывает существующий `.env`.** Повторный запуск на рабочей установке, стирающий `MASTER_KEY`, — это потеря всех паролей счетов. Отказ с внятным сообщением, а не тихая перезапись.

**6. ⚠️ `MASTER_KEY` генерируется как base64 от 32 байт.** Приложение теперь проверяет формат при старте (`S0-05`) и откажется грузиться в проде на кривом ключе. Секреты — из криптостойкого источника, не из `$RANDOM` и не из даты.

**7. Что делает `make up` в профиле `local`.** Поднимает postgres, redis, api, web. Миграции применяет контейнер `api` при старте (`SPEC.md` §11.1), отдельного шага нет. В выводе — URL и подсказка про `/dev/outbox`, чтобы человек не искал код входа в логах.

**8. Порты.** 5173 (web), 8000 (api), 5432 (postgres), 6379 (redis) свободны на машине разработки. Занятый порт должен давать понятную ошибку, а не падение контейнера без объяснений.

**9. Чужие контейнеры `tot-284-db-1` и `favorite-db-1`** от других проектов — не трогать. Имена и volume нашего compose не должны с ними пересекаться.

## Итог (оркестратор) — готово к ревью/мержу

Реализовано, отревьюено в три круга — **approve**. PR: https://github.com/N1ikefour/tradedesk/pull/7

Закрывает `X-01` целиком и `X-06` в части, которую возможно закрыть.

### Что сделано

**Продукт запускается целиком.** DoD проверен сквозным прогоном через vite-прокси — тем же путём, которым пойдёт тестировщик:

```
GET  /                          → 200
POST /api/v1/auth/request-code  → 202
GET  /api/v1/dev/outbox         → код
POST /api/v1/auth/verify        → 200 + Set-Cookie
GET  /api/v1/auth/me            → 200
POST /api/v1/auth/logout        → 204
GET  /api/v1/auth/me            → 401
```

Весь стек — **163 МБ**. Данные переживают `make down` → `make up`. Миграций в задаче нет.

### Дизайн-развилка

- **Своя подсеть `10.87.0.0/24`.** Docker раздаёт `172.16/12`, где на машине разработки уже живут сети чужих проектов.
- **Статические адреса у прокси, а не доверие подсети.** Доверять подсети = доверять шлюзу = доверять любому запросу с хоста напрямую в API. Ревью подтвердило прогоном: с подсетью 12 подделанных адресов проходят.
- **`TRUSTED_PROXIES` принимает только точные адреса**, CIDR отвергается при старте.
- **`make init` не перезаписывает существующий `.env`** — иначе повторный запуск на рабочей установке стёр бы `MASTER_KEY`, а это все пароли счетов пользователя.
- **Сервисы `worker` и `minio` не добавлены** вопреки `SPEC.md` §11.1: arq нет, minio никем не используется до `S2-04`. Падающий или бесполезный контейнер в установке у тестировщика хуже отсутствующего. Цель спеки остаётся.
- **Профиль `prod` написан, но не проверен** — сервера и домена нет.

### Тесты / проверки

**310 тестов** (было 279). CI на GitHub — оба джоба success. `make ci-target` — Python 3.12.14.

**Три круга ревью: 6 major, 8 minor и один blocker, внесённый вторым кругом и пойманный третьим.**

Главное из найденного:
- штатный путь запуска тестировщика не работал — в `start.sh` не было перехода в корень, а двойной клик по `.bat` даёт рабочую папку `infra\scripts`;
- `make up` рапортовал успех при упавшем API: статус брался с конвейера, где это код `tee`, а живых postgres и redis хватало для «хоть один работает»;
- профиль `prod` не проверял режим приложения — со штатным `.env` поднялся бы с открытой наружу страницей `/dev/outbox`, то есть с кодами входа для любой почты;
- `.env.example` рекламировал подсети в списке доверенных прокси, а подсеть — полный обход.

### ⚠️ Блокер, который внёс сам фикс

Второй круг разнёс проверку и увеличение счётчика лимита, чтобы отбитый запрос не платил чужой квотой. **Это разорвало атомарность.** Ревью доказало прогоном: 60 предоткрытых сокетов, отпущенных по барьеру → **60 из 60 прошли, 60 кодов, 60 писем**. Лимит не ослаб, а перестал существовать — размер обхода выбирал атакующий.

Сравнение на живом Redis: атомарная операция пропускает 3, разнесённая — 57.

Закрыто Lua-скриптом: оба счётчика читаются и увеличиваются одной операцией на стороне Redis. После: 60 одновременных → 3 прошли, 57 отбиты, счётчики по 3; всплеск по часовому лимиту — ровно 10.

**Ошибка постановки была моя:** я передал предложение ревьюера «разнести проверку и инкремент» как готовое решение, не оговорив требование атомарности. Второй раз за проект — первый был с однострочной правкой рендерера логов. Предложение ревьюера — гипотеза, передавать надо требования, а не рецепт.

**Компенсирующий `DECR` отвергнут с сильным доводом:** смерть процесса между увеличением и компенсацией оставляет счётчик завышенным до конца окна — то есть возвращает исходный дефект в виде редкого, необратимого и невоспроизводимого.

### Побочная находка, спасённая guard'ом из S0-02

Новый unit-тест импортировал `app.main` на уровне модуля. Приложение собирается на импорте, `get_settings` кэширован — кэш наполнился на **сборе** тестов, раньше фикстур, и интеграционный сьют пошёл в боевую базу: `275 passed, 34 errors`.

Поймал **guard тестовой БД из `S0-02`** — механизм сработал на реальной ошибке три задачи спустя. Ревью указало, что защита держится на двух вещах сразу: guard'е и на том, что имя `postgres` с машины разработки не резолвится. Опасен случай, когда резолвится. Заведено `X-09`.

### Не проверялось / follow-up

**Не проверялось:**
- **Профиль `prod` живьём — ни разу.** Caddy, автосертификат, `web-static` и их healthcheck не исполнялись. Проверены только разбор compose, `caddy validate`, сборка образа и гейты до входа в docker.
- **Windows не проверялась ни в одном круге** — а это ОС тестировщика. `.bat` прочитаны, не исполнены; вывод про двойной клик получен эквивалентом на sh.
- Потолок всплеска (60 соединений — то, что открылось без сопротивления); поведение при нескольких воркерах uvicorn.
- `Redis Cluster`: `EVAL` с несколькими ключами требует одного слота. Сейчас один инстанс.

**Известные пробелы:**
- **Семантика лимитера живёт только под маркером `integration`, а `ci-target` их деселектит** — на целевом Python 3.12 поведение лимитера не исполняется вовсе. Дыра именно в модуле, который только что переписали. Нечинимо дёшево: testcontainers не достаёт порт из sibling-контейнера.
- `hit_all` с одинаковым ключом дважды инкрементирует дважды. Сейчас недостижимо, но функция общая.
- `except Exception` делает сломанный Lua-скрипт неотличимым от «Redis недоступен».

Ограничение названо, а не спрятано.
