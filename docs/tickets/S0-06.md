## Контекст

**Первая задача, где продукт запускается целиком.** До сих пор всё жило в тестах и контейнерах testcontainers. DoD прямой и проверяемый: на чистой машине `make init && make up` → вход работает, код виден в `/dev/outbox`.

Это же черновик того, что будет делать друг-тестировщик по `SETUP.md` (`S0-09`, `T-01`). У него Windows, 16 ГБ, Docker Desktop, профиль `local`.

Смержено и доступно: API с `/health`, `/version`, полным auth-флоу и `/dev/outbox`; 13 таблиц + `dev_outbox`; шифрование credentials; веб — заглушка из `S0-01` (настоящий фронт в `S0-07`).

## ⚠️ Семантика / развилки

**1. ⚠️ `X-06` закрывается здесь — иначе вход сломается у тестировщика.**

Лимит «10 запросов кода в час на IP» сейчас читает адрес TCP-соединения. Как только между браузером и API появляется прокси, все пользователи приходят с одного адреса и **лимит становится общим на всю установку**. Ревью `S0-04` прогнало: 12 пользователей с одного адреса → `[202 ×10, 429, 429]`, блокируется одиннадцатый **пользователь**.

**В профиле `local` это тоже ломается:** vite проксирует `/api` в api-контейнер, значит API видит адрес vite, а не браузера.

Обе части:
- **инфра:** `uvicorn --forwarded-allow-ips` с **конкретным** адресом прокси, не `*`. Прокси обязан ставить `X-Forwarded-For` и не давать клиенту его подделать;
- **приложение:** читать `X-Forwarded-For` только от доверенного источника; список — из окружения, в `.env.example`. Исправить порядок: проверять IP-лимит **до** инкремента счётчика по email, иначе отбитые общим лимитом запросы жгут личную квоту.

Детали и acceptance — в `docs/tickets/X-06.md`. Закрываем его этим PR.

**2. ⚠️ Сервис `worker` НЕ добавляем**, хотя `SPEC.md` §11.1 его перечисляет. arq в проекте нет — решение `S0-04`, там же обоснование. Сервис, который сразу падает, хуже отсутствующего: тестировщик увидит красный контейнер и решит, что установка сломана. Появится вместе с воркером.

**3. ⚠️ `minio` НЕ добавляем в этой задаче**, хотя §11.1 относит его к профилю `local`. Им никто не пользуется до `S2-04` (вложения), а интеграционные тесты поднимают свой через testcontainers. Лишний сервис — лишние 200+ МБ памяти и лишняя точка отказа в установке у друга. Добавим в `S2-04` вместе с потребителем.

Оба отступления от §11.1 — осознанные, цель спеки остаётся. Записать в итог.

**4. Профиль `prod` пишем, но проверить не можем.** Сервера нет, домена нет, `docs/SERVER_STATE.md` пуст. Caddy с автосертификатом без реального домена не проверяется никак. Пиши по §11.1, но **честно помечай в итоге как непроверенное** — не выдавай написанный YAML за работающий прод.

**5. `make init` не перезаписывает существующий `.env`.** Повторный запуск на рабочей установке, стирающий `MASTER_KEY`, — это потеря всех паролей счетов. Отказ с внятным сообщением, а не тихая перезапись.

**6. ⚠️ `MASTER_KEY` генерируется как base64 от 32 байт.** Приложение теперь проверяет формат при старте (`S0-05`) и откажется грузиться в проде на кривом ключе. Секреты — из криптостойкого источника, не из `$RANDOM` и не из даты.

**7. Что делает `make up` в профиле `local`.** Поднимает postgres, redis, api, web. Миграции применяет контейнер `api` при старте (`SPEC.md` §11.1), отдельного шага нет. В выводе — URL и подсказка про `/dev/outbox`, чтобы человек не искал код входа в логах.

**8. Порты.** 5173 (web), 8000 (api), 5432 (postgres), 6379 (redis) свободны на машине разработки. Занятый порт должен давать понятную ошибку, а не падение контейнера без объяснений.

**9. Чужие контейнеры `tot-284-db-1` и `favorite-db-1`** от других проектов — не трогать. Имена и volume нашего compose не должны с ними пересекаться.

## Acceptance criteria

Сверх DoD спеки:

- **Сквозная проверка руками, а не рассуждением:** `make init && make up` на чистом состоянии → открыть UI, запросить код, взять его из `/dev/outbox`, войти, `me` отдаёт пользователя. Приложить фактический вывод.
- `make init` на существующем `.env` — отказ, `.env` не тронут.
- Сгенерированный `MASTER_KEY` проходит гейт формата из `S0-05`.
- **`X-06`:** 12 пользователей через прокси — все получают `202`; подделанный `X-Forwarded-For` от недоверенного источника лимит не сдвигает; отбитый IP-лимитом запрос не жжёт личную квоту.
- `make down` гасит своё и не трогает чужое.
- `make ci-target` работает и печатает версию Python.
- Повторный `make up` идемпотентен, данные в volume переживают перезапуск.
- Занятый порт → понятное сообщение.
- `make ci` зелёный.
