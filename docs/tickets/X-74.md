**Первая настоящая ошибка продукта, найденная на живой Windows.** Второй прогон у первого пользователя, 16 сентября, версия `v0.2.0`.

## Что произошло

Коллектор запустился, забрал задания (`200 OK`), отправил heartbeat (`200 OK`) — **и подключился к терминалу**. Упал внутри него:

```
Traceback (most recent call last):
  File "...\collector\main.py", line 328, in _ensure_terminal
    terminal.wait_for_history()
  File "...\collector\mt5_client.py", line 225, in wait_for_history
    total = mt5.history_deals_total(start, end)
SystemError: <built-in function history_deals_total> returned a result with an exception set

The above exception was the direct cause of the following exception:
OSError: [Errno 22] Invalid argument
```

Итог в логе: `{"event": "collector.crashed", ...}` и человеку — «Коллектор аварийно остановился (SystemError), счета больше не синхронизируются».

## Причина

`apps/collector-mt5/collector/mt5_client.py`, `wait_for_history`:

```python
start = datetime(1970, 1, 2, tzinfo=UTC).replace(tzinfo=None)
end = datetime.now(UTC).replace(tzinfo=None) + timedelta(days=365)
```

`MetaTrader5` — нативное расширение; наивный `datetime` оно переводит в `time_t` средствами Windows, а те на датах у самой эпохи дают `EINVAL`. `1970-01-02` выбрана как «день после эпохи, чтобы наверняка», и на macOS это работает. **На Windows — нет.** Это ровно тот класс, ради которого и затевался прогон: строка никогда не выполнялась на целевой платформе.

⚠️ Машина пользователя в UTC+5 — смещение может участвовать в переводе, но проверять надо **на Windows**, а не рассуждать.

## Вторая половина задачи, и она важнее первой

`wait_for_history` — **необязательный шаг**. Его собственная докстрока говорит: без него первый батч уедет с неполной историей, вставка идемпотентна, данные не потеряются, счёт покажет неполный журнал до следующего тика. То есть цена пропуска — **косметика**.

А цена отказа — **полная остановка коллектора**: `collector.crashed`, все счета перестают синхронизироваться. Удобство, которое валит продукт.

Значит чинить надо оба места:

1. **Дату** — брать заведомо безопасную (например, `2000-01-01`). Окно первого синка и так ограничено `FIRST_SYNC_DAYS` (по умолчанию 3650 дней), так что до 2000 года считать нечего.
2. **Живучесть** — отказ `wait_for_history` обязан оставаться предупреждением в логе, а не аварией. Ни одна необязательная оптимизация не имеет права останавливать синхронизацию.

⚠️ Заодно пересмотреть `end = now + 365 дней`: будущая дата туда же передаётся и тем же путём переводится.

## Acceptance criteria

- На Windows коллектор проходит `wait_for_history` и доходит до синхронизации.
- Отказ этого шага **по любой причине** не останавливает коллектор: тест на подделке, где `history_deals_total` кидает, и коллектор продолжает тик.
- Мутационный контроль: вернуть падение наружу → тест краснеет.
- ⚠️ Проверяется **на Windows**. На macOS отказ не воспроизводится — библиотеки нет вовсе.

## Обход, применённый на месте

Заменить `datetime(1970, 1, 2, ...)` на `datetime(2000, 1, 1, ...)` прямо в установке пользователя, чтобы не терять прогон.
