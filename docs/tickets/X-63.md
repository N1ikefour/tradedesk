⚠️ **Найдено на живой машине первого пользователя**, 10 сентября 2026, при первом в истории проекта прогоне установки на Windows. Первый шаг, на котором прогон встал.

## Суть

Все шесть `infra/scripts/*.bat` начинаются с `where bash` и без него не идут дальше:

```
where bash >nul 2>nul
if errorlevel 1 goto :nobash
```

**Установщик Git for Windows с параметрами по умолчанию `bash` в PATH не кладёт.** Он добавляет туда только `C:\Program Files\Git\cmd`, где лежит `git.exe`, а `bash.exe` живёт в `C:\Program Files\Git\bin`.

Измерено на месте (Windows 10 22H2, сборка 19045.6332):

```
C:\Users\…>where bash
ИНФОРМАЦИЯ: не удается найти файлы по заданным шаблонам.

C:\Users\…>dir "C:\Program Files\Git\bin\bash.exe"
20.08.2026  20:47    43 368 bash.exe
```

Файл есть, PATH о нём не знает.

## ⚠️ Хуже: после установки WSL находится ЧУЖОЙ `bash`

Второе наблюдение с той же машины, через час после первого. Когда WSL2 доустановили (`X-65`), в системе появился `C:\Windows\System32\bash.exe` — запускалка Linux-подсистемы, не оболочка. Она лежит в **системном** PATH, а `C:\Program Files\Git\bin` мы дописали в **пользовательский**, и системный просматривается первым. `where bash` стал находить сначала её.

`start.bat` запустился и упал:

```
<3>WSL (10 - Relay) ERROR: CreateProcessCommon:818: execvpe(/bin/bash) failed: No such file or directory
```

WSL-заглушка попыталась выполнить `/bin/bash` внутри Linux, а дистрибутива там нет — ставили только платформу ради Docker.

**Это хуже отсутствия `bash`**, и по двум причинам. Первая: правка PATH пользователя проблему не решает **в принципе** — пользовательский PATH всегда после системного. Вторая: сообщение об ошибке не имеет никакого отношения к делу, и человек без нашей подсказки не свяжет его ни с Git, ни с PATH.

Обошли запуском мимо `.bat`: Git Bash → `sh infra/scripts/start.sh`.

**Отсюда следует, что вариант 1 ниже — единственный настоящий:** искать `bash` по известному пути обязательно, потому что верить `where bash` нельзя не только когда он молчит, но и когда он отвечает.

## Почему это блокер, а не неудобство

`SETUP.md` §1 обещает: Git for Windows «приносит `bash`, `sh` и `openssl`: на них написаны скрипты запуска». Обещание неверно ровно в той части, которая нужна: `bash` приносится, но недостижимо.

Человек, идущий по инструкции, упирается в это **на шаге 4** — «Запустить приложение», — и видит «Не найден bash. Поставь Git for Windows», уже поставив Git. Сообщение при этом технически верное и совершенно бесполезное: оно советует сделать то, что уже сделано.

Обошли на месте руками: добавили `C:\Program Files\Git\bin` в пользовательский PATH.

## Что сделать — по убыванию предпочтения

**1. Скрипты сами находят `bash` по известному пути и НЕ пользуются `where bash`.** Проверять `%ProgramFiles%\Git\bin\bash.exe`, затем `%ProgramFiles(x86)%\Git\bin\bash.exe`, затем `%LOCALAPPDATA%\Programs\Git\bin\bash.exe` (установка per-user) — и звать по полному пути.

⚠️ **`where bash` нельзя использовать даже как запасной вариант**: после установки WSL он находит `System32\bash.exe`, и запуск через неё падает с сообщением про `/bin/bash`, никак с нами не связанным. Если уж брать результат `where`, то отбрасывать всё, что лежит в `System32`.

⚠️ Тогда же поправить и сообщение об отказе: «поставь Git» неверно, когда Git стоит. Правильное — «Git найден, но `bash` из него недоступен; ожидался в …».

**2. Добавить в `SETUP.md` §1 проверку `where bash`** с готовой правкой PATH — как страховку, даже если пункт 1 сделан.

⚠️ **Не советовать третий вариант на экране PATH установщика Git** («Use Git and optional Unix tools from the Command Prompt»): он кладёт в PATH ещё и `usr\bin`, где юниксовые `find` и `sort` подменяют одноимённые команды Windows на всей машине. Мы добавляли только `bin` намеренно.

## Acceptance criteria

- `start.bat` на машине, где Git установлен по умолчанию, работает без правки PATH руками.
- `start.bat` работает на машине с установленным WSL, где `where bash` отдаёт `System32\bash.exe` первым.
- Отказ при по-настоящему отсутствующем Git называет, где искали.
- Проверка есть в `SETUP.md` и в `docs/collector-windows-checklist.md`, блок 0.
- ⚠️ Проверить по-настоящему можно только на Windows — сказать это явно.
