## Контекст

Первая задача проекта. В репозитории нет ни одного приложения — только документы и каркас процесса. От этого тикета зависит всё остальное: `make lint` и `make test` — команды, которыми проверяются все последующие задачи, а CI — гейт перед каждым мержем.

Структура — `SPEC.md` §2.1, конвенции — §2.2, разрешённые зависимости — §2.3.

## ⚠️ Семантика / развилки

Решения приняты оркестратором до старта, чтобы агент не выбирал молча. Если какое-то мешает — эскалация, а не обход.

**1. Makefile содержит все команды из `CLAUDE.md` §4, но работают только `lint`, `test`, `help`.**
`init`, `up`, `down`, `migrate`, `revision`, `types` — заглушки, печатающие «реализуется в S0-06 / S0-02 / S0-03» и выходящие с ненулевым кодом. Причина: список команд задокументирован и им будут пользоваться; `make up`, падающий с «No rule to make target», хуже осмысленного сообщения. Реализуются в своих задачах.

**2. Приложения создаются пустыми — ровно настолько, чтобы CI был зелёным.**
- `apps/api`: `pyproject.toml`, пакет `app/` с `__init__.py`, `tests/` с одним тривиальным тестом (pytest без тестов выходит с кодом 5 и красит CI). **`main.py`, config, БД — это S0-02, здесь их нет.**
- `apps/web`: `package.json`, `vite.config.ts`, `tsconfig.json` (strict), eslint + prettier, `index.html`, минимальный `src/main.tsx`, рендерящий заглушку. **Роутер, layout, тема, генерация типов — это S0-07, здесь их нет.**
- `apps/collector-mt5`: `pyproject.toml`, пакет `collector/` с `__init__.py`, `collector.env.example` по `SPEC.md` §8.1. **Код коллектора — S1-08.**
- `packages/shared-schemas/`, `packages/mql5-ea/`, `infra/` — директории с `.gitkeep`. Содержимое — S1-01, этап 4, S0-06/T-02.

**3. Runtime-зависимости в `pyproject.toml` не объявляются — только dev-инструменты** (ruff, mypy, pytest, pytest-asyncio). Причина: fastapi/sqlalchemy/alembic нужны с S0-02, а объявленные, но неиспользуемые зависимости замедляют CI и создают иллюзию, что каркас приложения есть. Объявляются в задаче, которая их первой использует, из списка `SPEC.md` §2.3.

**4. ⚠️ `MetaTrader5` НЕ попадает в основные зависимости коллектора.** Пакет существует только под Windows — на Linux-раннере CI установка упадёт. Вынести в optional-dependencies (extras) или обусловить маркером окружения `sys_platform == 'win32'`. Это самая вероятная причина красного CI в этом тикете.

**5. `mypy --strict` настраивается сразу для `domains/ingest` и `domains/analytics`** (`SPEC.md` §2.2), хотя этих модулей ещё нет — через overrides в конфиге. Причина: настройка, отложенная «на потом», не появляется никогда.

**6. Pre-commit обязан включать `detect-private-key`** и проверку, что `.env` не коммитится. Секреты в истории — необратимая проблема (`DEVELOPER_MANUAL.md` §11.1).

## Acceptance criteria

Сверх DoD спеки («CI зелёный на пустых приложениях»):

- `make lint` и `make test` проходят локально и в CI, и это **одни и те же команды** — расхождение локального и CI-прогона считается багом инфраструктуры.
- CI состоит из двух независимых джобов: `api` (ruff + mypy + pytest на Python 3.12) и `web` (eslint + prettier --check + tsc + vite build на Node 20+). Триггеры: `push` в `main` и `pull_request`.
- `make help` печатает список команд с пояснением, какие ещё не реализованы.
- Ни один секрет и ни один `.env` не попадает в дифф.
- `git status` чист после прогона всех команд: артефакты сборки и кэши покрыты `.gitignore`.

## ⚠️ Ограничение верификации на машине разработки

Проверено оркестратором 2026-09-03 на машине принципала (macOS):

| Инструмент | Состояние |
|---|---|
| Python 3.12 | **отсутствует** (есть только 3.14) |
| `uv`, `pyenv`, `poetry`, `pipx`, `pre-commit` | **отсутствуют** |
| Docker daemon | **не запущен** |
| Node v22.23.1, npm, npx | есть |

Следствия для этого тикета:

- Python-инструменты ставятся в локальный venv на **3.14**, а не на целевой 3.12. Локальный зелёный прогон — не доказательство зелёного CI. **Авторитетный прогон — GitHub Actions на 3.12.**
- `pre-commit` ставится в тот же venv; его хуки прогоняются командой, а не через git-хук.
- Docker в этом тикете не нужен.
- В итоге обязательно разделить: что проверено локально (и на какой версии Python), что проверено в CI, что не проверялось.
