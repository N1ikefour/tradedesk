Найдено при доработке `S1-08`.

## Суть

`infra/scripts/ci-target.sh` — прогон на **целевом** Python 3.12 в контейнере, заведённый в `X-01` ровно потому, что на машине разработки стоит 3.14 и локальный зелёный прогон ничего не доказывает.

Для коллектора он делает только `ruff` и `mypy`. **Его 281 тест на 3.12 не гоняются.**

`make ci` их гоняет (цель `test-collector` добавлена в `S1-08`), но на 3.14. То есть про поведение коллектора на той версии, которую мы объявили целевой, гейт не знает ничего.

## Почему это не «на всякий случай»

Коллектор — **единственный код проекта, который поедет на чужую машину и который мы не можем проверить сами**. Его версия Python там неизвестна: первый пользователь поставил 3.14 через новый Python Install Manager, а пакет требует `>=3.12`, и `S1-10` обязан назвать версию явно (`SPEC.md` §12).

Значит расхождение версий здесь не теоретическое: у нас 3.14, целевая 3.12, у пользователя может быть третья. Единственная защита — гонять тесты на всех, что мы объявили поддерживаемыми.

Автор `S1-08` прогнал 281 тест в `python:3.12-slim` **руками** и получил зелёное. Ручной прогон не повторяется.

## Что сделать

Добавить `pytest` для `apps/collector-mt5` в `ci-target.sh` рядом с существующими `ruff` и `mypy`.

Проверить: зависимости коллектора в контейнере ставятся (`pip install -e "apps/collector-mt5[dev]"`), а `MetaTrader5` в них **не входит** и входить не должен — пакет ставится только на Windows, а тесты работают на подделках.

⚠️ Заодно решить, гонять ли `test-api` целиком: сейчас `ci-target` берёт unit-тесты, а интеграционные пропускает — testcontainers не достаёт опубликованный порт из sibling-контейнера (`CLAUDE.md` §4). Для коллектора этой преграды нет: у него нет ни базы, ни сети.
