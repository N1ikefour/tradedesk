Задачи нет в `SPEC.md` §12 — описание полное по `DEVELOPER_MANUAL.md` §8.3.

## Что случилось

Оркестратор правит доску, тикеты и документы **прямо в `main`** — так требует `docs/WORKFLOW.md` §1. Эти коммиты не проходят через PR, а значит **не проходят ни через какой гейт**: ни локальный `make ci`, ни GitHub Actions на ветке.

5 сентября 2026 скрипт оставил в `docs/tickets/X-07.md` лишнюю пустую строку в конце. Хук `end-of-file-fixer` в `pre-commit` на неё падает.

Дальше сработала механика, которую никто не держал в голове: **CI гоняет `pre-commit run --all-files` по всему дереву, а не по диффу ветки**. Сломанный документ в `main` начал валить сборку **чужих задач** — упал PR #15 с нормализатором, где к этому файлу никто не притрагивался.

## Почему это стоит починить механикой, а не внимательностью

**Диагностика уводит в сторону.** Выглядит как «нормализатор не прошёл CI». Причина — в документе из соседнего коммита, к задаче отношения не имеющего. Автор PR будет искать у себя.

**Ломается не тот, кто ошибся.** Свой коммит проходит молча, падает следующий PR любого автора. Обратная связь приходит не туда.

**Внимательность тут не работает** — правки идут скриптами, руками их никто не перечитывает, и в этом весь смысл.

## Повторилось, и хуже

**6 сентября 2026.** Скрипт `scripts/export_mt5_deals.py` уехал в `main` через `git add -A` вместе с коммитом тикета. `ruff format` в CI захотел его переформатировать — и сборка упала на ветке `X-25`, где к скрипту никто не притрагивался.

Первый раз (5 сентября) это был markdown и хук `end-of-file-fixer`. Теперь Python и `ruff format`. **Класс тот же, цена выше:** правок кода в `main` мимо гейта будет больше, чем правок текста.

Обнажилась и вторая половина проблемы: **в основном чекауте нет `.venv` вообще** — `make install` там никогда не запускался, потому что вся работа идёт в worktree. То есть прогнать хуки перед коммитом в `main` физически нечем, даже если помнить.

Значит вариант «А» из списка ниже (поставить хуки локально) не работает без предварительного `make install` в основном чекауте — а это ещё одно окружение, которое надо поддерживать.

## Варианты

**А. Хуки на `main` локально.** `make hooks` ставит `pre-commit install`, и тогда коммит в `main` пройдёт через те же хуки. Но это защищает только машину, где хуки поставлены, и молча не работает там, где нет.

**Б. Отдельный лёгкий workflow на push в `main`** — только `pre-commit run --all-files`, без тестов и сборки. Секунды, ловит ровно этот класс. Не мешает основному CI.

**В. Не пускать доковые коммиты в `main` напрямую** — вести их через PR. Честно, но противоречит `WORKFLOW` §1: доска обязана обновляться сразу, иначе перестаёт быть источником истины.

Б выглядит правильным: закрывает механикой, не меняет процесс и не полагается на настройку чужой машины.

## Acceptance criteria

- Сломанный markdown, запушенный в `main`, ловится **до** того, как уронит чужой PR.
- Сообщение об ошибке указывает на настоящую причину, а не на ветку, которая просто оказалась следующей.
- Основной CI не замедлился.
