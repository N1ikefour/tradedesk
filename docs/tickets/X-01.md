## Контекст

Целевая версия проекта — Python 3.12 (`SPEC.md` §2.2). На машине разработки её нет, есть только 3.14. Из-за этого в `S0-01` и `S0-02` каждый итог нёс оговорку: «локальный зелёный прогон не доказывает зелёный CI, авторитетная проверка — GitHub Actions». Цикл обратной связи получался длиной в пуш.

В `S0-02` оркестратор проверил гипотезу вручную: `docker run --rm -v "$PWD":/w -w /w python:3.12-slim` с установкой `apps/api[dev]` и прогоном ruff, mypy и unit-тестов. Работает и **сразу дало результат** — на 3.12 всплыло срабатывание `RUF001` на русских сообщениях об ошибках, которого хостовый прогон не показывал бы до самого CI.

Нужно превратить ручную команду в цель `Makefile`, чтобы «проверено на целевой версии» перестало зависеть от того, что у кого установлено, и от импровизации оркестратора.

## Что сделать

Цель `make ci-target` (имя обсуждаемо): тот же гейт, что `make ci`, но внутри контейнера `python:3.12-slim`.

- Смонтировать репозиторий, поставить `apps/api[dev]` и `apps/collector-mt5[dev]`, прогнать `ci-api`.
- Использовать именованный volume под кэш pip — без него переустановка зависимостей на каждый прогон занимает минуты и упирается в таймауты.
- Версия образа берётся из одного места с CI: сейчас `3.12` продублирована в `.github/workflows/ci.yml` и будет в `Makefile`. Расхождение этих двух чисел — тот самый класс багов, ради которого цель и заводится.
- `make help` обновить.

## ⚠️ Семантика / развилки

**1. Интеграционные тесты внутри контейнера.** testcontainers поднимает контейнеры через Docker-сокет; изнутри контейнера его по умолчанию нет. Варианты: (а) `ci-target` гоняет только линтеры и unit-тесты, интеграционные остаются на хосте; (б) монтировать `/var/run/docker.sock` внутрь. **Рекомендация — (а):** проще, без привилегий, и покрывает то, ради чего цель заводится — поведение линтеров, тайпчекера и кода на 3.12. Интеграционные тесты проверяют SQL и сеть, а не версию интерпретатора.

**2. `ci-target` не заменяет `make ci` и не становится вторым источником правды.** Гейт перед PR остаётся `make ci` (`CLAUDE.md` §6). `ci-target` — дополнительная проверка перед пушем, когда цена красного CI высока. Если целей станет две равноправных, они разъедутся.

**3. Авторитетным прогоном остаётся GitHub Actions.** `ci-target` сокращает цикл обратной связи, но не заменяет CI: там своё окружение, свои кэши и джоб web.

**4. Docker обязателен.** Цель должна падать с внятным сообщением, когда демон не запущен, а не с невнятной ошибкой сокета.

**5. Чужие контейнеры на машине неприкосновенны** (`tot-284-db-1`, `favorite-db-1` от других проектов). Цель не должна делать `docker system prune` и трогать чужие volume'ы.

## Acceptance criteria

- `make ci-target` на машине с Docker проходит зелёным и реально исполняется на Python 3.12 — версия печатается в выводе.
- Повторный прогон заметно быстрее первого (кэш pip работает).
- Без запущенного Docker — внятное сообщение и ненулевой код возврата.
- Версия Python задана в одном месте; расхождение с `ci.yml` невозможно или заметно.
- `make help` описывает цель и говорит, что она дополняет `make ci`, а не заменяет.
- Цель не трогает чужие контейнеры и не делает глобальных очисток Docker.
- Документация: строка в `CLAUDE.md` §4 и в `docs/DEVELOPMENT.md`.
