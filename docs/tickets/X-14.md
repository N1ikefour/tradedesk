## Контекст

Найдено агентом `S0-08` (наступил) и подтверждено ревью чтением compose.

`docker-compose.yml` у сервиса `web`: `[ -x node_modules/.bin/vite ] || npm ci`. То есть зависимости ставятся **только если в томе ещё нет vite**. Том `td_web_node_modules` создаётся один раз и живёт дальше сам по себе.

Следствие: как только кто-то добавляет пакет в `package.json`, в контейнере его нет. В `S0-08` после добавления `date-fns` контейнер отдавал `Failed to resolve import "date-fns-tz"`, и первый прогон смоука упал на пустой странице входа — при том, что локально всё собиралось.

Лечится вручную: `docker compose exec web npm ci && docker compose restart web`. Но об этом надо знать, а сообщение об ошибке об этом не говорит.

**Ловушка сработает у каждого следующего, кто добавит пакет.** И у тестировщика после `update` — если обновление принесёт новую зависимость фронта, он увидит пустую страницу без объяснения.

## Что сделать

Сделать так, чтобы состав установленного соответствовал `package-lock.json`.

Направления:
1. **Сверять lock-файл с установленным** — например, хранить в томе хеш `package-lock.json` и запускать `npm ci` при расхождении. Дёшево и автоматически.
2. Отдельная цель в `Makefile` для переустановки зависимостей контейнера — надёжно, но требует, чтобы человек знал, когда её звать.
3. Не держать `node_modules` в томе вовсе — но тогда каждый старт стека переустанавливает зависимости, а на Windows это минуты.

## ⚠️ Семантика / развилки

- **Проверять надо на реальном сценарии**, а не на свежем томе: добавить пакет в `package.json`, поднять стек с уже существующим томом, убедиться, что пакет доехал.
- Первый `npm ci` на Windows с bind-mount — это минуты; решение не должно превращать каждый `make up` в такое ожидание.
- Если выбран путь с хешем, помнить, что `package-lock.json` меняется и от несвязанных правок — лишняя переустановка не страшна, пропущенная страшна.

## Тот же класс для Python-worktree

Найдено при перебазировании `S1-06` на `main` с влитым `S1-01`. Пакет `jsonschema` появился в dev-зависимостях в `S1-01`; `.venv` соседнего worktree создавался раньше, и перебазирование принесло туда тест, который этот пакет импортирует.

`make ci` упал с `ModuleNotFoundError: No module named 'jsonschema'` — то есть выглядел как сломанный код, хотя код был цел. Лечится `make install`.

Симптом тот же, что у npm-зависимости в контейнере: **новая зависимость не доезжает до уже существующего окружения**, а сообщение об ошибке указывает на импорт и уводит от настоящей причины. Стоит решать одним движением — например, проверкой актуальности окружения в начале `make ci` или внятной подсказкой в тексте ошибки.

Из-за этого расширено и название тикета: речь не только про npm и не только про контейнер.

## Acceptance criteria

- Добавление пакета в `package.json` приводит к его появлению в контейнере без ручных команд.
- Повторный `make up` без изменений зависимостей не переустанавливает их заново.
- Проверено на существующем томе, а не на пустом.
- Если переустановка всё же нужна руками — сообщение об ошибке называет команду.
