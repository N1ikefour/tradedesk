# X-15 — Линтер ловит кнопку в форме без `type`

**Статус:** In Progress
**Роль:** frontend
**Ветка:** `fix/X-15-button-type`
**Источник:** третья переповерка `S0-08`

## Зачем

В `S0-08` кнопка «Повторить» стояла внутри `<form>` без `type`. По HTML это `type="submit"`, поэтому нажатие ради перезагрузки списка таймзон **отправляло форму** — уходил `PATCH /users/me`, которого человек не просил. По той же причине Enter в поле имени уходил в «Повторить», а не в «Сохранить»: неявная отправка выбирает первую submit-кнопку разметки.

Дефект прошёл **два круга независимого ревью**. Тест на этот путь существовал — ходил по сценарию «список зон упал, поле имени всё равно работает» — и не утверждал, что запрос не ушёл.

Класс дефекта неприятен тем, что **невидим в диффе**: отсутствие атрибута не подсвечивается. Соседняя «Отмена» `type` задавала, у «Повторить» забыли, и глазами это не ловится.

Проверено, что тесты этот класс не удерживают: снятие `type="button"` с обеих кнопок в `login-page.tsx` оставляет все 12 тестов файла зелёными. Поведенческий тест туда написать не на чем — лишний submit там безвреден (проверка длины кода плюс очистка поля), — то есть **тестами класс не закрывается в принципе**. Значит закрывать его должен линтер.

## Что сделать

Правило, при котором JSX-кнопка без явного `type` — ошибка линта. Покрыть и `<button>`, и `<Button>` (`components/ui/button.tsx` рендерит голый `<button {...props}>`, то есть наследует дефолт).

## Два пути — выбрать с обоснованием

**А. `eslint-plugin-react`, правило `react/button-has-type`.** Готовое, поддерживаемое, ровно про это. Цена — новая зависимость вне `SPEC.md` §2.3. **Принципал её одобрил.**

**Б. Встроенный `no-restricted-syntax` с AST-селектором.** JSX присутствует в AST, `typescript-eslint` отдаёт узлы `JSXOpeningElement`, esquery поддерживает `:has()` и комбинатор `>`. Ноль новых зависимостей.

Набросок, **не готовое решение — проверить и доработать**:

```js
selector: 'JSXOpeningElement[name.name=/^(button|Button)$/]:not(:has(> JSXAttribute[name.name="type"]))'
```

**Предпочтение — Б, если она работает надёжно.** Причина: по `CLAUDE.md` §8 новая зависимость требует решения принципала, а отсутствие зависимости не требует ничего; плюс `eslint-plugin-react` тянет за собой заметное дерево ради одного правила.

Но выбор за реализующим. Если Б окажется хрупкой — назвать конкретно, чем (ложные срабатывания, необходимость `> `-комбинатора, поведение с `{...props}`, кнопка из переменной, `React.createElement`), — и брать А. Обоснование выбора идёт в итог тикета.

## Обязательное доказательство

Правило без доказательства бесполезно ровно так же, как тест без утверждения — а именно это и породило тикет.

- **Мутация:** снять `type="button"` с «Повторить» в `settings-page.tsx` → `make lint` **обязан упасть** с внятным сообщением. Показать вывод.
- **Обратная проверка:** на нетронутом дереве `make lint` зелёный, ложных срабатываний нет.
- Пройти по всем существующим кнопкам: где `type` придётся дописать — дописать. Это и есть польза, а не побочный ущерб.
- Сообщение правила должно объяснять **почему**, а не «добавьте type». Человек, который его увидит, должен понять, что кнопка без типа отправляет форму.

## Границы

- Только `apps/web/**`.
- Поведение приложения не меняется: если правило требует дописать `type` там, где дефолт и так верен, — дописать явно, но `type="submit"` у настоящих submit-кнопок сохранить.
- Если выбран путь А — обосновать зависимость в PR и **предложить** правку `SPEC.md` §2.3 текстом, не вносить её молча.
