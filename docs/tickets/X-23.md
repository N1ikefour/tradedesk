## Что найдено

Ревью `S1-01` прогнало одно и то же тело через опубликованный `ingest-deals.schema.json` и через модель сервера. Семь случаев, где **файл отвергает, а сервер принимает**:

| значение | файл | сервер |
|---|---|---|
| `profit: "1e5"` | отвергает | принимает → `1E+5` |
| `profit: " 1.5"` | отвергает | принимает → `1.5` |
| `profit: "1_000"` | отвергает | принимает → **`1000`** |
| `profit: "\t2.5\n"` | отвергает | принимает → `2.5` |
| `account_id: "{0199a5c1-…}"` | отвергает | принимает |
| `account_id` без дефисов | отвергает | принимает |
| `account_id: "urn:uuid:…"` | отвергает | принимает |

Это **перекос в безопасную сторону**: отправитель, прошедший валидацию по файлу, отказа не получит. Поэтому не блокировало мерж `S1-01`.

## Почему всё-таки стоит починить

`"1_000" → 1000` и `"\t2.5\n" → 2.5` — это **тихая переинтерпретация денег**. Ровно тот класс, ради которого в этом же контракте стоит `extra="forbid"` с доводом «тихо потерянные деньги дороже громкой ошибки». Подчёркивание в числе не приходит от здорового сериализатора — оно приходит от сломанного, и принять его молча значит записать в базу число, которого отправитель не имел в виду.

`"1e5"` — отдельный случай: он вероятнее всего прилетит от чужого сериализатора, и сейчас это тот редкий разворот, когда отправитель, проверившийся по файлу, видит красное, а сервер молча берёт.

## Направление решения

**Ужесточать сервер, а не ослаблять файл.** Файл описывает то, что мы хотим принимать; сервер сегодня ленивее собственного контракта, и это лень pydantic по умолчанию, а не решение.

Отвергать: экспоненциальную запись, пробельные символы по краям, подчёркивания, неканонические формы UUID.

⚠️ **Осторожно с широкими средствами.** `strict=True` целиком поставить нельзя — он убьёт путь «JSON-число → `Decimal`», на котором держится точность (`S1-01`). Ужесточение должно быть точечным.

Если решение будет обратным — ослабить файл под сервер, — тогда в описание схемы нужен встречный раздел «что файл отвергает, а сервер принимает». Молчать про расхождение нельзя в любую сторону.

## Обязательное доказательство

Дифференциальный прогон: одно тело через `Draft7Validator` по опубликованному файлу и через модель. Расхождений быть не должно ни в одну сторону, кроме пяти зазоров, которые уже перечислены в описании самого файла и выражены в draft-07 быть не могут.

Мутация на каждое ужесточение.
