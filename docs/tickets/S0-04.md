## Контекст

Первый живой пользовательский флоу. До сих пор приложение отвечало только на `/health` и `/version`.

Смержено и доступно: модель данных (`S0-03`, таблицы `users`, `otp_codes`, `sessions` уже есть), формат ошибок `core/errors.py`, structlog со скрабом секретов (`X-02`), env-guard прода, Redis-клиент, guard тестовой БД.

## ⚠️ Семантика / развилки

Решено оркестратором до старта. Мешает — эскалация, не обход.

**1. ⚠️ `sessions.id` — `uuid4()`, НЕ `uuid7()`.**
Агент `S0-03` намеренно оставил колонку без `default` и эскалировал выбор сюда. `uuid7` публикует время создания сессии в открытом виде, а это значение cookie. `uuid4()` в CPython берёт байты из `os.urandom` — криптостойкий, 122 бита энтропии, отдельная зависимость не нужна. **Не используй `app/core/ids.py`** — он для пользовательских сущностей.

**2. ⚠️ Таблицы `dev_outbox` нет в модели данных.**
`SPEC.md` §4 её требует, §12 включает в DoD, но в разделе 3 её нет — `S0-03` создал 13 таблиц, и этой среди них не было. Схема не описана нигде. Значит нужна **своя миграция** в этой задаче.

Предложенный минимум: `id uuid pk`, `to_email text not null`, `subject text not null`, `body_text text not null`, `body_html text`, `created_at timestamptz not null default now()`. Индекс по `created_at desc` — страница читает последние. Если считаешь, что чего-то не хватает, — скажи до реализации.

**3. ⚠️ Отправка письма — синхронная, arq НЕ заводим.**
`SPEC.md` §10 описывает `send_email` как задачу arq с тремя ретраями, а `cleanup_otp` — как cron каждые 10 минут. Воркера в проекте нет, в DoD `S0-04` он не значится, и поднимать всю фоновую инфраструктуру ради письма, которое `ConsoleEmailProvider` пишет в лог и в таблицу мгновенно, — работа нескольких задач вперёд.

Здесь: отправка синхронная **за интерфейсом `EmailProvider`**, чтобы переезд на arq не менял места вызова. Цель §10 остаётся, отступление осознанное.

Просроченные коды: вместо cron — отбрасывать по `expires_at` при проверке. Чистка таблицы придёт с воркером.

**4. ⚠️ НЕ логировать сырой `exc.errors()` — условие из ревью `X-02`.**
Для пофилдовой ошибки валидации присланное значение лежит в `input` **скаляром, без собственного имени**, поэтому код входа напечатается целиком мимо скраба. `core/errors.py` уже оставляет только `msg` — не ослабляй это и не добавляй логирование `details`.

Ключи `code`, `otp`, `otp_code`, `verification_code`, `email` режутся цензором на любой глубине (`X-02`). Если нужно соотносить записи по пользователю — логируй `user_id` или маскированную форму под **другим** ключом, осознанно.

**5. Ответ на `request-code` — всегда `202`**, независимо от существования email. Иначе эндпоинт превращается в перечислитель зарегистрированных адресов.

**6. Хранение кода — только хеш.** `code_hash = sha256(code + OTP_PEPPER)`, колонка уже есть. Сам код не хранится и не логируется нигде, включая `dev_outbox` — туда попадает текст письма, и это осознанно: таблица работает только при `APP_ENV=local`.

**7. Проверка `Origin` на мутирующих запросах** (`SPEC.md` §4, CSRF). Отдельный CSRF-токен не нужен: SPA и API на одном origin, `SameSite=Lax`. Не забудь, что это влияет на все будущие POST, а не только на auth.

**8. `/users/me` — это `S0-08`.** Здесь только `GET /api/v1/auth/me`. `PATCH` не делать.

**9. `GET /api/v1/dev/outbox`** — читающий эндпоинт для страницы `/dev/outbox` из `S0-07`. Доступен **только при `APP_ENV=local`**, в проде отвечает 404. Сама страница — фронтенд, не эта задача.

## Acceptance criteria

Сверх DoD спеки:

- `POST /auth/request-code` отдаёт `202` и на существующий, и на несуществующий email; ответы неразличимы по телу и по времени в разумных пределах.
- Rate-limit: 3 запроса / 10 мин на email, 10 / час на IP; при превышении `429` с `retry_after`. Оба лимита покрыты тестами.
- Неверный код ×5 → код погашен; шестая попытка с **верным** кодом не пускает.
- Верный код → создаётся `users` при отсутствии, создаётся `sessions`, ставится cookie `td_session` с `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=30d`; `Secure` только при `APP_ENV=prod`.
- Скользящее продление: `last_seen_at` старше суток → обновляется и продлевается `expires_at`. Тест на обе ветки.
- Просроченный код не принимается.
- `GET /auth/me` без cookie → `401` в формате §5.1; с cookie → поля из §4.
- `logout` удаляет сессию; повторный `me` → `401`.
- Мутирующий запрос с чужим `Origin` отклоняется.
- **Ни код, ни хеш, ни email не появляются в логах** — тест на реальном выводе, не на глаз.
- Миграция `dev_outbox`: `upgrade head` и `downgrade base` проходят.
- `make ci` зелёный, прогон на целевом Python 3.12.

## Итог (оркестратор) — готово к ревью/мержу

Реализовано, отревьюено независимым ревьюером в три круга — **approve**. PR: https://github.com/N1ikefour/tradedesk/pull/5

### Контракт для S0-07

```
POST /api/v1/auth/request-code  {email}       → 202 {"status":"accepted"} ВСЕГДА
POST /api/v1/auth/verify        {email, code} → 200 {id,email,display_name,timezone,day_boundary_hour} + Set-Cookie
POST /api/v1/auth/logout                      → 204 всегда, идемпотентно
GET  /api/v1/auth/me                          → 200 те же поля | 401
GET  /api/v1/dev/outbox?limit=50              → 200 {items:[…]}, только APP_ENV=local
```

Ошибки: `400 validation_error` (`details.fields`), `422 invalid_code`, `422 too_many_attempts`, `429 rate_limited` (`retry_after` + заголовок `Retry-After`), `403 forbidden_origin`, `401 unauthorized`.

Cookie: `td_session=<uuid4>; HttpOnly; Max-Age=2592000; Path=/; SameSite=lax`, плюс `Secure` при `APP_ENV=prod`. Скользящее продление при `last_seen_at` старше суток.

### Дизайн-развилка

- **`sessions.id` — `uuid4`, не `uuid7`.** Значение уезжает в cookie, а v7 публикует время создания сессии. `uuid7` остаётся для `users.id`, где важна локальность вставок в индекс.
- **Отправка синхронная** за интерфейсом `EmailProvider`. `SPEC.md` §10 описывает arq с ретраями, но воркера нет и в DoD он не значится. Цель §10 остаётся, переезд не потребует менять места вызова.
- **Rate-limit fail-closed.** Изначально было fail-open с аргументом «перебор держит счётчик попыток в БД». Ревью прогоном показало, что аргумент верен только на один код: счётчик ограничивает 5 попыток на код, а выпуск новых кодов не ограничивало ничто — цикл «запросить → сжечь 5 → повторить» прошёл 6 раундов без сопротивления, плюс 25 писем на чужой адрес. Теперь при мёртвом Redis письмо не отправляется, `429` с `retry_after: 60`. `verify`, `me`, `logout` от Redis не зависят.
- **Текст ошибки БД не печатается вообще.** Ревьюер предложил `hide_parameters=True`; автор проверил и показал, что этого мало — Postgres кладёт `DETAIL: Failing row contains (…)` и `Key (email)=(…) already exists` в текст самого исключения, флаг его не трогает. Вместо traceback — структурный портрет: тип, `SQLSTATE`, параметризованный SQL. У прочих исключений traceback сохранён, на это отдельный тест.
- **Новый домен `app/domains/mail/`** — утверждён принципалом, `SPEC.md` §2.1 дополнена (v1.2).
- **`ConsoleEmailProvider` не пишет тело письма и адрес в лог**, хотя §4 говорит «в лог + в таблицу». Требование DoD об отсутствии кодов в логах сильнее; факт отправки логируется, код читается из `dev_outbox`.
- **`422` для `invalid_code` и `too_many_attempts`**, а не 400: 400 в словаре занят `validation_error`. Ревьюер проверил, что разделение не даёт сигнала атакующему — `too_many_attempts` возможен ровно один раз, дальше код погашен и ответ снова `invalid_code`.

### Тесты / проверки

**185 тестов** (на `main` был 81), из них 50 интеграционных на настоящих Postgres 16 и Redis 7.

| Проверка | Результат |
|---|---|
| CI на GitHub | **оба джоба success** |
| Целевой Python 3.12 | ruff, format, mypy 51 файл, 135 unit |
| `make ci` на хосте | зелёный, 185 passed |
| Миграции | `upgrade head` → `downgrade base` → `upgrade head` → `downgrade -1` → `upgrade head` |

**Проверено прогоном, а не чтением:**
- **Перечисление пользователей закрыто:** тело, статус и набор заголовков совпадают, тайминг 2.88 против 2.81 мс на 15 замерах.
- **Обход лимита попыток закрыт:** 5/10/20 одновременных `verify` с неверным кодом дают `attempts=5` и погашенный код. Без `FOR UPDATE` — `attempts=3` и следующий верный код пускает внутрь. Конкурентный тест стабилен: 10 прогонов подряд, 5 со случайным порядком.
- **Подмены сессии нет:** три повторных входа дают три разных идентификатора.
- **Просроченная сессия отвергается и не продлевается** — поля в БД не меняются.
- **`/dev/outbox` в проде отсутствует** и в маршрутах, и в OpenAPI.
- **Логи чистые на обоих путях** — и на успешном, и на ошибке БД, включая `unique_violation` по `users.email`.

### Три вещи, которые нашлись только потому, что проверяли, а не рассуждали

1. **`hide_parameters` закрывал половину** — предложение ревьюера, отвергнутое автором с доказательством.
2. **Логирование сбрасывалось после каждой миграции.** `alembic/env.py` вызывал `fileConfig`, а `alembic.ini` задаёт root `WARNING` и вывод в stderr — то есть любой тест, читающий stdout и утверждающий «секрета нет», мог зеленеть на **пустом буфере**. Дефект приехал из `S0-03` и жил три задачи. Первый фикс лечил флаг и симптом не снимал: ревьюер замерил состояние логгера и показал это. Вторая попытка автора держалась на утверждении «конфиг нужен, иначе SQLAlchemy печатает каждый запрос» — он проверил и опроверг его сам, после чего убрал вызов целиком.
3. **Старый тест на эту регрессию был плох, а не просто неполон.** Автор собрал прежний ассерт временным тестом и прогнал против состояния «починен только флаг» — тест зеленел. Ревьюер воспроизвёл таблицу дословно.

Побочный выигрыш: логи миграций перестали быть вторым форматом в другом потоке и приезжают в общий JSON.

### Не проверялось / follow-up

**Не проверялось:**
- Поведение под настоящим uvicorn и nginx — все прогоны через `ASGITransport`, адрес клиента подставлялся синтетически.
- `ResendEmailProvider` — не реализован, старт с `EMAIL_PROVIDER=resend` намеренно падает.
- Sentry с настоящим DSN.
- `FOR UPDATE` при параллелизме выше 20 и исчерпании пула соединений.

**⚠️ Два предусловия любого развёртывания за прокси — включая профиль `local` у тестировщика:**
1. `X-06` — лимит по IP общий на всех пользователей. Подтверждено: 12 пользователей с одного адреса дают `[202 ×10, 429, 429]`.
2. `X-07` — Sentry получает исключение мимо нашей защиты; `DETAIL` с адресом почты не убирается `hide_parameters`.

**Follow-up:**
1. `X-03` — OpenAPI объявляет 422, приложение отдаёт 400. **Закрыть до `S0-07`**, иначе фронт сгенерирует типы, которые врут. В `S0-04` это всплыло впервые: до него не было эндпоинтов с телом.
2. Лимита на `verify` нет вовсе — ни в коде, ни в `SPEC.md` §4. Аноним может сжечь чужой код пятью догадками сразу после того, как жертва его запросила. **Продуктовое решение принципала**, не дефект реализации.
3. `/dev/outbox` в `local` не требует аутентификации — кто дошёл до API, читает коды всех адресов. По задумке local-only, но при `APP_ENV=local` на не-локальном хосте это полный обход входа.
4. Retention `dev_outbox` — письма с кодами копятся бессрочно. Вместе с `cleanup_otp` и воркером.
5. Мёртвые секции `[logger_*]` в `alembic.ini` — ревьюер считает тикет избыточным: `env.py` объясняет комментарием, а секции остаются рабочим мутационным рычагом. Снести при следующей уборке в файле.

Мерж — за тобой. Деплоя нет: прода не существует.
