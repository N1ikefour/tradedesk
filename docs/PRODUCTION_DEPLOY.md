# PRODUCTION_DEPLOY — runbook

Updated: 2026-09-03

**Статус: заготовка, не runbook.** Прода нет (`docs/SERVER_STATE.md`), деплой-скриптов нет. Ниже — рамка, которую заполнят задачи `T-02` и работы этапа «рынок СНГ». Ничего из этого не проверено на реальном сервере.

## ⚠️ Коллектор на сервер не переезжает

Интуиция «вынесем на сервер, и всё станет проще» верна для приложения и **неверна для коллектора**.

Коллектор обязан работать на Windows рядом с **запущенным** терминалом MT5: библиотека `MetaTrader5` цепляется к терминалу локально, по сети этого не сделать. Значит при переезде система из «всё на одном компьютере» превращается в **две половины через интернет**.

**Что становится проще:** пользователю не нужны Docker, Postgres и Redis у себя — остаётся одна маленькая программа; журнал доступен с любого устройства; обновления и бэкапы в одном месте; приложение не выключается вместе с ноутбуком.

**Что становится сложнее:**

- **Синк всё равно идёт только когда Windows включён** и терминал запущен. Сервер этого не меняет: данные физически лежат в терминале.
- **`COLLECTOR_TOKEN` уезжает в интернет.** Сейчас он ходит на `localhost`. На сервере это публичный эндпоинт, и `X-27` (нет лимита попыток) из теоретического становится настоящим. Токен один на установку — подобрали его, получили пароли **всех** счетов.
- **`X-07` становится предусловием.** Пароль счёта лежит открытым текстом в кадре стека (`S1-05`), а `sentry_sdk.init()` вызывается без `include_local_variables=False`. С заданным `SENTRY_DSN` первое непойманное исключение увезёт пароли наружу.
- **`/internal/*` перестаёт быть internal.** Сегодня это только название: маршрут висит на общем приложении и в проде доступен оттуда же, откуда весь API. Найдено ревью `S1-05`.

**Вывод для планирования:** переезд на сервер — это не упрощение установки, а размен. Он снимает нагрузку с машины пользователя и добавляет три задачи безопасности, которые на локальной установке спят.

## Что уже зафиксировано решением

- Локальная и self-hosted установка — Docker Compose, профили `local` и `prod` (`SPEC.md` §11.1). Профиль `prod` добавляет Caddy с автосертификатом.
- Миграции применяет контейнер `api` при старте (`alembic upgrade head`), отдельного шага в скрипте нет.
- Скрипты `infra/scripts`: `start`, `stop`, `update`, `backup`, `restore` — в `.bat` и `.sh` (`SPEC.md` §11.3). Задача `T-02`.
- `update` обязан снимать бэкап **до** миграций: обновление не должно потерять позиции и рефлексии тестировщика (`PLAN.md` §6).
- Бэкапы — `pg_dump` в `backups/td-<date>.sql.gz`, хранить последние 14.

## Правила, которые действуют с первого деплоя

Из `DEVELOPER_MANUAL.md` §12 — не отменяются тем, что прода ещё нет:

- Каждое из действий требует **отдельного** явного «да» принципала: деплой, рестарт, миграции, правка env/секретов, правка конфига reverse-proxy, любые деструктивные операции. Одобрение одного не распространяется на следующее.
- Read-only диагностика (логи, health, SELECT) — свободно.
- Перед каждым деплоем — бэкап. Непроверенный restore считается несуществующим.
- Предпочтительный откат — forward-fix (revert-коммит → обычный деплой). Откат БД — только при порче данных.
- После деплоя обязательна верификация (`DEVELOPER_MANUAL.md` §12.4) и `docs:`-коммит с обновлением `docs/SERVER_STATE.md`.

## Чек-лист перед первым внешним запуском

`DEVELOPER_MANUAL.md` §15.7 плюс проектное:

- [ ] Секретов нет в репозитории; env-guards не дают стартовать с дефолтами.
- [ ] `MASTER_KEY` сгенерирован, сохранён принципалом вне репозитория, backfill выполнен.
- [ ] Rate-limit на `auth/request-code` и `auth/verify` работает.
- [ ] Бэкап + проверенный restore на копии данных.
- [ ] `SETUP.md` пройден на чистой Windows-VM без подсказок (`T-06`).
- [ ] Чек-лист приёмки `docs/acceptance-first-test.md` заполнен на своих данных (`T-05`).
