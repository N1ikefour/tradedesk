## Переменные окружения

Шаблон — `.env.example` (содержимое зафиксировано в `SPEC.md` §11.2). Реальный `.env` генерирует `make init`; в репозиторий он не попадает.

Секреты вводит принципал сам. Ассистент проверяет только **присутствие** переменной (`present` / `MISSING`), никогда не печатает значение.

### ⚠️ `MASTER_KEY` — потеря необратима

Пароли брокерских счетов лежат в базе зашифрованными. Ключ шифрования — `MASTER_KEY` — живёт **только в `.env`**, в базе его нет: дамп базы без этого файла бесполезен.

Обратная сторона: **потерял `MASTER_KEY` — потерял все пароли счетов.** Не «сложно восстановить», а невозможно. Пользователю придётся заново вводить investor-пароли всех счетов.

Отсюда правила:

- `.env` попадает в резервную копию отдельно от дампа базы и хранится там, где хранят пароли, а не рядом с дампом.
- Ключ не меняется правкой `.env`. Единственный законный способ — ротация:
  ```bash
  # 1. Новый ключ в MASTER_KEY, прежний — в MASTER_KEY_PREVIOUS
  cd apps/api && python scripts/rotate_master_key.py --dry-run
  cd apps/api && python scripts/rotate_master_key.py
  # 2. Только после «готово» убрать MASTER_KEY_PREVIOUS
  ```
- Ротация перешифровывает **обёртки**, а не сами зашифрованные пароли, поэтому обрыв посреди прогона безопасен: повторный запуск доводит дело до конца, пока задан `MASTER_KEY_PREVIOUS`.
- Убирать `MASTER_KEY_PREVIOUS` можно **только после того, как скрипт сказал «готово»** — он проверяет читаемость всех строк текущим ключом, прежде чем это разрешить.

Почему колонка `key_version` — отпечаток ключа, а не номер: `docs/adr/0003-key-version-as-fingerprint.md`.

## Troubleshooting

Наполняется реальными случаями, а не предположениями.

### Мутационные проверки дают ложный результат из-за кэша `.pyc`

**Симптом:** ломаешь код мутацией — тест зелёный; откатываешь — тест красный. Результаты не воспроизводятся.

**Причина:** CPython считает `.pyc` валидным, сверяя размер исходника и время изменения с точностью до секунды. Две правки одного файла, совпавшие по итоговому размеру и попавшие в ту же секунду, дают старый байткод при новом исходнике.

**Лечение:** гонять мутационные проверки с `PYTHONDONTWRITEBYTECODE=1` либо чистить `__pycache__` между итерациями.

Найдено в `X-02` при десяти мутационных прогонах подряд. Обычную разработку не задевает — только быстрые циклы «сломал → проверил → откатил».

### Прогон на целевой версии Python

На машине разработки стоит 3.14, целевая версия проекта — 3.12. Локальный зелёный прогон не доказывает зелёный CI. Проверка на целевой версии:

```bash
docker run --rm -v "$PWD":/w -w /w -v td-pipcache:/root/.cache/pip python:3.12-slim \
  bash -c 'pip install -q -e "apps/api[dev]" && cd apps/api && ruff check . && mypy . && pytest -m "not integration"'
```

Интеграционные тесты так не гоняются: testcontainers не достаёт опубликованный порт из sibling-контейнера. DDL и SQL от версии интерпретатора не зависят.

Это оформлено целью **`make ci-target`** (S0-06): она поднимает контейнер с целевой версией, ставит зависимости в кэшируемый volume и гоняет ruff, mypy и unit-тесты. Повторный прогон быстрый.

`make ci-target` **дополняет** `make ci`, а не заменяет её: интеграционных тестов и pre-commit в ней нет. Гейт перед PR — по-прежнему `make ci`, авторитетная проверка — GitHub Actions.
