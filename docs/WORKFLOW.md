# WORKFLOW — процесс в этом репозитории

Updated: 2026-09-03

Проектная настройка `DEVELOPER_MANUAL.md`. Мануал описывает систему; здесь — конкретные механики TradeDesk. Философия, запреты и матрица подтверждений мануала действуют без изменений.

---

## 1. Трекер — локальный

Linear в этом проекте не используем: у принципала исчерпан лимит задач. Решение и его цена — `docs/adr/0001-local-ticket-tracker.md`.

**Как устроено:**

| Что | Где | Кто ведёт |
|---|---|---|
| Бэклог — полный список задач с DoD | `SPEC.md` §12 | не дублируется больше нигде |
| Доска статусов | `docs/tickets/BOARD.md` | оркестратор |
| Тикет, взятый в работу | `docs/tickets/<ID>.md` | оркестратор |
| Шаблон тикета | `docs/tickets/_TEMPLATE.md` | — |

**ID задачи — из `SPEC.md` §12**: `S0-01`, `S1-04`, `T-02`. Второй нумерации не заводим.

**Файл тикета создаётся в момент взятия задачи в работу, а не заранее.** Он содержит только то, чего нет в `SPEC.md`: статус, ветку, PR, развилки, принятые решения и итог. Формулировку задачи и DoD не копируем — ссылаемся на `SPEC.md` §12.

**Доска и файлы тикетов живут в `main`, а не в ветке задачи.** Иначе статус задачи виден только после мержа, и доска перестаёт быть источником истины. Оркестратор коммитит их в `main` отдельными `docs:`-коммитами: при взятии в работу, при переводе в `In Review` (вместе с итогом) и после мержа.

Задача, которой нет в `SPEC.md` §12 (баг, находка ревью, follow-up), получает ID `X-NN` по возрастанию и полное описание в своём файле по шаблону `DEVELOPER_MANUAL.md` §8.3.

## 2. Статусы

Соответствуют `DEVELOPER_MANUAL.md` §8.4. Живут в `BOARD.md` и в шапке файла тикета — оба обновляет оркестратор одним движением.

| Статус | Кто ставит | Условие |
|---|---|---|
| `Backlog` | — | задача описана в `SPEC.md` §12 |
| `Todo` | принципал | взята в ближайшую работу |
| `In Progress` | оркестратор | worktree создан, агент запущен |
| `In Review` | оркестратор | реализация + верификация + PR готовы. Не раньше |
| `Done` | **только принципал** | смержено в `main` |
| `Canceled` | принципал | с причиной и ссылкой на замену |

## 3. Ветки и worktree

- `main` — всегда деплоябелен, мержит только принципал.
- Ветка задачи: `feat/<ID>-<slug>` (`SPEC.md` §2.2). Типы по Conventional Commits: `feat/`, `fix/`, `chore/`, `docs/`.
- Worktree задачи: `.claude/worktrees/<ID>` — обязателен для тикетной работы, в `.gitignore`.
- Chat-driven правки без тикета (опечатка, доки, обсуждение) — прямо в `main` отдельным коммитом, в основной папке.

```bash
git worktree add .claude/worktrees/S0-01 -b feat/S0-01-monorepo-skeleton
```

Один тикет = один worktree = один владелец = один PR. Несколько агентов в одном тикете работают **последовательно** в одном worktree. Параллельно — только разные тикеты.

После мержа: `git pull --ff-only` → `git worktree remove` → `git branch -d` → проверить `git worktree list`.

## 4. Коммиты и PR

Коммит — Conventional Commits, как в `SPEC.md` §2.2 и `DEVELOPER_MANUAL.md` §7.2:

```
feat(ingest): S1-04 POST /ingest/deals

Зачем и что на уровне решения, буллетами.
Контракты и edge-кейсы, если важны для истории.

S1-04.

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

Doc-обновления — всегда отдельным `docs:`-коммитом, не смешиваются с кодом.

Тело PR — по шаблону `DEVELOPER_MANUAL.md` §7.3, с поправкой: вместо ссылки на трекер — строка `Тикет: docs/tickets/<ID>.md`.

Коммитит и пушит **оркестратор после ревью**. Агенты не коммитят.

---

## 5. Итог задачи

Авторитетная запись — раздел `## Итог` в файле тикета (заменяет комментарий в трекере, `DEVELOPER_MANUAL.md` §8.5). Пишется оркестратором до перевода в `In Review`, коммитится вместе с PR или отдельным `docs:`-коммитом.

Задача завершена, когда: смержена, задеплоена (если требовалось), итог написан, живые доки обновлены, принципал поставил `Done` в `BOARD.md`.

## 6. Ревью

Полностью по `DEVELOPER_MANUAL.md` §9. Проектные акценты для ревьюера — в `.claude/agents/reviewer.md`. Отдельной security-роли нет: security-пункты чек-листа §9.2 обязательны в каждом ревью, отдельный аудит заказывается перед вехой «Первый тест».
