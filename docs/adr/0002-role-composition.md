# ADR-0002: состав ролей агентов на этапы 0–2
Дата: 2026-09-03. Статус: accepted.

## Контекст

`DEVELOPER_MANUAL.md` §4.7 требует подбирать состав ролей под конкретный проект, а не брать список §4.1 целиком: роли «про запас» не создаются (§1.2). Нужно решить, кого заводим сейчас, под задачи `SPEC.md` §12 этапов 0–2.

## Варианты

1. **Полный состав §4.1** (оркестратор, lead, backend, frontend, designer, infra, qa, reviewer) — ничего не забыто. Минус: четыре роли без работы на этапе 0; файлы ролей устаревают раньше, чем понадобятся.
2. **Минимум (оркестратор + reviewer)** и всё остальное силами оркестратора. Минус: теряется главная ценность — независимость ревьюера от автора и зона владения путями; backend и frontend начинают толкаться в одном контексте.
3. **Под задачи этапов 0–2**: оркестратор, backend, frontend, collector, infra, reviewer.

## Решение

Вариант 3. Утвердил принципал 2026-09-03.

Обоснование по каждой роли:

| Роль | Почему нужна сейчас |
|---|---|
| Оркестратор | обязательный минимум §4.7 |
| Reviewer | обязательный минимум §4.7. Отдельной security-роли нет: security-пункты §9.2 обязательны в каждом ревью, отдельный аудит заказывается перед вехой «Первый тест» |
| Backend | `apps/api` — ядро этапов 0–2, 20 из 38 задач |
| Frontend | `apps/web` — этап 0 (S0-07, S0-08) и весь этап 2 |
| Collector | `apps/collector-mt5` — **отдельная роль, а не часть backend**: синхронный код против async, только Windows, вне Docker, и верификацию физически нельзя прогнать на машине разработки (macOS) — проверяет принципал руками. Это ролевые отличия (scope, workflow, verification), а не доменные |
| Infra | `docker-compose.yml`, `Makefile`, `infra/`, CI — S0-01, S0-06, T-02 |

Отложены:

| Роль | Когда заводим |
|---|---|
| QA | этап 2 / веха «Первый тест» — там появляются smoke, E2E и чек-лист приёмки (`T-05`, `T-06`) |
| Designer | с `S2-06` (UI журнала). Носитель дизайна — живой прототип в коде на ветке (web-стек, §4.5), внешний инструмент не нужен |
| Lead | декомпозиция уже сделана в `SPEC.md` §12. Понадобится на задачах вне спеки |

## Последствия

- Skills создаются только там, где есть собственный домен (§4.4). Сейчас это `ingest-mt5`. `backend-api` и `web-ui` откладываются до появления эталонных модулей (`S0-02`, `S0-07`): skill — конденсат работающих паттернов, а не догадка о них.
- Один неймспейс — `.claude/`. Зеркал для второй ассистент-системы нет (решение принципала); при появлении второй системы роли и skills зеркалятся с идентичным содержимым.
- Состав пересматривается тем же циклом при изменении скоупа; неиспользуемые роли удаляются, а не копятся.
