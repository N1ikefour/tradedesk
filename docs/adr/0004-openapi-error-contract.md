# ADR-0004: формат ошибок описывается в OpenAPI глобально
Дата: 2026-09-04. Статус: accepted.

## Контекст

`SPEC.md` §5.1 фиксирует единый формат ошибки: `{"error": {"code", "message", "details"}}`. Реализация (`S0-02`, `apps/api/app/core/errors.py`) ему следует, в том числе приводит `422` от FastAPI к `400 validation_error` с `details.fields`.

**Но OpenAPI об этом не знает.** FastAPI автоматически объявляет для эндпоинтов с параметрами `422 HTTPValidationError` — схему, которой приложение никогда не отдаёт. Ни один из кодов словаря §5.1 в схеме не описан вовсе.

`CLAUDE.md` прямо говорит: фронт генерирует типы из OpenAPI (`make types` → `apps/web/src/api/schema.d.ts`). Значит `S0-07` получит типы, не соответствующие реальным ответам, и обработка ошибок во всех фичах будет писаться по неверному контракту.

Найдено ревью `S0-02`, независимо подтверждено автором `S0-04` — там появился первый эндпоинт с телом запроса, и расхождение стало наблюдаемым.

## Варианты

1. **Общая модель ошибки + `responses=` на каждом эндпоинте.** Точно и явно. Минус: требует дисциплины на каждом новом маршруте; забытый `responses=` возвращает расхождение молча, и заметить это можно только на фронте.
2. **Переопределить генерацию схемы приложения один раз:** объявить модель ошибки глобально, заменить автоматический `422` на наш `400`, добавлять `responses=` только там, где эндпоинт производит специфичный доменный код. Минус: правка схемы в одном месте менее очевидна для читателя маршрута.
3. **Не описывать ошибки в схеме вовсе.** Фронт типизирует только успешные ответы, ошибки разбирает общим хелпером. Минус: генератор типов не даст фронту ни кодов, ни формы `details`, и каждая фича будет угадывать.

## Решение

**Вариант 2.** Утвердил оркестратор 2026-09-04 в рамках `X-03`.

Аргумент: словарь кодов из §5.1 стабилен и общий для всего API, а формат ошибки одинаков для **каждого** маршрута. Описывать одно и то же на каждом эндпоинте — это дисциплина, которая обязательно даст сбой; вариант 1 переносит цену ошибки на фронт и обнаруживается поздно. Вариант 3 отказывается от главной ценности генерации типов ровно там, где она полезнее всего: ошибки — то, что фронт обрабатывает чаще успеха.

Специфичные коды (`invalid_code`, `too_many_attempts` из `S0-04`) объявляются на своих эндпоинтах поверх глобального набора.

## Последствия

- `/api/v1/openapi.json` перестаёт обещать `HTTPValidationError`, которого приложение не отдаёт.
- Фронт в `S0-07` получает из `make types` реальную форму ошибки и словарь кодов.
- Расхождение схемы и поведения становится проверяемым: тест сверяет фактический ответ с тем, что объявлено.
- Новый доменный код ошибки требует объявления на своём эндпоинте — иначе он не попадёт в типы. Это осознанная цена: глобально объявлен только общий набор.
- Коды §5.1, которых пока никто не производит (401, 403, 409, 429), объявляются сразу — фронт сможет обрабатывать их до появления производителей.
- Расширения `S0-02` (`405 method_not_allowed`, `415 unsupported_media_type`), которых нет в §5.1, тоже попадают в схему. Словарь §5.1 при следующей правке спеки стоит дополнить.

  **Поправка от 2026-09-04 (ревью `X-03`):** утверждение «фреймворк их порождает» верно только для 405. Ревью проверило grep'ом по пакету и двумя живыми пробами: FastAPI 415 **не ставит нигде**, неподходящий `Content-Type` даёт `400 validation_error`. Формулировку дал оркестратор при постановке `X-03`, и она успела уехать в `SPEC.md` v1.5 — исправлено в v1.5.1. Код 415 остаётся объявленным как «производителя пока нет»: он появится в `S2-04` с загрузкой вложений.
