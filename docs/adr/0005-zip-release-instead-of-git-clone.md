# ADR-0005 — Дистрибуция zip-архивом с релиза вместо `git clone`

**Дата:** 2026-09-05
**Статус:** Принято
**Решил:** принципал

## Контекст

`SETUP.md` (`S0-09`) доводит человека до входа в приложение за семь шагов, второй из которых — `git clone`. Для целевого пользователя это лишняя программа (Git for Windows) и лишнее понятие (репозиторий, ветка, клонирование) на самом раннем шаге — до того, как он увидел хоть какой-то результат.

`SPEC.md` §11.3 фиксирует `update.bat|sh` как `backup` → `git pull` → `build` → `up`, то есть предполагает, что у пользователя есть рабочая копия репозитория.

## Решение

Пользователь получает **zip-архив со страницы релизов GitHub**: скачал, распаковал, запустил `start.bat`. Git из требований уходит полностью.

Разработчики продолжают работать через клон — решение касается только дистрибуции.

## Последствие, которое обязано быть закрыто до передачи

**Обновление больше не может опираться на `git pull`.** И это не только замена команды.

При обновлении из архива человек естественно распакует новую версию **в новую папку**. Там нет `.env`, значит `make init` (или `init.bat`) создаст новый `MASTER_KEY`. Данные при этом лежат в именованном docker-томе, который переживает всё, и в них — пароли брокерских счетов, зашифрованные **старым** ключом.

Приложение поднимется. Журнал будет на месте. Счета отвалятся с ошибкой расшифровки, и человек не свяжет это с обновлением.

Поэтому `update` обязан:

1. работать **внутри существующей установки**, а не рядом с ней;
2. отказываться выполняться, если `.env` не найден, — громко, с объяснением, а не создавать новый;
3. сверять `MASTER_KEY` с тем, которым зашифрованы данные в томе, **до** того как что-то менять.

Третий пункт — не паранойя: это единственная защита от сценария «распаковал в новую папку и запустил там». Схема хранения ключа уже несёт отпечаток (`key_version`, см. ADR-0003), то есть проверка возможна без расшифровки.

## Что меняется в спеке

`SPEC.md` §11.3, строка `update.bat|sh`: `git pull` заменяется на скачивание и распаковку релиза поверх существующей установки, с сохранением `.env` и каталога `backups/`.

Появляется требование к CI: сборка zip-артефакта на релизном теге. Артефакт не должен содержать `.git`, `node_modules`, `.venv`, `backups`, `.env`.

## Альтернативы

**Оставить `git clone`.** Дешевле всего — ничего не делать. Отвергнуто: барьер стоит на втором шаге из семи, до первого результата, и требует установки программы, которая больше нигде в сценарии не нужна.

**Установщик (`.msi` / `.exe`).** Самый привычный для Windows путь. Отвергнуто на этом этапе: требует подписи кода (иначе SmartScreen ругается сильнее, чем на zip), а объём работы несопоставим с задачей «дать одному человеку попробовать».

**Docker-образ, публикуемый в registry.** Убирает и распаковку. Отвергнуто: всё равно нужен `docker-compose.yml` и `.env` на машине, то есть архив никуда не девается — только становится меньше.

## Цена

- Появляется релизный процесс, которого раньше не было: теги, сборка артефакта, changelog.
- `update` усложняется: скачивание, проверка целостности, сохранение `.env` и бэкапов.
- Пользователь не получает историю версий — откатиться можно только на предыдущий архив.
- Обновление перестаёт быть атомарным: между распаковкой и стартом установка находится в промежуточном состоянии. Отсюда требование делать `backup` **до** распаковки, а не после.
