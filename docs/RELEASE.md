# RELEASE — как выпускается версия

Пользователь получает zip со страницы релизов, а не клонирует репозиторий
(`docs/adr/0005-zip-release-instead-of-git-clone.md`). Здесь — как этот архив
собирается, что в нём лежит и что проверяется до публикации.

Инструкция для того, кто ставит приложение, — `SETUP.md`, шаг 2.

---

## Выпустить релиз

```bash
git checkout main && git pull
git tag v0.2.0
git push origin v0.2.0
```

Дальше всё делает `.github/workflows/release.yml`: собирает архив, проверяет его и
публикует релиз с двумя файлами — `tradedesk-<версия>.zip` и `…zip.sha256`.
Тег вида `vX.Y.Z-rcN` публикуется как pre-release.

Собрать тот же архив у себя, ничего не публикуя:

```bash
make release VERSION=v0.2.0     # → dist/tradedesk-0.2.0.zip и .sha256
```

CI зовёт **эту же цель**. Другого способа собрать релиз нет намеренно: артефакт и есть
продукт, и «в CI собралось иначе» здесь означало бы, что проверить его до публикации
нечем.

### Тег обязан стоять на main, и гейт по нему обязан быть зелёным

Оба условия `release.yml` проверяет сам, до сборки, а не принимает на веру:

- `git merge-base --is-ancestor` — коммит тега есть в `origin/main`. Триггер срабатывает
  на теге в **любой** ветке, так что без этой проверки на страницу релизов уезжает код,
  которого `ci.yml` не видела.
- заключение `ci.yml` **по этому же SHA** равно `success`, с ожиданием до 30 минут.
  `git push origin main --tags` запускает оба workflow одновременно, и релизный успевает
  опубликоваться раньше, чем гейт покраснеет. «Последний прогон» здесь смотреть нельзя —
  это будет чужой прогон.

Отменённый прогон (`ci.yml` отменяется своей `concurrency`, если следом в main прилетел
ещё коммит) считается непройденным гейтом. Лечится перезапуском `ci.yml` на нужном
коммите и повторным пушем тега.

⚠️ Обе проверки — защита от ошибки, не от злого умысла: workflow берётся из коммита тега,
поэтому тот, кто может запушить тег, может запушить и ветку с вырезанными проверками.
Закрывается это только правилом на теги в настройках репозитория — см. открытые вопросы.

## Что внутри

Правило одно: **репозиторий минус то, что пользователю не нужно или вредно**. Не
список включений — он забывает новый каталог на следующей же задаче, и релиз молча
приезжает без него.

Не попадает в архив:

| Что | Почему |
|---|---|
| `.env`, `node_modules`, `.venv`, `backups/`, `dist/`, кэши | их не видит `git ls-files` — они в `.gitignore` |
| `.github/` | конфиг CI, на машине пользователя не работает |
| `.claude/` | файлы ассистентов |
| `docs/tickets/` | внутренняя кухня: порты, worktree, черновики решений |

Всё остальное едет как есть, включая `docs/` и тесты: расхождение «из клона работает,
из архива нет» — худший из возможных багов для артефакта дистрибуции, и лучший способ
его не получить — не расходиться.

Внутри архива один каталог `tradedesk-<версия>/`, чтобы распаковка в «Загрузки» не
рассыпала три сотни файлов.

**Образы не собираются заранее.** Пользователь собирает их у себя (`docker compose
build`). Готовые образы потребовали бы registry и авторизации в нём на машине, где мы
экономим каждый шаг установки, а базовые образы всё равно качаются из сети.

## Версия

Приложение печатает версию на `/api/v1/version`, а берёт её из метаданных
установленного пакета (`importlib.metadata` → `apps/api/pyproject.toml`). Цепочка:

```
тег v0.2.0  →  apps/api/pyproject.toml в архиве: version = "0.2.0"
            →  pip install при сборке образа
            →  importlib.metadata
            →  GET /api/v1/version → {"version": "0.2.0"}
```

Версия проставляется **в архиве**, а не в репозитории: расходиться нечему, забыть
поднять номер перед тегом невозможно. В репозитории `version` остаётся прежней — это
и есть признак «сборка не релизная».

Тот же номер лежит в файле `VERSION` в корне архива — чтобы узнать версию установки,
не поднимая её (это понадобится `update` из `T-02`).

`v` в тег входит, в версию пакета — нет; `-rc1` в версии пакета пишется как `rc1`
(PEP 440).

## Что проверяется до публикации

`infra/scripts/make-release.sh` не собирает архив, пока не сойдётся:

- форма тега — `vX.Y.Z` или `vX.Y.Z-rcN`, **без ведущих нулей**: `v01.2.3` выглядит
  допустимым, но PEP 440 нормализует его в `1.2.3`, и на релизе будет написано одно,
  а `/api/v1/version` вернёт другое;
- в составе нет символических ссылок. `cp` разыменовывает симлинк, поэтому `notes.txt`,
  указывающий на файл вне репозитория, уехал бы в архив **содержимым** этого файла —
  проверка на `.env`-подобные имена такого не ловит, имя обычное;
- в составе нет неотслеживаемых файлов. Это отказ, а не предупреждение: цена ошибки —
  чужой файл на странице релизов. Осознанно собрать вместе с ними —
  `RELEASE_ALLOW_UNTRACKED=1 make release VERSION=…`;
- в составе нет `.env` и подобных файлов окружения, `.git`, `node_modules`, `.venv`,
  `backups`, `dist`, кэшей, `docs/tickets`;
- все имена файлов — ASCII (Windows-распаковщик корёжит остальное, а путь установки
  у первого пользователя и так кириллический — `X-43`);
- на месте всё, без чего не пройдёт `SETUP.md`: `docker-compose.yml`, `Makefile`,
  `.env.example`, скрипты, `Dockerfile`-ы, `VERSION`;
- у `infra/scripts/*.sh` и `docker-entrypoint.sh` есть бит исполнения — и он **пережил
  упаковку**: архив тут же распаковывается обратно и права проверяются на распакованном;
- версия в `pyproject.toml` разбирается как toml и равна тегу.

Проверки имён и симлинков идут по **отфильтрованному** составу, а не по всему дереву:
тикеты у нас пишутся по-русски, и черновик `docs/tickets/решение.md` блокировал бы
релиз, хотя в архив не попадает.

Изменённый отслеживаемый файл архив не блокирует — он уедет в том виде, в каком лежит
на диске, — но упоминается в выводе отдельной строкой. Молча собранный релиз
с недоделанной правкой в `SETUP.md` обнаруживается только у пользователя.

`.github/workflows/release.yml` добавляет к этому главное: **собирает образ api из
распакованного архива** и читает версию из установленного в нём пакета. Исходники в
репозитории проверяет `make ci`; то, что из архива собирается рабочий образ с верной
версией, не проверяет больше никто — а уезжает человеку именно он.

Контрольная сумма (`sha256`) публикуется рядом. Она нужна не от злоумышленника —
от оборванной загрузки, которая иначе проявится непонятной ошибкой на сборке;
`update` из `T-02` сверяет её, не спрашивая человека.

Побайтовой воспроизводимости у сборки нет: zip хранит время файлов, и два прогона на
одном теге дают разные суммы. Сумма привязана к **опубликованному файлу**, а не к тегу —
пересобирать релиз и класть его поверх старого нельзя, это сломает проверку у того, кто
уже скачал.

### Кто проверяет сам сборщик

`infra/scripts/test-make-release.sh` — `make test-release`, входит в `make ci-api`.
Собирает архивы в синтетических репозиториях (тесту нужно коммитить симлинки, `.env`
и `node_modules`, чего в рабочем дереве делать нельзя) и держит по случаю на каждую
проверку из списка выше. Снятая проверка = красный тест с понятным именем.

Это единственный страж артефакта: `release.yml` запускается **по тегу**, то есть тогда,
когда ломать уже поздно. Сломанная регулярка запрещённых путей без этого теста
не покраснела бы нигде — архив собрался бы и опубликовался.

Отдельным случаем закрыт `Makefile`: значение `VERSION` доезжает до скрипта окружением,
а не подстановкой в тело рецепта. Подстановку выполняет `sh`, а значение тега
контролирует любой, кто может запушить тег, — и джоб релиза ходит с `contents: write`.

## Как этим пользуется `update` (`T-02`)

`infra/scripts/update.sh` написан, и вот на какие свойства архива он опирается:

- Внутри архива один каталог `tradedesk-<версия>/` — распаковка «поверх установки»
  снимает этот уровень, иначе получилась бы вложенная копия.
- Распаковка **не удаляет** файлы, которых в новой версии нет: старый файл переживёт
  обновление. Если это когда-нибудь начнёт мешать, чинится списком файлов, а не zip'ом.
- `.env` и `backups/` в архиве отсутствуют, поэтому распаковка их не затрёт — но и не
  спасёт: `MASTER_KEY` живёт только в `.env` (ADR-0005). Поэтому `update` сверяет
  отпечаток ключа из `.env` с `key_version` в `account_credentials` **до** всего
  остального и отказывается работать, если они разошлись.
- Установленную версию `update` читает из файла `VERSION` в корне, не поднимая
  приложение; поднятое — отдаёт её же на `/api/v1/version`. Обе величины не просто
  печатаются в отчёте, а **сверяются**: разошлись — обновление считается незавершённым
  и заканчивается отказом.

  ⚠️ Расхождение здесь — не теория. Время файла zip хранит с точностью до двух секунд,
  поэтому у двух подряд собранных архивов контекст сборки выходит побайтово одинаковым,
  BuildKit берёт слой из кэша и собирает **предыдущий** код поверх новых файлов. Человек
  видит новый номер в `VERSION` и старое поведение — «обновился, и не помогло». Лечится
  `docker compose build --no-cache api` и повторным `update`.
- Отсутствие `VERSION` для `update` означает «это клон, а не установка» — и он
  отказывается распаковывать архив поверх рабочей копии.
- Контрольную сумму `update` сверяет сам, до распаковки.
- `update.sh`, `backup.sh`, `restore.sh`, их `.bat` и `common.sh` внесены в списки
  `REQUIRED` и `EXECUTABLES` сборщика: релиз без скриптов обновления или с потерянным
  на них битом исполнения не соберётся вовсе.

**Скачивание ассета аккаунта GitHub не требует.** Репозиторий открыт 7 сентября 2026:
анонимный запрос к API отдаёт 200 и `"private": false`. `update` ходит за релизом
без токена и без заголовка `Authorization`. На **нашем** ассете это не проверено —
проверять не на чем, релизов нет (см. открытые вопросы); сам путь «скачать релизный
ассет анонимно» проверен на чужом публичном репозитории.

## Открытые вопросы

- **Ни одного релиза ещё не опубликовано.** `GET /repos/N1ikefour/tradedesk/releases`
  отдаёт пустой список, удалённых тегов `vX.Y.Z` нет. Прогон `X-19` был живым, но его
  релиз с тех пор убран, а значит **путь «человек открывает страницу релизов и качает
  архив» сейчас не работает ни у кого**: качать нечего. `SETUP.md` шаг 2 и `update`
  без аргументов упрутся в это первым делом. Закрывается пушем тега — действие
  принципала.
- **SmartScreen и пометка «скачано из интернета» не проверялись:** Windows-машины у
  нас нет. Нужен ли шаг «Разблокировать» перед распаковкой, выясняет `T-06`; в
  `SETUP.md` это место помечено плашкой. Отдельно это заденет `S1-10`: скачанный
  `install-service.ps1` с такой пометкой блокирует политика выполнения PowerShell.
- **Правила на теги в репозитории не настроены.** Проверки «тег на main» и «`ci.yml`
  зелёная» живут в `release.yml`, а он берётся из коммита тега — значит, обходятся
  веткой с вырезанными проверками. Это защита от ошибки, а не от злого умысла. От
  второго защищает только ruleset на `refs/tags/v*` в настройках GitHub (кто может
  создавать теги; запрет на перезапись существующего). Настройка репозитория —
  действие принципала, кодом из PR не делается.
- **Changelog не ведётся.** Тело релиза сейчас — короткая инструкция и контрольная
  сумма. `CHANGELOG.md` заводится, когда появятся внешние потребители изменений
  (`DEVELOPER_MANUAL.md` §7.4).
